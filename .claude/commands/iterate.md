# 反復を 1 回回す（既定の開発サイクル）

**引数（任意）:** スライス番号または内容（例: `/iterate S03`、
`/iterate CSVのフィルタ`）。省略時は `docs/backlog.md` の最上段を取る。

**1 回の反復で 7 点セットを全部そろえる。** 上げる成熟度は 1 段だけ
（L0 → L1、または L1 → L2）。2 段まとめて上げない。
目安は **半日以内** 。超えたらスライスが大きすぎる。

> **省くのは分量であって、成果物の種類ではない。**
> 要求仕様書・設計書・単体テスト・実装・統合テスト・テスト結果まとめ・
> マニュアルの 7 点は毎回そろえる（正: `agile-process/deliverables.md`）。
> 1 つでも次の反復へ送ったら、その 1 つは二度と書かれない。

## 実行方針

**原則としてユーザーの介入なしに完了まで進む。** 停止するのは次の 3 つだけ:

1. **不可逆な操作を含む** ことが判明した（削除・課金・外部送信）→
   厚い経路（`/add-feature`）へ切り替える判断をユーザーに確認する
2. **ゴールの外** の実装が必要になった（`docs/concept.md` の非目標に触る）
3. **仕様と実装が矛盾した** （勝手にどちらかへ合わせない。絶対ルール 3）

**停止しない**（自分で決めて記録して進む）もの:

- 層の割り当て・契約を切るか・命名 → `Skill('layered-architecture')` に従い決め、
  設計書の「判断の記録」に理由と却下案を書く
- 仮実装で済ませるかどうか → L1 なら仮実装で進め、負債に記録する
- 仕様の細部 → L1 は正常系だけ。境界値は L2 の反復に回す

ただし **節目 3 か所では短い報告を出す**（承認は待たない。下の各段を参照）。
`.steering/local-mode.md` が存在する場合は無停止で実行せず、
`.claude/local-llm/policy.md` に従いステップごとに停止して報告する。

## 前提

- 骨組みが通っていること（`docs/backlog.md` の「骨組み」が `通った`）。
  通っていなければ **このコマンドを実行せず `/skeleton` を案内する**
- 着手中のスライスが無いこと（WIP = 1）。あればそれを先に終わらせる

## 段0: 選ぶ（1 本だけ）

1. `docs/backlog.md` を読む
2. 引数が無ければ `maturity.md` の PM ルールで対象と目標レベルを決める:
   - L0 のスライスが残っている → 最上段の L0 を L1 へ
   - 全スライスが L1 → 価値の高い順に L2 へ
   - 負債が反復 2 回分たまっている → **`/refactor` を先に案内して終了する**
3. 対象と目標レベルを宣言する（例: `S03 を L0 → L1`）
4. `Skill('steering')` で `.steering/[YYYYMMDD]-[S##-名前]/` を作り、
   `tasklist.md`（7 点セットのチェックリスト）と `INDEX.md` を置く
5. バックログの「いま着手中」を `S## 段0 準備中` に更新する
6. **Issue 追跡が `on` のときだけ** —— `issue_mode.py` の終了コードで判定し
   （0 = on、1 = off、2 = 未設定）、on なら `Task(issue-manager)` に
   「対象 Issue を開いて着手を示す」を依頼する。 **off なら何もしない**
   （`gh` を呼ばない。判定を記憶で行わない）

**以降、段が変わるたびに「いま着手中」を `S## 段n {何を}（担当）` に更新し、
`INDEX.md` に 1 行追記する。** これがユーザーの追跡手段になる。

## 段1: 要求仕様書（`requirement-writer`）

`Skill('slice-definition')` と `Skill('usdm')` に従い
`docs/usdm/src/S##-<name>.html` を書く。

| 目標 | 書くもの | 上限 |
|---|---|---|
| L0 → L1 | 要求＋ **理由** ＋ 仕様（正常系） | 要求 1・理由 1 行・仕様 3 条 |
| L1 → L2 | 同じ要求の仕様に境界値・失敗経路を追記 | 制限なし（ここは網羅する） |

- 表の下の **トレース表** は枠だけ用意する（埋めるのは各成果物の担当）
- 検証: `<ツール実行コマンド> .claude/tools/build_usdm.py` が 0
- 厚い経路が必要か判定する（`agile-process` の「いつ厚く書くか」）。
  該当したら停止例外 1 としてユーザーに確認する
- **節目報告①**: 要求 1 行・理由 1 行・仕様の数を出す

## 段2: 設計書（`designer`）

`Skill('functional-design')` に従い `docs/design/S##-<name>.md` を書く。

- **構造を表す図を 1 枚**（`flowchart TD`。層は色分け、契約は破線）
- 構成 10 行（層・契約・入口・流れ・配線・仮実装）
- **判断の記録**（採用した理由・他の選択肢・メリデメ）
- 層と契約の正は `Skill('layered-architecture')` 。
  外部 I/O は契約経由。無いなら契約を切らない（切らない判断も記録する）
- **判断点に当たったら `Skill('option-first')` で選択肢を出す** ——
  後戻りコストが高い / 家風に影響する / 名前が外に出る、の 3 つと
  プロファイルの「選択領域」だけ。 **L1 の反復では最大 1 回**
  （それ以外は推奨で進み、却下案ごと「判断の記録」に書く）
- 検証: `powershell -File .claude/tools/check_diagrams.ps1 -Path <設計書>` が 0
- トレース表の「設計」列を埋める
- **節目報告②**: 層と契約の要点 1 行 ＋ **却下した案 1 行** を出す

## 段3: 単体テスト（`unit-tester`）

`Skill('development-guidelines')` と `Skill('visual-debugging')` に従う。

1. 設計書の入口に対してテストを先に書く（docstring 4 項目必須）
2. プロファイルの範囲指定テストコマンドで **Red を確認** する（件数を記録）
3. Red が確保できなかったテストは変異テストで有効性を確認する:

   ```
   <ツール実行コマンド> .claude/tools/mutate.py --file <実装> --find <正> --replace <誤> --expect <テスト名>
   ```

   SURVIVED が出たらテストの穴なので、テストを足してから進む
4. コミットする（接頭辞 `テスト:`。赤いままでよい唯一の段）

## 段4: 実装（`coder`）

1. Red を消す **最小限** のコードだけ書く（設計書の層・契約・関数名に従う）
   - **L1**: 仮実装・ハードコード可。ただし 4 層には分ける
   - **L2**: 仮実装を消す。想定内の失敗は結果値で返す
2. プロファイルの全体テストコマンドで全緑を確認する
3. コミットする（接頭辞 `実装:`。差分 20〜30 行を超える前に区切る）
4. トレース表の「実装」列を埋める

**テストは追加も変更もしない。** テストが間違っていると思ったら段3 へ差し戻す。

## 段5: 統合テスト（`integration-tester`）

**この段を飛ばさない。** 反復ごとに完走できることを確かめるのが背骨。

1. プロファイルの統合テストコマンドで **既存の E2E を含めて** 実行する
   （骨組みの E2E が赤くなったら回帰。直してから進む）
2. 目標が L1 なら、このスライスの仕様に対応する E2E を 1 本足す
3. 目標が L2 なら、仕様 1 条につきテスト 1 本以上にする
4. プロファイルの動作確認コマンドで実物を動かし、出力を得る

## 段6: テスト結果まとめ（`test-summarizer`）

`Skill('test-reporting')` に従い `docs/test-reports/S##-<name>.md` を書く。

- 実測の件数（プロファイルの「テスト件数の数え方」。手計算しない）
- 仕様番号 → テスト名 → 結果の対応表（ **未カバーの仕様も行に残す** ）
- 実物を動かした出力をそのまま
- 緑になった仕様の検証欄を `□` → `☑` にし、トレース表のテスト列を埋める

## 段7: マニュアル（`manual-writer`）

`.claude/skills/writing-conventions/guides/manual.md` に従い
`docs/manual.md` を更新する。

- 共通 3 節（環境構築・実行方法・テストの実行方法）が最新かを毎回確かめる
- `## S## <スライス名>` の節を足す（何ができるか・最小の実行例＋実測の出力・
  引数の表。L2 以降は落とし穴も）
- トレース表の「マニュアル」列を埋める

## 段8: 検証と記録

1. `implementation-validator` を起動する。プロンプトに
   **「対象は S##、現在 L{n}、目標 L{n+1}。maturity.md の目標レベルの列だけで
   判定してください」** を明記する
   - 目標レベルの [必須] があれば直して再検証する
   - **上のレベルの指摘は負債候補として受け取り、不合格の理由にしない**
   - 安全機構に触れた場合のみ `security-checker` を併走させる
2. `doc-syncer` を起動する（チェックリスト A）。ハブ・バックログ・負債表・
   要求一覧・構成・現在地を同期する
3. **Issue 追跡が `on` のときだけ** —— `issue-manager` に、実測での
   チェックリスト更新・成熟度ラベルの張り替え・完了報告のコメントを依頼する
   （閉じるのは L3 に到達したときだけ）
4. **節目報告③**: 5 行サマリ（下の「完了後の報告」）を出す

## 完了条件（すべて機械で確認する）

- [ ] **`check_deliverables.py --slice S##` が 0**（7 点セットがそろっている）
- [ ] **`build_usdm.py` が 0**（理由の欠落・番号の不整合・トレースの切れが無い）
- [ ] 全テストが緑（骨組みの E2E を含む。passed / skipped を報告に含める）
- [ ] 実物を動かした出力がテスト結果まとめとハブに貼られている
- [ ] 残した手抜きが負債表に記録されている
- [ ] `docs/backlog.md` の成熟度・着手中・次の一手が更新済み
- [ ] `.steering/<反復>/tasklist.md` の 7 点がすべて `[x]`
- [ ] 未コミットの変更が残っていない

## 完了後の報告（5 行）

```
ゴール: {docs/concept.md の一行}
到達:   L3 {n}本 / L2 {n}本 / L1 {n}本 / L0 {n}本（全 {N} 本）
一式:   {n}/{n} 本がそろっている（欠けは S##: {何が}）
負債:   {n} 件（痛み高 {n} 件）
次の一手: {1 つだけ}
```

次の一手は `maturity.md` の PM ルールに機械的に当てはめて 1 つだけ出す。
詳しく見たいときは `/status`（1 画面のダッシュボード）を案内する。

## やってはいけないこと

- **7 点のうち 1 つを次の反復へ送る**（最も重い失敗）
- 段の順序を入れ替える（実装してから要求・設計を書き写す）
- 2 段まとめて上げる（L0 → L2）
- 目標が L1 のときに境界値・失敗経路・文書整備をやる
- 手抜きを記録せずに残す
- 骨組みの E2E が赤いまま次へ進む
- 着手中のスライスを残して別のスライスに移る
