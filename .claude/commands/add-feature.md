# フェーズの追加実装（原則自動実行モード）

**引数:** P番号または機能名（例: `/add-feature P03`、`/add-feature ユーザー認証`）

**実行方針:** このワークフローは原則としてユーザーの介入なしに完了まで自動で
実行する。各ステップ完了後、ただちに次へ移行する。 **ただし以下の3つの例外では
必ず停止してユーザーに確認する**:

1. **設計と実装の矛盾**: 設計書どおりに実装できない・設計判断の変更が必要
2. **破壊的操作**: ファイル削除・git の履歴改変・凍結文書に触れる事態
3. **スコープ変更**: 引数で指定されたフェーズの範囲を超える実装が必要になった

なお **ステップ1（要求仕様）の未確定事項の確認は例外扱い** で、
AskUserQuestion を使ってよい（要求の推測は後工程すべてを汚染するため）。

## 前提

`CLAUDE.md` の **プロジェクトプロファイル** が整備されていること。
無ければ先に `/setup-project` を実行する（コマンド・パスを推測させない）。

**`.steering/local-mode.md` が存在する場合は無停止で実行しない** ——
ローカル LLM で駆動しているので、`.claude/local-llm/policy.md` に従い
**ステップ 1 つごとに停止して報告する** 。以降の「原則自動実行」は
そのときだけ「原則ステップ停止」に読み替える。

## サブエージェントの使い方（レポート駆動・全ステップ共通）

コンテキストを圧迫する作業（多数ファイルの読み込み・長いログの精読・
テスト/ビルドの実行）は `.claude/agents/` のサブエージェントに委譲する。
全エージェントは知覚-行動ループ（`report-protocol.md` の「0. 動作原理」）で
動き、行動は常に Tool を通す。プロセス全体をエージェント常用で進める場合の
指揮手順は `.claude/agents/orchestrator.md` を参照:

- 起動プロンプトに **steering ディレクトリのパスを必ず含める**
  （サブエージェントはノートを読んで経緯を回復し、結果を
  `reports/[NN]-<name>.md` に書き出す）
- 応答は「レポートパス + 要約」だけ受け取る。対処が必要なときだけ
  該当レポートを読む（親のコンテキスト節約）
- 自分（親）の重要な決定は decisions.md に、作業を止める問題は
  blockers.md に日付付きで追記する

## ステップ0: コンテキスト確立

1. `CLAUDE.md`（プロファイル）→ 全体概要 → ロードマップ表を読む
2. ロードマップ表で該当フェーズの状態を特定する:
   - **📝 要求のみ** → ステップ2（設計）へ
   - **🔧 設計済み・未実装** → ステップ3（作業計画）へ
   - **🕐 候補・未着手、または新規要望** → ステップ1（要求仕様）へ
3. 影響しそうな現状設計書と既存コードを確認する
   （広い探索が必要なら file-finder / impact-analyzer に委譲する）

## ステップ1: 要求仕様

1. `Skill('requirements-definition')` で `docs/requirements/P##-<name>.md` を作成する
2. **受け入れ条件は統合テストに翻訳できる粒度** で書く（入力 → 観測結果・
   境界値・失敗経路）。曖昧な点はここでユーザーに確認する
3. ロードマップ表に行を追加し、要求仕様のみでコミットする（接頭辞 `要求:`）

## ステップ2: 設計

1. `Task` で `impact-analyzer` を起動し、影響範囲を調査する
2. `Skill('functional-design')` で `docs/design/proposals/P##-<name>.md` を作成する
   - 「受け入れ条件の充足方針」表で、要求仕様書の全条件に設計要素と
     検証方法（単体 / 統合）を割り当てる
3. 図を検証し、全テスト緑を確認して設計のみでコミットする（接頭辞 `設計:`）

## ステップ3: 作業計画（steering）

1. `Skill('steering')` を **作業計画モード** で実行し、
   `.steering/[日付]-[P##-機能名]/` に requirements.md / design.md /
   tasklist.md を作成する
2. tasklist.md は設計書の「テスト観点」をマイクロコミット単位のタスクに分解し、
   末尾に統合テストのフェーズを置く

## ステップ4: 実装ループ（tasklist.md の完全消化）

**tasklist.md の全タスクが `[x]` になるまで繰り返す。**

1. tasklist.md を読み、先頭の未完了タスクを特定する
2. `Skill('steering')` の **実装モード** に従い TDD で実装する:
   - テストを書く → Red 確認 → 実装 → 全緑確認
   - `Skill('development-guidelines')` の規約（docstring・命名・レイヤー配置）を遵守
   - コンテキスト節約が必要な場合はタスク単位で `tdd-implementer`
     サブエージェントに委譲できる（steering パスとタスク名を渡す）
3. **Red が確保できなかった場合は変異テストで有効性を確認する**
   （`<ツール実行コマンド> .claude/tools/mutate.py --file <実装> --find <正>
   --replace <誤> --expect <テスト名>`。前置コマンドはプロファイルの
   「`.claude/tools/` の Python ツール実行」、テストコマンドが
   `uv run pytest -q` でないなら `--test-command` で渡す）。
   SURVIVED が出たらテストの穴であり、テストを追加してから次へ進む
4. コミットする（1タスク = 1コミット）
5. tasklist.md の該当タスクを `[x]` に更新し、1 に戻る

### 実装ループ内の例外処理

- **タスクが大きすぎる**: サブタスクに分割して tasklist.md を更新し、継続する
- **技術的理由で不要になった**: `- [x] ~~タスク名~~（不要: 理由）` で記録し、継続する
- **冒頭の停止例外1〜3に該当**: ループを止めてユーザーに確認する
- **禁止**: 「後でやる」でのスキップ・未完了タスクを残した終了

### 実装ループ完了時の機械検証

新しい実装を **契約の別実装として** 追加したフェーズでは、実装ループの
完了時に core 無変更を機械確認する:

```
<ツール実行コマンド> .claude/tools/check_unchanged.py --since <フェーズ開始コミット>
```

（`<ツール実行コマンド>` はプロファイルの
「`.claude/tools/` の Python ツール実行」。検査対象は
`.claude/core_files.txt` に列挙しておく）

1 ファイルでも差分があれば、拡張の仕方が家風パターンから外れている。
ステップ5 へ進む前に是正する。

## ステップ5: 実装検証（サブエージェント）

`Task` ツールで `implementation-validator` を起動する:

- prompt: 「P##（機能名）の実装を検証してください。要求仕様書は
  docs/requirements/P##-<name>.md、設計書は docs/design/proposals/P##-<name>.md、
  対象ファイルは [パスリスト]、作業ディレクトリは
  .steering/[日付]-[P##-機能名]/ です。」
- 応答の要約で [必須] があれば該当レポートを読んで修正し
  （修正もマイクロコミット）、再検証する。
  設計との相違が報告されたら **停止例外1としてユーザーに確認する**
- 必要に応じて併走させる: 安全機構に触れた場合は security-checker、
  テストが落ちて原因が読めない場合は test-analyzer

## ステップ6: 統合テスト（サブエージェント）

`Task` ツールで `integration-tester` を起動する:

- prompt: 「P## の受け入れ条件を統合テストで検証してください。要求仕様書は
  docs/requirements/P##-<name>.md、作業ディレクトリは
  .steering/[日付]-[P##-機能名]/ です。」
- 受け入れ条件が満たせない場合、原因に応じて差し戻す:
  - 実装の不備 → ステップ4 へ
  - 設計の不備 → 停止例外1としてユーザーに確認
- 全条件が緑になるまで繰り返す

## ステップ7: 文書反映

`doc-syncer` サブエージェントに一括委譲する
（`Skill('architecture-design')` と同一のチェックリストを持つ）:

1. 設計書冒頭を「✅ 実装済み・反映済み」に更新
2. 要求仕様書の受け入れ条件を統合テスト結果に基づき `[x]` に更新
3. 影響する現状設計書の図・表を更新
4. リファレンス（クラス・関数一覧・テスト件数は実測）を更新
5. マニュアル（`docs/manual.md`）を更新。外から呼べるものが増えていれば
   必須（CLAUDE.md 開発ルール 9）。コード例は実行して出力を照合する
   （Python なら `<ツール実行コマンド> .claude/tools/check_doc_examples.py docs/manual.md`）
6. ロードマップ表を ✅ に更新
7. 変更した図を検証し、全テスト緑を確認して文書反映をコミットする

## ステップ8: 振り返り

`Skill('steering')` の **振り返りモード** で tasklist.md に記録する。
**プロセス改善提案** を必ず書く（`reports/` の知覚・行動ログから、
ツール化の候補・定義の曖昧さ・決定論化の候補・プロファイルの不足を抽出する）。
これがエージェント・スキルを育てる材料になる。

## 完了条件

- tasklist.md の全タスクが完了状態（`[x]` または技術的理由の明記付きスキップ）
- implementation-validator の検証をパス（[必須] 0 件）
- **要求仕様書の受け入れ条件がすべて統合テストで緑**
- 全テストが緑（passed / skipped 数を最終報告に含める）
- 現状設計書・リファレンス・マニュアル・ロードマップ表・
  設計書 ✅・要求仕様書の受け入れ条件 `[x]` が反映済み
- 作業のまとまりごとにコミット済み（未コミットの変更が残っていない）
- 振り返りにプロセス改善提案が記録されている

完了条件を満たすまで、停止例外を除き自律的に問題解決を続けること。
