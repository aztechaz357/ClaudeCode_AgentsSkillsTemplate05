# 厚い経路（例外のスライス 1 本用）

**引数:** スライス番号または機能名（例: `/add-feature S05`、
`/add-feature ユーザー認証`）。

> **既定の開発の入口は `/iterate`** 。このコマンドは厚く書く必要がある
> 少数のスライスだけに使う。判定条件を満たさないなら `/iterate` を案内して終了する。
>
> **違うのは深さだけで、成果物は同じ 7 点セット。**
> 要求仕様書と設計書を網羅的に書き、L1 を飛ばして L2 相当から始める。
> 単体テスト・実装・統合テスト・テスト結果まとめ・マニュアルは
> `/iterate` と同じようにそろえる（`agile-process/deliverables.md`）。

## ステップ-1: 厚い経路が本当に必要か判定する（省略禁止）

`Skill('agile-process')` の「いつ厚く書くか」に照らす。
**次のどれかに当てはまること。**

| 条件 | 厚く書く理由 |
|---|---|
| 不可逆な操作を含む（削除・課金・送信） | 後から直せない |
| 外部に公開する（他人が使う API・CLI） | 契約を変えられなくなる |
| 安全機構に触る（権限・入力検証・秘密情報） | 抜けが事故になる |
| データ形式を決める（保存形式・スキーマ） | 移行コストが後で発生する |
| 3 回作り直しても L1 にならない | 設計不足が原因 |

**どれにも当てはまらない場合はこのコマンドを実行しない。**
`/iterate` を案内して終了する（薄い経路が既定であることを伝える）。

また **骨組みが通っていない場合も実行しない** —— `/skeleton` が先。
厚い設計を骨組みの前に置くと、通った経路が無いまま設計だけが積み上がる。

## 実行方針

原則としてユーザーの介入なしに完了まで進む。停止例外は 3 つ:

1. **設計と実装の矛盾**（勝手にどちらかへ合わせない）
2. **破壊的操作**（ファイル削除・git 履歴改変・凍結文書）
3. **スコープ変更**（指定スライスの範囲を超える実装が必要）

ステップ1（要求仕様）の未確定事項の確認は例外扱いで、AskUserQuestion を使う。
`.steering/local-mode.md` があるときは無停止で実行せず、
`.claude/local-llm/policy.md` に従いステップごとに停止する。

サブエージェントの使い方（レポート駆動）は `.claude/agents/report-protocol.md`
と `.claude/agents/orchestrator.md` を参照する。起動プロンプトには
**steering ディレクトリのパスと目標成熟度** を必ず含める。

## ステップ0: コンテキスト確立

1. `CLAUDE.md`（プロファイル）→ `docs/concept.md` → `docs/backlog.md` を読む
2. 対象スライスの現在の成熟度と、既存のスライス文書を確認する
3. 影響範囲が広いなら `impact-analyzer` に委譲する

## ステップ1: 要求仕様（厚い）

1. `Skill('requirements-definition')` で `docs/requirements/S##-<name>.md` を作る
2. 仕様は **境界値・失敗経路まで網羅** する
   （このスライスは L1 を飛ばして L2 相当から始まる。`maturity.md` の
   「レベルを飛ばしてよい場合」に該当）
3. 曖昧な点は AskUserQuestion で確認する
4. コミットする（接頭辞 `要求:`）

## ステップ2: 設計（厚い）

1. `Skill('functional-design')` で `docs/design/proposals/S##-<name>.md` を作る
   - 「仕様の充足方針」表で全条件に設計要素と検証方法を割り当てる
   - 層の配置は `Skill('layered-architecture')` に従う
     （クリーンアーキテクチャを要求しない。逆流禁止だけを守る）
2. 図を書いたら `.claude/tools/` の図検証ツールで構文検証する
3. 全テスト緑を確認してコミットする（接頭辞 `設計:`）

## ステップ3: 作業計画

`Skill('steering')` の **作業計画モード** で
`.steering/[日付]-[S##-機能名]/` に 3 ファイルを作る。
tasklist.md は設計書の「テスト観点」をマイクロコミット単位に分解する。

## ステップ4: 実装ループ（tasklist.md の完全消化）

全タスクが `[x]` になるまで繰り返す。

1. tasklist.md の先頭の未完了タスクを特定する
2. TDD で実装する（テスト先行 → Red 確認 → 実装 → 全緑）。
   タスク単位で `unit-tester` → `coder` に委譲できる
   （プロンプトに **「目標成熟度 L2。仮実装は不可」** と明記する）
3. Red が確保できなかったタスクは `mutate.py` で有効性を確認する
   （SURVIVED ならテストを足してから進む）
4. コミットする（1 タスク = 1 コミット）
5. tasklist.md を `[x]` に更新して 1 に戻る

例外処理: タスクが大きすぎる → 分割して継続 / 技術的理由で不要になった →
`- [x] ~~タスク名~~（不要: 理由）` で記録して継続 / 停止例外 1〜3 → 確認。
**「後でやる」でのスキップは禁止。**

プロファイルの設計の型に `core 無変更` があり、対象が
`.claude/core_files.txt` に載っている（= L3 到達済み）場合は、
実装ループ完了時に機械確認する:

```
<ツール実行コマンド> .claude/tools/check_unchanged.py --since <開始コミット>
```

## ステップ5: 実装検証

`implementation-validator` を起動する。プロンプトに
**「目標成熟度 L2。`maturity.md` の L2 列で判定」** を明記する。
[必須] があれば直して再検証する。安全機構に触れたなら
`security-checker` を併走させる（このコマンドを使うスライスでは原則併走）。

## ステップ6: 統合テスト

`integration-tester` を起動し、要求仕様書に書かれた仕様を統合テストに
翻訳させる。既存の E2E（骨組み由来）が赤くなっていないことも確認する。
満たせない場合は原因に応じて差し戻す（実装不備 → ステップ4 /
設計不備 → 停止例外 1）。

## ステップ6.5: テスト結果まとめとマニュアル

**厚い経路でも 7 点セットは同じ。** ここを省かない。

1. `test-summarizer` に `docs/test-reports/S##-<name>.md` を書かせる
   （`Skill('test-reporting')`。目標成熟度 L2 なので **未カバーの仕様 0 件** ）
2. `manual-writer` に `docs/manual.md` を更新させる
   （共通 3 節の確認 ＋ `## S##` 節。L2 なので落とし穴の表まで書く）
3. 要求仕様書と要求 HTML のトレース表の 5 列がすべて埋まっていることを
   `build_usdm.py` の終了コード 0 で確認する

## ステップ7: 文書反映

`doc-syncer` に委譲する。プロンプトに **目標成熟度 L2** を明記する
（チェックリスト A のみ実行。現状設計書への統合は L3 の作業で、
L3 に上げる指示があるときだけ含める）。

## ステップ8: バックログの更新と振り返り

1. `docs/backlog.md` の成熟度・次の一手・負債表を更新する
2. `Skill('steering')` の **振り返りモード** で tasklist.md に記録する。
   **プロセス改善提案** を必ず書く（`/improve-process` の材料）
3. 「厚い経路が本当に必要だったか」を 1 行で振り返る
   （不要だったなら、次は薄い経路で足りるという学びを記録する）

## 完了条件

- [ ] tasklist.md の全タスクが完了状態
- [ ] **`check_deliverables.py --slice S##` が 0**（7 点セットがそろっている）
- [ ] **`build_usdm.py` が 0**（トレースが切れていない）
- [ ] implementation-validator の L2 判定をパス（[必須] 0 件）
- [ ] 要求仕様書に書かれた仕様がすべて統合テストで緑
- [ ] 骨組みの E2E を含む全テストが緑（passed / skipped を報告に含める）
- [ ] `docs/backlog.md` の成熟度と負債表が更新済み
- [ ] 未コミットの変更が残っていない
- [ ] 振り返りにプロセス改善提案が記録されている
