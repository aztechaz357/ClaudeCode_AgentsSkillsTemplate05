# プロセス改善（エージェント・スキルを育てる）

**引数（任意）:** 対象範囲（例: `/improve-process P03`、`/improve-process 直近5フェーズ`）。
省略時は `.steering/` 配下の全ディレクトリを対象にする。

`.steering/` に蓄積された **環境・行動・知覚の記録** を分析し、
`.claude/` のエージェント定義・スキル・ツールを改善するコマンドです。

前提となる考え方: エージェントが失敗したり迷ったりしたとき、直すべきは
「その場の指示」ではなく **プロセスの定義** です。同じ状況が次に来たときに
同じ迷いが起きないようにして初めて、育てたことになります。

## ステップ1: 記録の収集（サブエージェントに委譲）

`Task` で `log-analyzer`（または general-purpose）を起動する:

- prompt: 「`.steering/` 配下の [対象範囲] の `reports/*.md` と
  `tasklist.md` の振り返り・`blockers.md`・`decisions.md` を読み、
  次の 4 分類でプロセス上の問題を抽出してください。
  各項目に出典（ファイルパス）と発生回数を添えてください。
  (1) 繰り返された手作業（ツール化の候補）
  (2) エージェントが判断に迷った・手戻りした箇所（定義の曖昧さ）
  (3) LLM の裁量が大きかった箇所（決定論化の候補）
  (4) プロファイルに無くて推測した項目（プロファイル不足）
  レポートは `.steering/[今日の日付]-process-improvement/reports/01-log-analyzer.md`
  に書き出してください。」
- 応答は要約のみ受け取る

## ステップ2: 改善案の優先順位付け

抽出された問題を、次の基準で並べる:

1. **発生回数** が多いもの（2 回以上は必ず対処）
2. **影響範囲** が広いもの（複数エージェントに関わる > 単一エージェント）
3. **決定論化の効果** が大きいもの（LLM の裁量を減らせる量）

上位から順に、改善の種類を決める:

| 問題の分類 | 改善の形 | 対象ファイル |
|---|---|---|
| 繰り返された手作業 | ツールの新設 | `.claude/tools/`（`tool-authoring` のフロー） |
| 定義の曖昧さ | 手順・判断基準の具体化 | `.claude/agents/<name>.md` |
| LLM の裁量が大きい | チェックリスト・テンプレート・機械検証への置換 | スキルの SKILL.md / templates |
| プロファイル不足 | 項目の追加 | `CLAUDE.md` のプロジェクトプロファイル |
| 工程の抜け | フェーズ表・コマンドの手順追加 | `orchestrator.md` / `.claude/commands/` |

## ステップ3: 改善の適用

**1 改善 = 1 コミット** で適用する。各改善について:

1. 対象ファイルを読み、既存の構造・書式に合わせて編集する
2. **手順の正を二重化しない** —— 同じ手順が複数ファイルにある場合は、
   一方を正とし他方はリンクにする（フェーズ表は orchestrator と
   add-feature が同一構成であるべき、等）
3. ツールを新設する場合は `tool-authoring` の作成順序
   （エージェント → スキル → ツール → 検証 → コミット）を守る
4. コミットメッセージに「どの記録（出典）に基づく改善か」を書く

## ステップ4: 報告

ユーザーに報告する:

- 適用した改善の一覧（分類・対象ファイル・出典の記録）
- 見送った改善とその理由（発生 1 回のみで様子見、等）
- 次に同じ問題が起きたら作るべきもの（候補として `tool-authoring` の
  「候補」節に記録済みであること）

## 注意

- **記録に無い問題を推測で直さない** 。改善は必ず実際の記録を出典とする
- 定義を長くすることが改善ではない。曖昧さを消して **短く具体的に** する
  （エージェント定義が肥大化すると、それ自体がコンテキストを圧迫する）
- プロジェクト固有の学びは `CLAUDE.md` のプロファイルへ、
  プロセス一般の学びは `.claude/` のテンプレートへ振り分ける
