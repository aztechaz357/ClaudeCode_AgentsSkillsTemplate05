# 記録の点検

記録間の整合と、実装との同期漏れを検出して報告する。
**点検と報告まで** で、修正はユーザーの指示を受けてから行う。

対象文書のパスは `CLAUDE.md` の **プロジェクトプロファイル** の
「ドキュメント構成」表を正とする。判定基準は
`.claude/skills/agile-process/maturity.md` の段階別 DoD。

**成熟度に応じて点検する** 。L1 のスライスに現状設計書が無いのは正常であり、
問題として報告しない。一方 **7 点セットは L1 でもそろっている必要がある** 。

## 0. 機械検証を先に回す（目視で数えない）

点検はこの 3 本から始める。終了コードが判定であり、意見ではない。

```
<ツール実行コマンド> .claude/tools/check_deliverables.py
<ツール実行コマンド> .claude/tools/build_usdm.py --check
<ツール実行コマンド> .claude/tools/build_structure.py --check
```

| ツール | 1 が返ったときの意味 |
|---|---|
| `check_deliverables.py` | 7 点セットのどれかが欠けている（出力に欠落の一覧）。 **[必須]** |
| `build_usdm.py --check` | USDM 違反、トレースの切れ、または要求一覧が古い。 **[必須]** |
| `build_structure.py --check` | `docs/structure.md` が実物と食い違っている。再生成を提案する |

以降の目視の点検は、 **機械で見られないところだけ** を見る。

## 点検対象と観点

### 1. 文書の存在（成熟度別）

7 点セットの存在は上の `check_deliverables.py` が見る。ここで見るのは
それ以外の文書。

| 文書 | いつ必須か | 無いときの扱い |
|---|---|---|
| `docs/concept.md` | 常に（一行 + 完走の定義） | 重大問題 |
| `docs/backlog.md` | 常に | 重大問題 |
| `docs/design.md` | L3 のスライスがある場合 | L3 があれば重大問題。無ければ **正常** |
| `docs/decisions/ADR-*.md` | スライスを越える判断があった場合 | 設計書に大きな判断が埋もれていれば ADR 化を提案 |
| `docs/reference.md` | 任意 | 作成提案（急がない） |
| `docs/structure.md` | 常に（生成物） | 無ければ `build_structure.py` の実行を提案 |
| `docs/requirements/` `docs/design/proposals/` | 厚い経路のスライスがある場合 | 該当が無ければ **正常**（空でよい） |

**空のファイルが置かれている場合はそれ自体が問題** として報告する
（「先に作らない」方針に反する）。ただし 7 点セットは「先に作らない」の
対象外 —— 着手したスライスでは全部そろっているのが正常。

### 2. バックログと実物の整合（最重要）

バックログは進捗の正なので、実物と食い違っていれば **実物を正として**
バックログの修正を提案する。

- スライス表の成熟度が、スライス文書冒頭の「成熟度」と一致しているか
- スライス表に載っているスライスの文書が実在するか（リンク切れ検出）
- 「いま着手中」が **1 本以下** か（WIP = 1 の違反検出）
- 「骨組み」が `通った` なのに E2E テストが存在しないことはないか
- 負債表の `済` になっている行が、実際にコミットで返されているか
  （コミットハッシュを `git show` で確認する）
- 負債表の未返却件数（痛み 高 が 3 件以上あれば `/refactor` を提案する）

### 3. 成熟度ごとの完了条件の充足

各スライスについて、 **記載されている成熟度の条件を満たしているか** を見る
（上のレベルの条件で判定しない）。

- **L1 と書かれているのに** E2E が無い / 実績に実行出力が貼られていない
  / 残した手抜きが記録されていない / 設計書に判断の記録が無い → 重大問題
- **L2 と書かれているのに** 仕様に `□` が残っている /
  失敗経路のテストが無い / 仮実装が残っている（`TODO` / `FIXME` を Grep）
  / 外部 I/O が契約を経ずに呼ばれている → 重大問題
- **L3 と書かれているのに** アーキテクチャテストが赤い / `docs/design.md`
  に反映されていない / 該当スライスの負債が残っている → 重大問題

### 3.2 成果物の中身（存在だけでは足りないもの）

`check_deliverables.py` は存在と形を見るが、中身の質は見ない。ここを読む。

- 設計書の「判断の記録」が **結論だけ** になっていないか
  （他の選択肢とメリデメが書かれているか）
- テスト結果まとめの数字が、実際のテスト出力と一致するか
  （疑わしければテストを実行して突き合わせる）
- マニュアルの共通 3 節のコマンドが **実際に動くか**（抜き取りで実行する）
- マニュアルの実行例の出力が実物と一致するか
  （Python なら `check_doc_examples.py docs/manual.md`）

### 3.5 USDM の記法（機械検証）

次を実行し、終了コードで判定する（目視で代用しない）:

```
<ツール実行コマンド> .claude/tools/build_usdm.py --check
```

| 終了コード | 扱い |
|---|---|
| 0 | 記法 OK かつ要求一覧が最新 |
| 1 | USDM 違反（理由の欠落・番号の不整合等）または STALE。 **[必須]** |
| 2 | 対象の要求 HTML が 0 件。骨組み前なら正常、それ以外は [必須] |

あわせて、スライス文書の「要求」節が **リンクだけ** になっているかを見る。
要求の本文が両方に書かれていたら二重管理なので [必須] として報告する。

### 4. トレーサビリティ

背骨は **要求 →（理由）→ 仕様 → E2E テスト** の 1 本。

- 仕様（`☑` のもの）に対応する E2E テストが実在するか
- 骨組みの E2E が今も存在し、緑か（実際にテストを実行して確認する）
- 厚い経路のスライスでは、要求仕様書に書かれた仕様が設計書の
  「仕様の充足方針」表に 1 条も落ちずに現れているか

### 5. 同期漏れの兆候

- L3 のスライスでソースを変更したのに `docs/design.md` が
  変更されていないものがないか（`git log --stat` で確認）
- `docs/reference.md` のテスト件数と実測（プロファイルの「テスト件数の
  数え方」）が一致しているか（実際にコマンドを実行して確認する。手計算しない）
- `.claude/skills/repository-structure/template.md` のスナップショットが
  実ディレクトリと食い違っていないか
- プロファイルに記載のコマンドが実際に動くか（抜き取りで実行。
  特に「動作確認」コマンド）

## 報告形式

```markdown
# 記録の点検結果（YYYY-MM-DD）

## 現在地
- 成熟度: L1 {n} 本 / L2 {n} 本 / L3 {n} 本 / L0 {n} 本
- 負債: {n} 件（痛み高 {n} 件）
- 骨組みの E2E: ✅/❌

## 問題なし
- （確認できた項目）

## 要対応
1. [必須] …（不整合の内容と修正案）
2. [推奨] …

## バックログと実物の食い違い
- S##: バックログ `L2 固い` / 実物 {仮実装が残存} → バックログを L1 に戻す提案

## トレーサビリティの欠落
- S##: {仕様} → {対応する E2E が無い}

## 提案
- （`/refactor` の実行提案・未作成文書の作成提案 等）
```

## 注意

- **成熟度より上の基準で問題を作らない** 。L1 のスライスに docstring が
  無い・層が分かれていないのは正常（報告しない）
- 大量の詳細レビューが必要な場合は、文書ごとに `/review-docs` の実行を提案する
- 点検で見つかった構造的な問題（同じ抜けが繰り返し起きる等）は、
  `/improve-process` でプロセス側の改善につなげる
