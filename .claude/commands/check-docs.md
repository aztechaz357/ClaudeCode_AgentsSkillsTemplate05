# プロジェクト文書の点検

文書間の整合と、実装との同期漏れを検出して報告する。
**点検と報告まで** で、修正はユーザーの指示を受けてから行う。

対象文書のパスは `CLAUDE.md` の **プロジェクトプロファイル** の
「ドキュメント構成」表を正とする。

## 点検対象と観点

### 1. 文書の存在と役割

プロファイルの「ドキュメント構成」表に挙がっている文書が実在するか。
無いものは、必須（要求仕様書・設計書・ロードマップ表）なら重大問題として、
任意（用語集等）なら作成提案として報告する。

### 2. 整合チェック

- ロードマップ表のステータス（📝/🔧/✅）と、要求仕様書・設計書の冒頭
  ステータスが一致しているか
- リファレンスのテスト件数と実測（プロファイルの「テスト件数の数え方」）が
  一致しているか（実際にコマンドを実行して確認する。手計算しない）
- 全体概要の文書マップとリンク先が実在するか（リンク切れ検出）
- 現状設計書に記載のクラスがソースに実在するか（抜き取りで数クラス）

### 3. トレーサビリティ（工程間の追跡）

決定論的なプロセスの生命線。フェーズごとに次を確認する:

- 要求仕様書の受け入れ条件が、設計書の「受け入れ条件の充足方針」表に
  **1 条も落ちずに** 現れているか
- 統合テストに割り当てられた条件に、対応する統合テストが実在するか
- ✅ 済みフェーズで、受け入れ条件のチェックボックスが `[x]` になっているか

### 4. 同期漏れの兆候

- 直近のコミットでソースを変更したのに現状設計書・リファレンスが
  変更されていないものがないか（`git log --stat` で確認）
- `.claude/skills/repository-structure/template.md` のスナップショットが
  実ディレクトリと食い違っていないか
- プロファイルに記載のコマンドが実際に動くか（抜き取りで実行）

## 報告形式

```markdown
# 文書点検結果（YYYY-MM-DD）

## 問題なし
- （確認できた項目）

## 要対応
1. [必須] …（不整合の内容と修正案）
2. [推奨] …

## トレーサビリティの欠落
- P##: {受け入れ条件} → {設計 or 統合テストに対応なし}

## 提案
- （未作成文書の作成提案 等）
```

## 注意

- 大量の詳細レビューが必要な場合は、文書ごとに `/review-docs` の実行を提案する
- 点検で見つかった構造的な問題（同じ抜けが繰り返し起きる等）は、
  `/improve-process` でプロセス側の改善につなげる
