# ツールをサクッと作る

引数: 作りたいものの説明（例: `/tool 2つの CSV の差分を行単位で出したい`）

工房レーン（`workshop/tools/`）にツールを 1 本追加する。
本開発レーンの工程（要求仕様書・設計書・作業計画・統合テスト・文書同期）は
**通らない** 。ただし **テスト先行は省かない** 。

## ステップ1: 範囲を 1 行に絞る

引数から `summary`（1 行）と `name`（小文字ケバブケース）を作る。

- 1 行に収まらない場合はユーザーに「今まさに困っている 1 つの用途」を聞く
- **1 行に絞れない依頼は工房レーンの案件ではない** 。本開発レーン
  （`/add-feature`）を提案して確認を取る

`-Lang` はプロファイルの主言語から決める（既定 `py`）。

## ステップ2: 重複を確認する

```
powershell -File .claude/tools/index_workshop.ps1 -Check
```

`workshop/CATALOG.md` を読む。同じことをするツールがあれば
**新設せずに既存へ引数を足す** ことを提案し、ユーザーの確認を取る。

（`workshop/` がまだ無ければ、この確認は飛ばしてよい）

## ステップ3: tool-smith サブエージェント起動

Task ツールで tool-smith サブエージェントを起動する:

- subagent_type: "tool-smith"（未登録の環境では general-purpose を使い、
  最初に `.claude/agents/tool-smith.md` と
  `.claude/skills/quick-tool/SKILL.md` を読むよう指示する）
- description: "Build a workshop tool"
- prompt: "`workshop/tools/<name>/` にツールを 1 本作ってください。
  summary: <1行>。言語: <lang>。用途の詳細: <ユーザーの説明>。
  `.claude/skills/quick-tool/SKILL.md` の 8 手順に従い、
  テストを先に書いて Red を確認してから実装し、README の実行例は
  実際に動かした出力を貼り、`index_workshop.ps1` で登録してコミットまで
  行ってください。止まる条件に当たったら実装せずに報告してください。"

## ステップ4: 結果の確認と報告

1. サブエージェントの応答（作成パス・テスト結果・実行例・コミット）を確認する
2. `workshop/CATALOG.md` に行が増えたことを確認する
3. ユーザーには次を報告する:
   - ツールのパスと `summary`
   - **実際の実行例とその出力**（コピーして使える形で）
   - テスト件数
   - 次に足せそうなオプション（あれば 1〜2 個。無ければ書かない）

## 止まったときの対応

tool-smith が「止まる条件」で戻ってきた場合、勝手に進めない。

| 報告内容 | 対応 |
|---|---|
| 範囲が広すぎる | 用途を 1 つに絞るか、`/add-feature` に回すかをユーザーに確認 |
| 昇格の判断に該当 | `/promote` を案内する |
| 依存追加が必要 | プロファイルの依存方針に照らし、ユーザーの判断を仰ぐ |
| Red を作れない | テストが何も検証していない。仕様の確認をユーザーに求める |
| 既存ツールと重複 | 既存を拡張してよいかユーザーに確認 |

## 注意事項

- このコマンドは `.claude/tools/` には追加しない。開発プロセス自体を
  機械化する道具は `tool-authoring` スキルの領分（判断基準が違う）
- ツールが育って 1 ディレクトリに収まらなくなったら `/promote` で
  本開発レーンへ上げる
