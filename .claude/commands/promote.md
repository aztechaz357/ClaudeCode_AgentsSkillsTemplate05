# 工房から本開発レーンへ昇格させる

引数: ツール名とフェーズ番号（例: `/promote csv-diff P07`）

工房レーン（`workshop/tools/<name>/`）で育ったツールを、
本開発レーン（要求仕様書 → 設計書 → TDD → 統合テスト → 文書同期）へ移す。

**このコマンドは昇格の判断と入力の準備までを行う。**
実装そのものは `/add-feature P##` が引き受ける。

## ステップ1: 昇格が妥当か検証する

`workshop` スキルの「昇格の判断」に照らす。次のどれかに当てはまること。

| 該当条件 | 本開発レーンで得られるもの |
|---|---|
| 他のツールから使いたくなった | 契約（インタフェース）と依存の逆転 |
| 1 ファイルに収まらなくなった | 層への分割 |
| 自分以外が使う | 受け入れ条件と統合テスト |
| 壊れると困る | アーキテクチャテストと回帰テスト |
| 設定・状態を持ち始めた | infrastructure への隔離 |

**どれにも当てはまらない場合は昇格させない。** その旨をユーザーに伝え、
工房に置いたままにすることを提案する（全部を上げると工房の速度が死ぬ）。

また、対象が **開発プロセス自体を機械化する道具** （検証・生成スクリプト）
だった場合は、本開発レーンではなく `.claude/tools/` が行き先。
`tool-authoring` スキルを案内して終了する。

## ステップ2: 現状を棚卸しする

対象ツールの `README.md`・実装・テストを読み、次を書き出す:

- 現在できること（実行例と実出力。README に貼ってあるもの）
- 現在できないこと（README の「既知の制限」）
- 踏んだ落とし穴（README の「落とし穴」表）
- 既存テストのケース一覧

**これが要求仕様書の材料になる。** 工房で貯めた実運用の知見が
そのまま受け入れ条件と境界値になるので、捨てない。

## ステップ3: 要求仕様書の入力を作る

`requirements-definition` スキルに渡す形で、ステップ2 を整理する。

- 「落とし穴」表の各行 → **失敗経路の受け入れ条件**
- 「既知の制限」 → **非目標** または次フェーズ送り
- README の実行例 → **正常系の受け入れ条件**（入力 → 観測結果の形に直す）
- 既存テストのケース → 統合テストへ翻訳する候補

ここまでをユーザーに示し、フェーズの範囲について確認を取る。

## ステップ4: 工房側に昇格の跡を残す

**工房のディレクトリは削除しない。** 次の 2 点だけ変更する。

1. `README.md` の front matter を `status: promoted` にし、`updated` を今日に
2. `README.md` の本文先頭に、昇格先（`docs/requirements/P##-*.md` と
   本実装のパス）へのリンクを 1 行足す

```
powershell -File .claude/tools/index_workshop.ps1
```

跡を残すのは、半年後に「これはどこへ行ったのか」を辿れるようにするため。

## ステップ5: 本開発レーンへ引き渡す

`/add-feature P##` を案内する（ユーザーの指示があればそのまま起動する）。
ステップ3 で作った材料を、要求仕様書の入力として渡す。

昇格したツールの実装コードは **そのまま移植しない** 。
本開発レーンは要求仕様書 → 設計書 → TDD の順で進むため、
工房の実装は「動く参照実装」として設計時に読む位置づけになる。

## ステップ6: コミット

```
docs: <name> を P## へ昇格（工房 → 本開発レーン）

- workshop/tools/<name>/README.md を status: promoted に更新し昇格先へのリンクを追加
- 昇格の根拠: <該当した条件>
- 要求仕様書の材料（実行例・落とし穴・既知の制限）を P## の入力として整理
- CATALOG.md を再生成
```
