# 設計書 作成ガイド

テンプレート（./template.md）の各セクションをどう書くかの実践指針。

## 図面先行の原則

コードを書く前に、設計書で構造とやり取りを図面化する。
実装中に設計判断が変わったら **設計書を先に直してから** コードを書く。

## 各セクションの書き方

### 目的

- 要求仕様書の「ユーザー価値」を実装可能な言葉に落とす。
  要求仕様書を書き写すのではなく、設計の狙いを述べる
- 出典（要求仕様書の該当節）を明記して追跡可能にする

### 仕様の充足方針

- **要求仕様書に書かれた仕様を 1 行も落とさず表に並べる** 。ここで
  「この条件を満たす設計要素が無い」ことに気づくのが、設計工程の主目的の1つ
- 検証方法の欄で単体 / 統合を割り振る。統合に割り振った条件は
  後の integration-tester がそのままテストにする

### 位置づけ（レイヤー配置）

- 追加・変更のすべてを層に割り付けた表にする。ここで依存ルール違反が
  見えるようにする（例: presentation が infrastructure を知る配置は違反）
- 迷ったら repository-structure スキルの配置判定を使う

### 新規契約とクラス

- 契約（インタフェース）はシグネチャまで書く。メソッド名・引数名は実装で
  そのまま使う想定の精度にする（実装時に考えさせない）
- 図は1〜2枚に絞る。構造ならクラス図、時系列の協調ならシーケンス図
- Mermaid の英語識別子には日本語の意味を note か表で併記する
- 図を書いたら必ず `.claude/tools/` の図検証ツールで構文検証する

### 既存変更点（最小限）

- 変更するものより先に「変更しないもの」を確認する。設計の型は
  **core 無変更**（中核クラス・既存デコレータ）。観測・状態の追加は
  「domain 契約 + infrastructure 実装 + 注入」で行う
- 既存クラスへの引数追加はデフォルト値付き（未注入なら従来どおり）の
  後方互換パターンを基本とする

### テスト観点

- **TDD の起点になる最重要セクション** 。実装はここをテストコードに
  翻訳するところから始まる
- 「何を入れたら何が返るか」まで具体化する（「正しく動くこと」は書かない）
- 必ず含める: 失敗経路（フェイルソフト / フェイルクローズの確認）、
  未注入・未設定時の後方互換、冪等性、境界値
- 外部依存はフェイクで検証できる設計になっているかをここで確かめる

### 設計上の決定と却下案

- 「なぜこの形か」だけでなく「なぜ他の形にしなかったか」を残す。
  後から見た人（未来の自分）が同じ検討を繰り返さないため
- 却下理由は具体的に（例: 「共通メソッドへの引数追加は全デコレータに
  転送修正が波及し、転送し忘れると黙って値が落ちる」）

### 既知の制限

- v1 で意図的に許容する制限を隠さず書く。「問題が出たらどう解決するか」の
  方向まで添える
- スコープ外（やらないこと）と混同しない。制限 = 入るが不完全、
  スコープ外 = 入らない

## 分割の目安

- 1 設計書 = 入口から出口まで通る 1 スライス。大きすぎるなら
  S##-1 / S##-2 ではなく別番号のスライスに分ける
- 分割の結果、厚い経路が不要な部分が出たら **そこは薄い 1 枚へ回す**
