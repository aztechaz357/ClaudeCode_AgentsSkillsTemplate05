# 実装前設計（設計書）作成スキル（厚い経路のみ）

> **⚠️ このスキルは既定の経路ではありません。**
> 通常のスライスの設計は `slice-definition` スキルの **「薄い設計」5 行**
> （触るファイル・入口の関数名・流れ・層・仮実装）で足ります。
> 図もクラス図もシーケンス図も書きません。
>
> 厚い設計書を書くのは、対応する要求仕様書
> （`docs/requirements/S##-*.md`）が存在するスライスだけです。
> 判定条件は `agile-process` スキルの「いつ厚く書くか」が正
> （不可逆・外部公開・安全機構・データ形式・3 回失敗）。
>
> 要求仕様書が無いのにこのスキルを使おうとしているなら、
> **`slice-definition` へ戻ってください。**

厚い経路の第 2 工程です（要求仕様書 → **設計書** → TDD 実装 → 統合テスト）。
設計書の役割は **実装フェーズで LLM に考えさせる量を減らすこと** です。
レイヤー配置・シグネチャ・テスト観点まで確定していれば、実装は
「設計書をコードに翻訳する」決定論的な作業に近づきます。

## 前提条件

設計書の作成を開始する前に、以下を読むこと:

1. `CLAUDE.md`（プロジェクトプロファイル含む）- 開発規約・層構成・家風パターン
2. **該当スライスの要求仕様書**（`docs/requirements/S##-<name>.md`）- 設計の入力
3. `.claude/skills/layered-architecture/SKILL.md` - 層の配置と依存ルール
4. `docs/design.md`（現状設計。あれば）- 既存構造との整合
5. `docs/backlog.md` - S## の採番元と依存関係

## 層の扱い（クリーンアーキテクチャを要求しない）

配置は **レイヤードアーキテクチャ** に従う（`layered-architecture` が正）。
守るのは **逆流禁止・循環禁止の 1 ルールだけ** 。

- `application` から `infrastructure` を **直接呼んでよい**
  （契約を切って注入する必要はない）
- 契約（インタフェース）を作るのは、`layered-architecture` の
  「クリーンアーキテクチャへ育てる」の症状表に該当したときだけ。
  **症状が出ていないのに先に契約を切らない**（先回りの抽象化）
- `domain` が標準ライブラリのみに依存することは常に守る

## 出力先と採番

```
docs/design/proposals/S##-<name>.md   （1 スライス 1 ファイル）
```

- S## は対応する要求仕様書と同じ番号を使う
- 作成と同時に `docs/backlog.md` の該当行の文書列へリンクを張る
- 実装完了時は設計書冒頭を「✅ 実装済み・反映済み」に更新する
  （doc-syncer のチェックリスト B。L3 に上げるときだけ）

## テンプレートとガイド

- テンプレート: ./template.md
- 詳細ガイド（各セクションの書き方・良い例）: ./guide.md

## 品質チェック（作成後）

- [ ] **対応する要求仕様書が存在するか**（無ければ薄い経路へ戻る）
- [ ] 構成が揃っているか（目的 / 位置づけ / 契約・クラス / 既存変更点 /
      テスト観点 / 決定と却下案 / 既知の制限）
- [ ] **要求仕様書の受け入れ条件がすべて設計でカバーされているか**
      （条件 → 設計要素の対応が追えるか）
- [ ] 層の配置が逆流していないか（`layered-architecture` の 1 ルール）
- [ ] **症状が出ていないのに契約・プラグイン機構・設定機構を入れていないか**
- [ ] テスト観点がテストコードに翻訳できる具体性か
- [ ] 図を構文検証したか（`.claude/tools/` の図検証ツール）
- [ ] `**強調**` の前後に半角スペースがあるか
- [ ] `docs/backlog.md` の文書リンクを更新したか
