# マニュアル（取扱説明書）の規約

**動く機能を追加したら、必ずマニュアル（`docs/manual.md`）を更新する。**
「使い方が分からない機能」は存在しないのと同じ。

## 必須であって任意ではない

- フェーズで **ユーザーが呼び出せるもの** （エントリポイント・
  Composition Root の配線関数・CLI）を追加したら、マニュアルの更新は
  **完了条件に含まれる** 。「今回は内部実装だけ」と判断してよいのは、
  外から呼べるものが何も増えていないときだけ
- マニュアルは **フェーズの最後に思い出して書くものではない** 。
  実装が動いた時点で書き、実際に動かしながら書く

## 最低限入れる内容

1. **準備** —— 依存のインストールと動作確認のコマンド
2. **最小の実行例** —— コピーして貼れば動く最短のコード
3. **引数の意味** —— 単位付きの表。物理量は単位を必ず書く
4. **結果の読み方** —— 戻り値の構造と、使う前に確認すべきこと
5. **落とし穴** —— 間違えやすい点を「症状 → 原因 → 対処」の表で。
   実際に踏んだものを残す
6. **既知の制限** —— できないことを明記する（設計書の「既知の制限」と揃える）

## コード例は実行して出力を確認する

**出力を推測で書かない。** 実際に実行し、得られた出力をそのまま貼る。

Python プロジェクトでは、コード例を ` ```python ` 、その出力を直後の
言語指定なし ` ``` ` に書くと検証ツールが自動で照合する。

```
<プロファイルの「.claude/tools/ の Python ツール実行」コマンド> .claude/tools/check_doc_examples.py docs/manual.md
```

このツールは ` ```python ` ブロックを実際に実行し、直後の出力ブロックと
照合する。 **マニュアルを更新したら必ず実行する。**
出力に `N compared` が表示されるので、 **照合された数が例の数と一致して
いることを確認する** （一致しないなら書式がずれていて、実行しただけで
照合されていない）。

Python 以外の言語のプロジェクトでは、同等の照合手段を用意するまで
**コード例を手で実行し、その出力を貼る** （推測で書かないことは同じ）。

> 実例: このツールを導入した時点で、既に書いてあった手書きの期待出力
> 2 箇所が実際の出力と食い違っていた。人間もエージェントも出力を
> 正確には覚えていない。

## 工房レーンでの簡易版

工房のツール（`workshop/tools/<name>/README.md`）では、上の 6 項目のうち
**1・2・3・5 の 4 つ** を最低限とする（`quick-tool` スキルのテンプレートが
この形になっている）。

- 実行例の出力は **実際に動かして貼る** —— これは工房でも必須。
  推測で書いた出力は嘘になる
- 「4. 結果の読み方」「6. 既知の制限」は、書けるなら書く。
  `/promote` で本開発レーンへ昇格させるときに必須へ引き上げる
