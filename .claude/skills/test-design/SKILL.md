# テスト設計スキル（test-design）

テストは **書き方より「何を守るか」で決まる** 。
このスキルは、テストコードを書く前に観点を選び、
**選ばなかった観点も理由ごと残す** ための手順です。

`option-first` の適用例の 1 つ（判断点＝どこまで守るか）。
選択肢の作り方の正は `Skill('option-first')`、ここでは **カタログと選び方**
だけを持ちます。

## なぜ先に選ぶのか

- 観点を決めずに書くと、 **書きやすいテストだけ** が増える
  （正常系の重複が並び、失敗経路は 1 つも無い、という形になりやすい）
- 後から「なぜこの観点は無いのか」を問われても答えられない
- 人が選ぶ経験を積める唯一の工程。実装の選択より学習効果が高い
  （テストは「何が起きたら困るか」の一覧であり、仕様理解そのもの）

## 観点カタログ（ここから選ぶ）

| 観点 | 何を守るか | 向く場面 | 目安の本数 |
|---|---|---|---|
| **代表値** | 期待どおり動くこと | すべて（L1 の既定） | 1〜2 |
| **同値分割** | 入力の種類ごとの振る舞い | 入力に種類がある | 種類の数 |
| **境界値** | 境目での取り違え（`<` と `<=`） | 数値・件数・日付の範囲 | 境界 × 2 |
| **失敗経路** | 想定内の失敗の扱い | ファイル・通信・外部入力 | 失敗の種類 |
| **状態遷移** | 順序に依存する壊れ方 | 状態を持つ・手順がある | 遷移の数 |
| **不変条件** | いつでも成り立つ性質 | 集計・変換・整合性 | 1〜3 |
| **性質ベース** | 網羅では見つからない反例 | 変換の往復・並べ替え | 1 |
| **回帰** | 直したバグが戻らないこと | バグ修正のたび | 1 / 件 |

**「網羅率」は観点ではない。** 何 % 通ったかは、何を守ったかを語らない。

## 成熟度でどこまで採るか

| 目標 | 既定で採る | 選択肢として聞く（`既定` モード） | 採らない |
|---|---|---|---|
| L0 → L1 | 代表値のみ | **1 回だけ**（追加で 1 観点採るか） | 境界値・状態遷移・性質ベース |
| L1 → L2 | 代表値・同値分割・境界値・失敗経路 | 最大 2 回（状態遷移 / 不変条件） | 性質ベース |
| L2 → L3 | 上記すべて ＋ 回帰 | 聞かない | —— |

**関与モードが `伴走` なら、成熟度にかかわらず必ず 1 回聞く**
（`CLAUDE.md` の「関与モード」節。L2 → L3 でも聞く）。
`任せる` なら 0 回で、既定の観点だけ採る。
**「何を守らないと決めたか」は、テストの書き方より学びが大きい** ——
`伴走` でここを飛ばすと、テストが「AI が勝手に決めた網」のままになる。

**L1 で境界値を網羅するのは越権**（絶対ルール 9）。
L1 の目的は「端から端まで通ること」であって「壊れないこと」ではない。

## 聞き方（`option-first` の形に従う）

```markdown
**判断点**: S03 のフィルタで、代表値のほかに 1 観点だけ足すなら？

1. **失敗経路（推奨）** —— 列名が存在しないときの振る舞いを 1 本
   - 選ぶと: 実データで最初に踏む失敗を、L1 のうちに潰せる
   - 選ばないと: 列名の打ち間違いで例外がそのまま出る（L2 まで残る）
2. **境界値** —— 0 件・1 件・全件一致の 3 本
   - 選ぶと: 件数まわりの取り違えが出なくなる
   - 選ばないと: 空入力で落ちる可能性が残る（負債に記録して L2 で返す）
3. **足さない** —— 代表値 1 本で次へ進む
   - 選ぶと: 反復が最短で終わる
   - 選ばないと（＝足すと）: 実装が 30 分ほど伸びる

**推奨の理由**: 実データが外部ファイルなので、最初に踏むのは失敗経路
```

- 各案に **「選ばないとどうなるか」** を必ず書く（無い提示は差し戻し）
- 「足さない」を必ず選択肢に含める —— 増やす方向だけの提示は誘導になる
- 応答が無ければ **推奨で進む** 。待ち続けない

## 採らなかった観点の扱い（負債にしない）

**選ばれなかった観点は「負債」ではなく「意図的な非目標」** 。
両者を混ぜると負債表が「やっていないこと」で埋まり、機能しなくなる。

| 種類 | 書く場所 | 例 |
|---|---|---|
| 意図的な非目標（今回は採らないと決めた観点） | 設計書の「判断の記録」 | 「境界値は L2 で採る。L1 の目的は完走」 |
| 負債（採るべきだったが手を抜いた） | `docs/backlog.md` の負債表 | 「失敗時に例外が漏れる。痛み 中」 |

判定基準は **「次の成熟度で必ず採るか」** 。採るなら非目標、
採る予定が無いのに穴が残っているなら負債。

## 成果物: テスト仕様書（8 点セットの #3）

観点を選んだら、その場で **テスト仕様書 1 枚** に落とす。

```
docs/test-specs/S##-<name>.md      （雛形: ./template.md）
```

これは **走らせる前に書く「何を確かめるか」の一覧** であり、
テスト結果まとめ（#7）とは別物。実行結果・件数・ログを **ここに書かない** 。

中身は 2 つだけ。

1. **採った観点と、採らなかった観点**（上のカタログから。理由つき）
2. **入出力の例**（`N##` = 正常系 ／ `E##` = 異常系）——
   そのままテストコードに写せる粒度の実際の値

書式と ID の規約の正は `agile-process/deliverables.md` の
**「入出力と例（正常系・異常系）」** 節。要求仕様書・設計書と
**同じ ID が同じケースを指す** ので、`N1`・`E1` は必ず含める
（要求・設計に 2 行しかないものを、ここで観点ごとに増やしていく）。

| 目標 | 例の行数 |
|---|---|
| L1 | **3〜6 行** （`N1`・`E1` ＋ 追加した観点の分だけ） |
| L2 | 採った観点ごとに網羅（境界値なら境界 × 2、失敗経路なら失敗の種類ごと） |
| L3 | ＋回帰の例（直したバグ 1 件につき 1 行） |

### 記録の行き先（テスト仕様書に書かないもの）

- 選んだ観点と却下した観点の **判断の経緯** → **設計書の「判断の記録」**
  （テスト仕様書には結論だけ 1 行書き、経緯は設計書側に置く）
- 観点 → **テスト名** の対応 → **テスト結果まとめ**（`test-reporting` の対応表）
- 新しいファイルを `docs/test-design/` に作らない ——
  成果物の種類は 8 点で固定（`agile-process/deliverables.md`）

## やってはいけないこと

- 観点を選ばずにテストを書き始める（書きやすいものだけが増える）
- L1 で全観点を採る（目標成熟度を超える作業。絶対ルール 9）
- 選択肢に「足さない」を入れない（増やす方向の誘導になる）
- 採らなかった観点を負債表に書く（負債表が「やっていないこと」で埋まる）
- 観点だけ決めてテストを書かない（決めた観点は必ず 1 本以上のテストになる）
- テストコードをこのスキルの中で書く（それは `unit-tester` の仕事）
- **テスト仕様書に実行結果・件数・ログを書く**（走らせる前の文書。
  結果はテスト結果まとめ #7 の領分）
- **テストコードを書いてからテスト仕様書を埋める**（順序が逆になると
  仕様書が目録になり、書き忘れた観点は仕様書にも載らない）
- **異常系（`E##`）を 1 行も書かないまま次へ渡す**（異常時の振る舞いを
  実装者がその場で決めることになる）
