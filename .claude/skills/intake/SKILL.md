# 記入用ワークシート（intake）

**「何を作るか」と「なぜ要るか」はユーザーの中にしかない。**
`AskUserQuestion` は速いが、選択肢からしか拾えない。理由・非目標・懸念は
本来もっと長く、もっとその人の言葉であるはずのもので、
**選択肢に丸めた時点で失われる** 。

このスキルは、その失われる分を **エディタで書いてもらう** ための器を定める。

## 何が変わるか

| | CLI（`AskUserQuestion`） | ワークシート |
|---|---|---|
| 書ける量 | 1 行 | 制限なし（改行・箇条書き・コード片） |
| 書ける形 | 選択肢から選ぶ | **選択肢 ＋ 自由記述** |
| 書く時間 | その場で即答 | 中断・再開できる |
| 向くもの | 粒度・方式の二者択一 | **理由・非目標・懸念・具体例** |
| 向かないもの | 長い理由 | すぐ決まる択一（往復が無駄） |

**どちらも使う。** 骨格（粒度・方式）は CLI で即決し、
肉付け（理由・非目標・入出力の例）はワークシートで書いてもらう。

## 置き場所と命名

```text
.steering/[YYYYMMDD]-[S##-機能名]/intake/
     ├── S##-要求.md     # 段1 用（雛形: ./template-requirement.md）
     └── S##-設計.md     # 段2 用（雛形: ./template-design.md）
```

- `.steering/` 配下なので **gitignore 対象** 。成果物は増えない
  （8 点セットは 8 点のまま）
- **ワークシートは入力であって、成果物の写しではない** 。
  `steering` スキルが禁じている「要求・設計を写した中間ファイル」とは
  向きが逆 —— 正式文書が **まだ無い** 段階で、その材料を集める器

## 流れ（4 手）

```
1 作る      Claude がワークシートを生成し、パスを出して待つ
2 書く      ユーザーがエディタで埋める（全部でなくてよい）
3 回収      ユーザーが /intake と打つ → Claude が読む
4 深掘り    空欄・矛盾・抽象語を指摘して詰め、正式文書へ落とす
```

- **`/intake` が打たれるまで読みに行かない。** 書きかけを読んで
  的外れな指摘を出すと、書く気が失われる
- 手 3 と手 4 は繰り返してよい（1 回で完結させなくてよい）
- 落とし切ったらワークシートの先頭に `> **取り込み済み**（YYYY-MM-DD）` を
  書き、以降 **編集しない** 。正は `docs/` 側へ移る

## ワークシートの作り方（4 つの必須要素）

**空欄を並べただけの用紙は埋まらない。** どの欄にも次を添える。

1. **なぜこの欄が要るのか** —— 1 行。埋めないと何が起きるかを書く
2. **選択肢**（あるものだけ）—— `- [ ]` のチェックボックスで 3〜4 個。
   `option-first` と同じ形（推奨を先頭・ **選ばないとどうなるか** を各案に）
3. **自由記述欄** —— 選択肢に無い答えを書く場所を **必ず併置する** 。
   選択肢だけにすると、CLI で聞くのと変わらない
4. **記入例** —— 薄い灰色の例を 1 つ。 **例を消して上書きする** 形にする
   （白紙は埋まらないが、例があれば直せる）

~~~markdown
### 理由 —— なぜ要るのか

> ここが空だと、以降の成果物が全部「たぶんこうだろう」の上に積み上がる。
> **きれいな言葉に直さなくてよい。** 愚痴のままで構わない。

- [ ] 毎回手でやっていて時間が溶ける
- [ ] 手でやると間違える
- [ ] 人に頼まれて渡す必要がある
- [ ] 上のどれでもない（下に書く）

**自由記述**:

```
例: 月末に 30 個の CSV を目視で数えていて、去年 2 回数え間違えた。
```
~~~

## 深掘りの仕方（回収したあとの仕事）

**埋まっている欄をほめるのではなく、埋まっていない欄と、
埋まっているが曖昧な欄を突く。**

| 見つけるもの | 何を言うか |
|---|---|
| **空欄** | なぜその欄が要るかをもう一度示し、 **候補を 2〜3 個出して選ばせる** （白紙のまま聞き返さない） |
| **抽象語**（「適切に」「うまく」「ちゃんと」） | 「それは何が起きたら適切でないと言えますか」と観測できる形に落とす |
| **理由が要求の言い換え**（「〜が必要だから」） | 要求の **外側の事実** を聞く（いつ・何回・どれだけ困ったか） |
| **異常系が空** | **最も重い穴** 。埋まるまで設計へ進まない（失敗時の振る舞いを実装者が勝手に決めることになる） |
| **矛盾**（非目標に書いたことが仕様に混ざっている） | 両方を並べて、どちらが本当かを聞く |
| **書きすぎ**（L1 なのに仕様が 10 条） | スライスが大きすぎる。分割を提案する |

深掘りは **1 往復につき 3 点まで** 。全部指摘すると添削になり、
書く側が受け身になる。

## 落とす先（ワークシート → 正式文書）

| ワークシートの欄 | 落とす先 |
|---|---|
| 要求・理由・非目標 | `docs/usdm/src/S##-*.html` の要求行・理由行・説明行 |
| 入出力・正常系・異常系 | 同 HTML の入出力表と例の表（`N1`・`E1`） |
| 完走の条件 | 同 HTML の仕様行 |
| 層・契約・データの持ち方 | `docs/design/S##-*.md` の構成と図 |
| 迷ったこと・却下した案 | 同設計書の「判断の記録」 |
| 懸念・気になっていること | `docs/backlog.md` の負債表、または設計書の「L2 で足すもの」 |

**理由はユーザーの言葉のまま残す。** 敬体に直す・要約する・
「〜のため」に整えるのは構わないが、 **事実を落とさない**
（「去年 2 回数え間違えた」の「2 回」を消さない）。

## いつ使うか（関与モードで決まる）

| モード | ワークシート |
|---|---|
| `伴走` | **段1・段2 で必ず作る** 。CLI の 2 問と併用する |
| `既定` | 作らない（CLI の判断点だけ）。ユーザーが `/intake` と打てば作る |
| `任せる` | 作らない |

`伴走` でも **ユーザーが「今回は口頭でいい」と言えば作らない** 。
器を押しつけない（書く気を削ぐと、CLI より情報が減る）。

## やってはいけないこと

- **`/intake` を待たずに読みに行く**（書きかけへの指摘は、書く気を折る）
- **空欄を Claude が埋める** —— 特に理由と異常系。ここを推測した反復は、
  以降の成果物が全部推測の上に乗る
- 選択肢だけを並べる（自由記述欄が無いなら CLI で聞けばよい）
- 記入例を置かない（白紙は埋まらない）
- **落とした後もワークシートを更新し続ける**（正が 2 か所になりドリフトする。
  取り込んだ時点でワークシートは死ぬ）
- ワークシートを `docs/` に置く（成果物ではない。8 点セットは 8 点のまま）
- 1 往復で 4 点以上指摘する（添削になり、書く側が受け身になる）
- ユーザーの応答を待ち続ける —— 一定時間で **推奨で進み** 、
  進めた事実と根拠を記録に残す（`option-first` と同じ）
