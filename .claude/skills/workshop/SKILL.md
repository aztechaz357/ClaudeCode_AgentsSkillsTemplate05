# 工房レーン（workshop）

このプロジェクトには **2 つのレーン** がある。工房レーンはそのうち軽い方で、
反復開発レーンとの違いは 表 1 のとおり。

表 1: 2 つのレーンの違い

| | 工房レーン（`workshop/`） | 反復開発レーン（`docs/` + ソースルート） |
|---|---|---|
| 起点 | 思いつき・その場の困りごと | ゴール（`docs/concept.md`）とバックログ |
| 単位 | ツール 1 本 / ノート 1 本 | 縦切りスライス（S##） |
| 前工程 | なし | ゴールと完走の定義 → バックログ |
| 構造 | 1 ディレクトリ完結。層構成なし | クリーンアーキテクチャ（4 層 + 契約） |
| テスト | **必須**（テスト先行・Red 確認） | 必須（テスト先行 + E2E） |
| 文書 | `README.md` 1 枚 | **8 点セット**（要求・設計・テスト結果・マニュアル ほか） |
| 記法規約 | Markdown のみ必須（番号・作図は任意） | Markdown 必須（図は L3 で必要になったら） |
| 入口 | `/tool` `/note` | `/backlog` `/skeleton` `/iterate` `/refactor` |
| 所要 | 数十分 | 1 反復あたり半日以内 |

**工房レーンで省くのは前工程と構造であって、テストではない。**
テストを省くと「動いていたはずのツール」が黙って壊れ、次に使うときに
デバッグから始めることになる。それは速さを先食いしただけで、
思いつきを形にする速度をむしろ落とす。

## ディレクトリ構成

```
workshop/
├─ CATALOG.md            ツール一覧（自動生成。手で編集しない）
├─ tools/
│  └─ <kebab-name>/
│     ├─ README.md       このツールの取扱説明書（front matter がカタログの元）
│     ├─ main.<ext>      実装（1 ファイル完結が原則）
│     └─ test_main.<ext> テスト
└─ notes/
   ├─ INDEX.md           ノート一覧（自動生成。手で編集しない）
   └─ YYYY-MM-DD-<slug>.md
```

- ツール名・ノートの slug は **小文字ケバブケース** （`csv-diff`・`ps51-encoding`）
- ツールは **1 ディレクトリ完結** 。他のツールを import しない
  （共有したくなったら、それは昇格の合図。下の「昇格の判断」へ）
- `CATALOG.md` と `notes/INDEX.md` は `index_workshop.ps1` の生成物。
  手で書き換えても次の生成で消える

## front matter（カタログの元データ）

ツールの `README.md`:

```yaml
---
name: csv-diff          # ディレクトリ名と一致させる
summary: 2つの CSV の差分を行単位で出す   # 一覧で読む唯一の説明。1行で書く
created: 2026-07-30
updated: 2026-07-30     # 中身を変えたら必ず更新する
tags: [csv, diff]
status: draft           # draft | working | stable | promoted | retired
lang: py
entry: main.py
---
```

ノート:

```yaml
---
title: PowerShell 5.1 の文字コード事故
date: 2026-07-30
tags: [powershell, windows]
status: note            # note | idea | decision | howto
related: []             # 関連するノートのファイル名・ツール名
---
```

`status` は 表 2 の 5 段階で表す。ツールの中身を変えたら
`updated` と合わせて必ず見直す。

表 2: ツールの `status`

| status | 意味 | 次にすること |
|---|---|---|
| `draft` | 雛形を作っただけ。まだ動かない | テストを書いて実装する |
| `working` | 自分の用途では動く。粗さは残る | 使いながら落とし穴を README に足す |
| `stable` | 繰り返し使っている。壊れたら気づく | そのまま使う |
| `promoted` | 反復開発レーンへ昇格済み | `workshop/` 側は参照だけ残す |
| `retired` | 使わなくなった | 消さずに残す（なぜ捨てたかが情報） |

`retired` を消さないのは、同じ思いつきを半年後にもう一度やらないため。

## 作業の入口

| やること | 使うもの |
|---|---|
| ツールを 1 本作る | `/tool` → `quick-tool` スキル → `tool-smith` エージェント |
| ノートを 1 本書く | `/note` → `note-taking` スキル |
| 過去の成果物を探す | `/workshop search <語>` |
| 散らかりを整える | `/workshop tidy` → `note-keeper` エージェント |
| 反復開発レーンへ上げる | `/promote <tool> S##` |

## 索引の更新（必須）

ツールやノートを **追加・改名・status 変更したら必ず実行する** 。

```
powershell -File .claude/tools/index_workshop.ps1
```

差分だけ確認したいときは `-Check`（書き込まずに STALE を報告し、
ズレていれば終了コード 1）。

## 昇格の判断（工房 → 反復開発）

次のどれかに当てはまったら、そのツールは工房に置いておくには
大きくなりすぎている。`/promote` で反復開発レーンへ上げる。

- **他のツールから使いたくなった** —— 呼び出せる形への整理が要る
- **1 ファイルに収まらなくなった** —— 層に分ける段階（L2）
- **自分以外が使う** —— 仕様と E2E が要る
- **壊れると困る** —— 回帰テストと逆流の機械検証の対象にする
- **設定・状態を持ち始めた** —— infrastructure に隔離する対象

昇格しても **ゼロからやり直さない** 。動いている工房ツールは
`L1 動く` 相当から出発し、`/iterate` で成熟度を上げていく
（詳細は `/promote` の「昇格後の成熟度を決める」）。

逆に、 **昇格させない基準** も同じくらい大事。
「一度きりの調査」「自分の手元だけで完結する」「壊れても数分で書き直せる」
ものは工房に置いたままにする。全部を反復開発レーンに上げると、
思いつきを形にする速度が失われる。

昇格の手順は `/promote` コマンドを正とする。

## 棚卸し

月に 1 回、または `CATALOG.md` が 20 行を超えたら `/workshop tidy` を回す。

- `draft` のまま 30 日以上動いていないツールは、実装するか `retired` にする
- 同じことをする 2 本のツールは 1 本に寄せる（片方を `retired`）
- タグが 1 回しか使われていないものは、既存のタグに寄せる
- `related` が空のノートに、関連するノート・ツールを結ぶ

## 工房レーンで守る規約（これだけ）

- テストを先に書き、Red を確認してから実装する
- `README.md` の実行例は **実際に動かして出力を貼る** （推測で書かない）
- 図を描くならアスキーアートは使わない（`writing-conventions`）
- `**強調**` の前後に半角スペースを置く（`writing-conventions`）
- 作業のまとまりごとにコミットする

反復開発レーンの規約（スライス文書・バックログ・層構成・番号規約・
全体像の同期）は **工房レーンには適用しない** 。
