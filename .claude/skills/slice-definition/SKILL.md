# スライス定義スキル（slice-definition）

反復開発の既定の文書は **スライス 1 枚** 。
要求仕様書と設計書を分けず、1 ファイルが成熟度に応じて育っていく。

```
docs/slices/S##-<name>.md   （1 スライス 1 ファイル）
```

厚く書く必要があるスライス（不可逆・外部公開・安全機構・データ形式）だけ、
`requirements-definition` → `functional-design` の重い経路を使う。
判定条件は `agile-process` スキルの「いつ厚く書くか」を正とする。

## 要求は USDM で書く

要求部（要求・理由・仕様）の **記法の正は `usdm` スキル** 。
ここでは重複させない。要点だけ:

- 要求は `### 【REQ<番号>】<〜したい>` 。番号は S## と一致させる
- **理由は必須** 。無いと `build_usdm.py` が終了コード 1 で落とす
- 仕様は `- [ ] \`<要求番号-連番>\` 本文` 。`[x]` は検証済み

## 分量の上限（守ること）

L1 に着手する時点で書くのは、次の 3 つだけ。

| 節 | 上限 | 内容 |
|---|---|---|
| 要求と理由 | 要求 **1 個** ・理由 **1 行** | 「〜したい」＋なぜ困っているか |
| 仕様 | **3 条** | 正常系のみ。「入力 → 観測できる出力」 |
| 薄い設計 | **5 行** | 触るファイル・入口の関数名・データの流れ |

**上限を超えたら、書きすぎではなくスライスが大きすぎる。** 分割する。

L2 に上げるときに仕様へ境界値・失敗経路を追加し、
L3 に上げるときに `docs/design.md`（現状設計 1 枚）へ内容を移す。

## 要求・理由・仕様の書き方

L1 では **要求 1 個・理由 1 行・仕様 1〜3 条** だけ。
境界値と失敗経路は L2 の仕事なので、ここで考え込まない
（考え込むのが重さの正体）。

**L1 で書くもの**:

```markdown
### 【REQ1】CSV の行数をすぐ知りたい

- **理由**: 受領した CSV が想定件数かを Excel で開いて確認しており、
  10 万行だと開くだけで数分かかる

**仕様**:

- [ ] `<1-1>` `tool count data.csv` を実行すると、データ行数が `N 行` の形で標準出力に出る
```

**L2 で足すもの**（このスライスを L2 に上げる反復で、同じ要求に追記する）:

```markdown
- [ ] `<1-2>` 空ファイルを渡すと `0 行` が出る（ヘッダのみも 0 行）
- [ ] `<1-3>` 存在しないパスを渡すと終了コード 1 とパスを含むエラーが出る
```

チェックポイント（L1 用。4 つだけ）:

- [ ] 要求が「〜したい」の形か（「〜機能」「〜すること」になっていないか）
- [ ] **理由が要求の外側にある事実か**（要求の言い換えになっていないか）
- [ ] 仕様が「入力 → 観測できる出力」の形で、E2E テストに翻訳できるか
- [ ] クラス名・ライブラリ名を書いていないか（それは薄い設計の領分）

## 薄い設計の書き方

図もクラス図もシーケンス図も **書かない** （L3 で必要になったら
`docs/design.md` に書く）。5 行で足りる。

```markdown
- 触るファイル: `src/tool/cli.py`（追加）、`src/tool/count.py`（新規）
- 入口: `cli.main(argv)` → `count.count_rows(path) -> int`
- 流れ: 引数 → ファイル読み → 行数 → 標準出力
- 層: presentation（cli）→ application（count）。逆流なし
- 仮実装: ヘッダ判定は「1 行目を常にヘッダとみなす」で済ませる
```

「仮実装」の行が書けているかが重要。 **ここに書いた仮実装が、
そのまま負債表の 1 行になる** 。

## 進め方

1. **知覚**: `docs/backlog.md` の対象行・`docs/concept.md` のゴール・
   隣接する既存スライス文書を読む。既に動いているコードがあれば実物を見る
2. **書く**: `./template.md` を写して要求・理由・仕様と薄い設計を埋める
   （要求部の記法は `usdm` スキルの `template.md` と同一）
3. **確認**: 曖昧なままでも **L1 なら進んでよい** 。ただし次の 3 つだけは
   AskUserQuestion で確認する（後戻りが大きいため）:
   - **理由**（推測で書かない。理由の推測は仕様の推測より害が大きい）
   - 出力の形式（他のものがこれを読む場合）
   - 不可逆な操作を含むかどうか
4. **検証**: `<ツール実行コマンド> .claude/tools/build_usdm.py` を実行し、
   USDM 違反が 0 件であることを確認する（理由の欠落・番号の不整合を検出する）
5. **反復後**: 「実績」に実際の出力を貼り、「残した手抜き」を埋め、
   バックログの負債表へ転記して、要求ビューアを再生成する

## 成熟度を上げるときの追記

| 上げる先 | 追記する節 | やること |
|---|---|---|
| L2 | 仕様 | 境界値・失敗経路・既定値を追加し、テストを 1 条 1 本以上に |
| L2 | 残した手抜き | 仮実装を消し、消した行に `済` を付ける |
| L3 | （移す） | 構造の内容を `docs/design.md` へ移し、ここはリンクにする |

## 品質チェック

- [ ] **`build_usdm.py` が 0 件で通る**（理由の欠落・番号の不整合がない）
- [ ] 要求が「〜したい」で、理由が要求の外側にある事実か
- [ ] 仕様が 3 条以内（L1 の場合）
- [ ] 薄い設計が 5 行以内で、触るファイルと入口の関数名が書かれている
- [ ] 仮実装・ハードコードが「残した手抜き」に列挙されている
- [ ] 実績に **実際に実行した出力** が貼られている（推測禁止・絶対ルール 7）
- [ ] `docs/backlog.md` の成熟度と負債表が同期している
