# スライス定義スキル（slice-definition）

反復に着手するとき、最初に作るのは次の 2 枚。

```
docs/usdm/src/S##-<name>.html   … 要求仕様書（8 点セットの 1 番目）＋ トレース表
docs/slices/S##-<name>.md       … ハブ（8 点への索引・実績・残した手抜き）
```

残りの 5 点（設計書・単体テスト・実装・統合テスト・テスト結果・マニュアル）は
それぞれの担当が作る。 **このスキルは一式の入口を用意するところまで** 。
一覧と担当の正は `agile-process/deliverables.md` 。

## スライスの切り方

**層ではなく経路で切る。** 「入力を受け取り、処理し、観測できる結果を返す」
までが 1 本に入っていること。

- **良い**: 「CSV を渡すと件数が標準出力に出る」（入口・処理・出口が入っている）
- **悪い**: 「domain 層のエンティティを定義する」（横切り。単体では動かない）

目安は **8 点セットを半日以内でそろえられる量** 。超えるなら分割する。

## 要求は USDM で書く

記法の正は `usdm` スキル。ここでは重複させない。要点だけ:

- `.claude/skills/usdm/template.html` を `docs/usdm/src/S##-<name>.html`
  にコピーして埋める。要求ID は `REQ<番号>` で、番号は S## と一致させる
- **理由は必須** 。無いと `build_usdm.py` が終了コード 1 で落とす
- 仕様は `<tr class="spec">` の行。検証欄 `□` / `☑` が検証状態
- 表の下に **トレース表** を置く。`☑` にした仕様は 5 列すべてを埋める

## 分量の上限（守ること）

L1 に着手する時点で書くのは、次の 3 つだけ。

| 節 | 上限 | 内容 |
|---|---|---|
| 要求と理由 | 要求 **1 個** ・理由 **1 行** | 「〜したい」＋なぜ困っているか |
| 仕様 | **3 条** | 正常系のみ。「入力 → 観測できる出力」 |
| ハブ | 索引と空の実績欄 | 本文は書かない（各成果物へのリンクだけ） |

**上限を超えたら、書きすぎではなくスライスが大きすぎる。** 分割する。

L2 に上げるときに仕様へ境界値・失敗経路を追加し、
L3 に上げるときに設計の内容を `docs/design.md`（現状設計 1 枚）へ移す。

## 要求・理由・仕様の書き方

L1 では **要求 1 個・理由 1 行・仕様 1〜3 条** だけ。
境界値と失敗経路は L2 の仕事なので、ここで考え込まない
（考え込むのが重さの正体）。

**L1 で書くもの**（`docs/usdm/src/S01-count.html` の `<tbody>`）:

```html
<tr class="requirement">
  <td class="category">集計</td><td class="kind">要求</td>
  <td class="check"></td>
  <td class="id">REQ1</td><td class="body">CSV の行数をすぐ知りたい</td>
</tr>
<tr class="reason">
  <td class="category"></td><td class="kind">理由</td>
  <td class="check"></td><td class="id"></td>
  <td class="body">受領した CSV が想定件数かを Excel で開いて確認しており、
    10 万行だと開くだけで数分かかる</td>
</tr>
<tr class="spec">
  <td class="category"></td><td class="kind">仕様</td>
  <td class="check">□</td><td class="id">1-1</td>
  <td class="body">tool count data.csv を実行するとデータ行数が「N 行」の形で
    標準出力に出る</td>
</tr>
```

**L2 で足すもの**（このスライスを L2 に上げる反復で、同じ要求に追記する）:

```html
<tr class="spec">
  <td class="category"></td><td class="kind">仕様</td>
  <td class="check">□</td><td class="id">1-2</td>
  <td class="body">空ファイルを渡すと「0 行」が出る（ヘッダのみも 0 行）</td>
</tr>
<tr class="spec">
  <td class="category"></td><td class="kind">仕様</td>
  <td class="check">□</td><td class="id">1-3</td>
  <td class="body">存在しないパスを渡すと終了コード 1 とパスを含むエラーが出る</td>
</tr>
```

チェックポイント（L1 用。4 つだけ）:

- [ ] 要求が「〜したい」の形か（「〜機能」「〜すること」になっていないか）
- [ ] **理由が要求の外側にある事実か**（要求の言い換えになっていないか）
- [ ] 仕様が「入力 → 観測できる出力」の形で、E2E テストに翻訳できるか
- [ ] クラス名・ライブラリ名を書いていないか（それは設計書の領分）

## ハブに書くこと・書かないこと

| 書く | 書かない |
|---|---|
| 8 点セットへのリンクと状態 | 要求の本文（要求 HTML が正） |
| 実績（実際に動かした出力の要約） | 設計の内容（設計書が正） |
| 残した手抜きの表 | テストの件数の詳細（テスト結果まとめが正） |
| 進め方の判断（分割・順序・打ち切り） | 設計の判断（設計書の「判断の記録」が正） |

**リンク先に書いてあることを写さない。** 写した瞬間に二重管理が始まり、
必ず片方が古くなる。

## 進め方

1. **知覚**: `docs/backlog.md` の対象行・`docs/concept.md` のゴール・
   隣接する既存スライスを読む。既に動いているコードがあれば実物を見る
2. **書く**: `.claude/skills/usdm/template.html` を
   `docs/usdm/src/S##-<name>.html` にコピーして要求・理由・仕様を埋め、
   `./template.md` を写してハブを作る
3. **確認**: 曖昧なままでも **L1 なら進んでよい** 。ただし次の 3 つだけは
   AskUserQuestion で確認する（後戻りが大きいため）:
   - **理由**（推測で書かない。理由の推測は仕様の推測より害が大きい）
   - 出力の形式（他のものがこれを読む場合）
   - 不可逆な操作を含むかどうか
4. **検証**: `<ツール実行コマンド> .claude/tools/build_usdm.py` を実行し、
   USDM 違反が 0 件であることを確認する
5. **反復後**: 検証済みになった仕様の `□` を `☑` に変え、トレース表を埋め、
   ハブの「実績」「残した手抜き」を埋め、バックログの負債表へ転記する

## 成熟度を上げるときの追記

| 上げる先 | 追記する場所 | やること |
|---|---|---|
| L2 | 要求 HTML の仕様 | 境界値・失敗経路・既定値を追加し、テストを 1 条 1 本以上に |
| L2 | ハブの「残した手抜き」 | 仮実装を消し、消した行に `済` を付ける |
| L3 | （移す） | 設計の内容を `docs/design.md` へ移し、設計書はリンクにする |

## 品質チェック

- [ ] **`build_usdm.py` が 0 件で通る**（理由の欠落・番号の不整合・線の切れ）
- [ ] **`check_deliverables.py --slice S##` が 0 で通る**（8 点がそろっている）
- [ ] 要求が「〜したい」で、理由が要求の外側にある事実か
- [ ] 仕様が 3 条以内（L1 の場合）
- [ ] ハブに他の成果物の本文を書き写していないか
- [ ] 仮実装・ハードコードが「残した手抜き」に列挙されているか
- [ ] 実績に **実際に実行した出力** が貼られているか（推測禁止・絶対ルール 7）
- [ ] `docs/backlog.md` の成熟度と負債表が同期しているか
