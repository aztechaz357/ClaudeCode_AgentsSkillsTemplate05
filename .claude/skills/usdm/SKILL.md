# USDM 記法（usdm）

このプロジェクトの要求は **USDM** で書く。
USDM の核心は次の 3 つで、これ以外の作法は本スキルでは要求しない。

1. **要求は「〜したい」で書く** —— 願望の形にすると、主体と目的が残る
2. **要求には理由を必ず併記する** —— 理由のない要求は認めない
3. **仕様は要求から導出する** —— 番号で親要求に紐づけ、漏れを検出できるようにする

## なぜ理由を必須にするのか

**理由が無い要求は、後で捨てられない。**

反復開発では「これは今回のゴールに寄与しないので降ろす」という判断を
繰り返す。そのとき判断材料になるのは要求の文面ではなく **理由** である。
理由が無いと、作るべきか分からないまま全部作ることになり、
ゴールが遠ざかる（このプロセスが最も避けたい状態）。

副産物として、理由は **仕様の漏れを教えてくれる** 。
「全件出ると目で探すことになる」が理由なら、
「0 件のときはどう見えるべきか」が自然に出てくる。

そして理由の有無は **機械検証できる** 。`build_usdm.py` が
理由の無い要求を終了コード 1 で落とす。LLM の判断に頼らない。

## 記法

要求はスライス文書（`docs/slices/S##-<name>.md`）の「要求」節に書く。
厚い経路では要求仕様書（`docs/requirements/S##-<name>.md`）に書くが、
**記法は同じ** 。

```markdown
## 要求

### 【REQ2】列を指定して絞り込みたい

- **理由**: 全件出ると目的の行を目で探すことになる
- **範囲**: 完全一致のみ。部分一致・正規表現は対象外

**仕様**:

- [ ] `<2-1>` `--col NAME=値` を渡すと、その列が値と完全一致する行だけを数える

### 【REQ2.1】複数列を AND で指定したい

- **理由**: 1 列では絞り切れないデータがある

**仕様**:

- [ ] `<2.1-1>` `--col` を 2 回渡すと両方に一致する行だけを数える
```

### 各要素の規則

| 要素 | 規則 |
|---|---|
| 要求見出し | `### 【REQ<番号>】<〜したい>` 。 **見出しレベルは常に `###`** |
| 階層 | **番号のドットだけで表す** （`REQ2.1` は `REQ2` の子）。見出しレベルで深さを表さない —— 二重表現は必ず食い違う |
| 理由 | `- **理由**:` **必須** 。1 行で書く |
| 範囲 | `- **範囲**:` 任意。要求の及ぶ境界を書く（対象外を明示する） |
| 仕様 | `**仕様**:` の直後の箇条書き。`- [ ] \`<番号>\` 本文` |
| 仕様番号 | `<要求番号-連番>` 。`REQ2.1` の仕様は `<2.1-1>` `<2.1-2>` |
| 検証状態 | `[ ]` 未検証 / `[x]` 検証済み（対応するテストが緑） |
| スライス番号 | **S## と REQ## を一致させる** （`S02` なら最上位は `REQ2`） |

### 番号を要求と一致させる理由

バックログ（`docs/backlog.md`）のスライス行が、そのまま要求一覧を兼ねる。
番号を別体系にすると対応表が必要になり、対応表は必ず腐る。
**要求の正は 1 か所（スライス文書）だけ** に保つ。

トレーサビリティの背骨:

```
docs/concept.md の完走の定義   … 最上位要求
  → docs/backlog.md のスライス行 … 要求（S## = REQ##）
    → スライス文書の【REQ##】     … 要求
      → 【REQ##.n】               … 下位要求
        → <##-n>                  … 仕様
          → E2E テスト            … 検証
```

## 成熟度との対応（薄さを保つ仕組み）

**USDM を入れても要求は薄いまま。** 深さを決めるのは成熟度で、
完了条件の正は `.claude/skills/agile-process/maturity.md` 。

| 成熟度 | 書く量 |
|---|---|
| **L1 動く** | 要求 **1 個** ・理由 **1 行** ・仕様 **1〜3 条**（正常系のみ） |
| **L2 固い** | 同じ要求に仕様を追加（境界値・失敗経路・既定値）。下位要求が必要なら足す |
| **L3 整った** | 要求は変えない。構造を `docs/design.md` へ反映する |

**L1 で仕様を網羅しようとしない。** 上限を超えたら、書きすぎではなく
スライスが大きすぎる（`docs/backlog.md` で分割する）。

L2 に上げる反復で足す仕様の例:

```markdown
- [ ] `<2-2>` 一致行が 0 件なら `0 行` と出す（空でも異常終了しない）
- [ ] `<2-3>` 存在しない列名なら終了コード 1 と列名一覧を出す
```

## 書き方の良い例と悪い例

### 要求は「〜したい」で書く

**悪い例**（主体と目的が消える）:

```markdown
### 【REQ2】フィルタ機能
### 【REQ2】列を指定して絞り込むこと
```

**良い例**:

```markdown
### 【REQ2】列を指定して絞り込みたい
```

「機能」で終わる名詞句は要求ではなく実装の名前。
「〜すること」は仕様の語法であって要求の語法ではない。

### 理由は「なぜ困っているか」を書く

**悪い例**（何も言っていない）:

```markdown
- **理由**: 必要だから
- **理由**: 仕様書に書かれているから
- **理由**: 絞り込みができないと不便だから
```

3 つ目は一見それらしいが、要求を言い換えただけ。
**理由は要求の外側にある事実** でなければならない。

**良い例**（要求を消しても成立する事実）:

```markdown
- **理由**: 実データが 5 万行あり、全件出ると目的の行を目で探すことになる
- **理由**: 現状は Excel に貼って手でフィルタしており、毎回 10 分かかる
```

判定法: **理由を読んで、要求とは別の仕様を思いつけるか** 。
思いつけないなら、それは理由になっていない。

### 仕様は「入力 → 観測できる出力」で書く

**悪い例**（検証できない）:

```markdown
- [ ] `<2-1>` 絞り込みが正しく動作する
```

**良い例**:

```markdown
- [ ] `<2-1>` `--col NAME=値` を渡すと、その列が値と完全一致する行だけを数える
```

クラス名・ライブラリ名は書かない（それは「薄い設計」の領分）。

## 機械検証（必ず実行する）

要求を書いたり直したりしたら実行する。前置コマンドはプロファイルの
「`.claude/tools/` の Python ツール実行」を使う（推測しない）。

```
<ツール実行コマンド> .claude/tools/build_usdm.py
<ツール実行コマンド> .claude/tools/build_usdm.py --check
```

検出される違反:

| 違反 | 意味 |
|---|---|
| 理由の欠落 | USDM の核心ルール違反。理由を書く |
| 仕様が 0 件の要求 | L1 でも仕様は 1 条必要。要求だけ書いて止まっている |
| 仕様番号と親要求番号の不一致 | `REQ2` の下に `<3-1>` がある等。導出関係が壊れている |
| 番号の重複 | 同じ要求番号・仕様番号が 2 か所にある |
| S## と REQ## の不一致 | ファイル名の S02 に対して最上位が `REQ3` 等 |

**NG が出たまま反復を完了としない。**
`--check` は生成せず、HTML が要求より古い（STALE）ことを終了コード 1 で報告する。

## 表示（HTML ビューア）

`build_usdm.py` は要求ツリーを 1 枚の自己完結 HTML（`docs/usdm/index.html`）に
出力する。外部依存ゼロなので `file://` でそのまま開ける。

- 要求ツリー（番号の階層。折りたたみ）
- **理由は常時表示** —— USDM の核心なので隠さない
- 仕様一覧（`[x]` は検証済みバッジ）・全文検索・成熟度バッジ

生成物は gitignore 対象（`docs/usdm/`）。要求を直したら再生成する
（忘れても `--check` が検出する）。

## やってはいけないこと

- 理由を書かずに要求を足す（機械検証で落ちる）
- 理由に要求の言い換えを書く（機械検証では落ちないが、無意味）
- 要求を別ファイル（要求ツリー専用の文書）に切り出す —— 二重管理になる。
  要求の正はスライス文書だけ
- 見出しレベルで階層を表す（番号だけが正）
- L1 で仕様を網羅する（越権。次の反復の仕事）
- 生成された HTML を手で編集する（次の生成で消える）
