# USDM 記法（usdm）

このプロジェクトの要求は **USDM** で、 **HTML の表** として書く。
表の形は Excel の USDM テンプレート（`USDMテンプレート_v0.02.xlsx`）と
同じ列・同じ行の語彙で、ブラウザでそのまま開ける HTML にしたもの。

USDM の核心は次の 3 つで、これ以外の作法は本スキルでは要求しない。

1. **要求は「〜したい」で書く** —— 願望の形にすると、主体と目的が残る
2. **要求には理由を必ず併記する** —— 理由のない要求は認めない
3. **仕様は要求から導出する** —— 番号で親要求に紐づけ、漏れを検出できるようにする

## なぜ理由を必須にするのか

**理由が無い要求は、後で捨てられない。**

反復開発では「これは今回のゴールに寄与しないので降ろす」という判断を
繰り返す。そのとき判断材料になるのは要求の文面ではなく **理由** である。
理由が無いと、作るべきか分からないまま全部作ることになり、
ゴールが遠ざかる（このプロセスが最も避けたい状態）。

副産物として、理由は **仕様の漏れを教えてくれる** 。
「全件出ると目で探すことになる」が理由なら、
「0 件のときはどう見えるべきか」が自然に出てくる。

そして理由の有無は **機械検証できる** 。`build_usdm.py` が
理由の無い要求を終了コード 1 で落とす。LLM の判断に頼らない。

## 置き場所

| | パス | 誰が書くか |
|---|---|---|
| **手書きの正**（機能要求） | `docs/usdm/src/S##-<name>.html` | 人・エージェント |
| **手書きの正**（品質要求） | `docs/usdm/src/Q##-<name>.html` | 人・エージェント |
| **要求一覧**（生成物・gitignore） | `docs/usdm/index.html` | `build_usdm.py` |
| テンプレート | `.claude/skills/usdm/template.html` / `template-quality.html` | —— |
| 記入例（話題沸騰ポット） | `.claude/skills/usdm/example/` | —— |

**1 スライス（1 品質特性）につき 1 ファイル。** テンプレートをコピーして
埋める。要求一覧はそれを束ねた **生成物** で、手書きファイルと
**同じ表構造・同じ見た目** になる（1 枚を開いても一覧を開いても同じ列が並ぶ）。

スライス文書（`docs/slices/S##-<name>.md`）の「要求」節には
**リンクだけ** を置く（`template.md` 参照）。要求の本文をスライス文書に
書き写さない —— 二重管理になり、必ず食い違う。

```
docs/
  slices/S02-filter.md      … 薄い設計・実績・残した手抜き（要求はリンク）
  usdm/
    src/S02-filter.html     … ★手書きの正（機能要求）
    src/Q01-time.html       … ★手書きの正（品質要求）
    index.html              … 生成物（要求一覧 1 枚）
```

## 表の形（機能要求）

Excel シート「機能要求」と同じ 4 列。

```html
<table class="usdm functional">
<thead>
<tr><th>カテゴリ名</th><th>要求</th><th>要求ID</th><th>要求仕様</th></tr>
</thead>
<tbody>
<tr class="requirement">
  <td class="category">抽出</td>
  <td class="kind">要求</td>
  <td class="id">REQ2</td>
  <td class="body">列を指定して絞り込みたい</td>
</tr>
<tr class="reason">
  <td></td><td></td>
  <td class="kind">理由</td>
  <td class="body">実データが 5 万行あり、全件出ると目で探すことになる</td>
</tr>
<tr class="spec-group">
  <td></td><td></td>
  <td class="kind">＜列指定＞</td>
  <td></td>
</tr>
<tr class="spec">
  <td></td>
  <td class="check">□</td>
  <td class="id">2-1</td>
  <td class="body">--col NAME=値 を渡すとその列が値と完全一致する行だけを数える</td>
</tr>
</tbody>
</table>
```

### 行の語彙（`<tr class="...">`）

**行の意味は class が正。** 位置や見た目では判断しない。

| class | Excel の行 | 中身 | 必須 |
|---|---|---|---|
| `requirement` | 要求 | 「〜したい」（抽象的）。`td.id` に要求ID | ● |
| `reason` | 理由 | 「〜なので」。 **要求 1 個につき 1 行必須** | ● |
| `note` | 説明 | 備忘録。実装されなくてよいもの。範囲・対象外もここ | |
| `req-group` | ＜要求グループ名＞ | 下位要求の束ね名。`td.kind` に `＜…＞` | |
| `spec-group` | ＜仕様グループ名＞ | 仕様の束ね名。`td.kind` に `＜…＞` | |
| `spec` | □□□ + 仕様 | 「〜を〜する」（具体的）。`td.check` と `td.id` | ● |

### セルの語彙（`<td class="...">`）

| class | 意味 |
|---|---|
| `category` | カテゴリ名（最上位要求の行にだけ書く） |
| `kind` | ラベル欄（`要求` `理由` `説明` `＜グループ名＞`）。 **グループ行だけ機械が読む** |
| `id` | 要求ID（`REQ2`）または仕様ID（`2-1`） |
| `body` | 本文 |
| `check` | 検証状態。`□` 未検証 / `☑` 検証済み（対応するテストが緑） |

- **空の `<td></td>` を消さない** —— 列がずれる。意味は持たない
- セルは **class で読む** ので、体裁のために空セルを足しても壊れない
- 本文中の改行・インデントは 1 行に畳まれる（見た目のためのもの）

### 番号の規則

| 対象 | 形 | 例 |
|---|---|---|
| 機能要求のファイル | `S##-<name>.html` | `S02-filter.html` |
| 機能要求の要求ID | `REQ<番号>` （ **S## と一致** ） | `REQ2` `REQ2.1` |
| 品質要求のファイル | `Q##-<name>.html` | `Q01-time-efficiency.html` |
| 品質要求の要求ID | `QUA<番号>` （ **Q## と一致** ） | `QUA1` `QUA1.1` |
| 仕様ID | `<要求の番号部分>-<連番>` | `2-1` `2.1-1` `Q1-1` |

- **階層は番号のドットだけで表す** （`REQ2.1` は `REQ2` の子）。
  行の位置・インデントで深さを表さない —— 二重表現は必ず食い違う
- 品質要求の番号部分は `Q` 付き（`QUA1` の仕様は `Q1-1`）。
  機能要求と混ざらないようにするため

### 番号を要求と一致させる理由

バックログ（`docs/backlog.md`）のスライス行が、そのまま要求一覧を兼ねる。
番号を別体系にすると対応表が必要になり、対応表は必ず腐る。
**要求の正は 1 か所（`docs/usdm/src/` の 1 ファイル）だけ** に保つ。

トレーサビリティの背骨:

```
docs/concept.md の完走の定義      … 最上位要求
  → docs/backlog.md のスライス行  … 要求（S## = REQ##）
    → docs/usdm/src/S##-*.html    … 要求
      → REQ##.n                   … 下位要求
        → ##-n                    … 仕様
          → E2E テスト            … 検証（緑になったら ☑）
```

## 表の形（品質要求）

Excel シート「品質要求」と同じ列。機能要求の 4 列の前に
`品質特性` `品質副特性` を、後ろに `評価尺度` `対応知識・技術` を足したもの。

要求を書く前に **定義 → 解釈 → メトリクス** の 3 行を必ず置く。

| class | 意味 | 必須 |
|---|---|---|
| `characteristic` | 品質特性・副特性と、JIS X 25010:2013 の **定義** をそのまま引く | ● |
| `interpretation` | **解釈** —— その定義を、この開発対象では何と読むか | ● |
| `metrics` | **メトリクス** —— 達成度合いを評価する指標と測定方法 | ● |

そのあとは機能要求と同じ（`requirement` → `reason` → `spec`）。
ただし **仕様には `td.measure`（評価尺度）が必須** 。
測れない品質要求は検証できないので、書く意味がない。
`td.knowledge`（対応知識・技術）は任意。

```html
<tr class="spec">
  <td></td><td></td>
  <td class="check">□</td>
  <td class="id">Q1-1</td>
  <td class="body">10 ℃ で 100 mL の水を 1 分以内に沸騰させる</td>
  <td class="measure">通電開始から沸騰検知までの経過時間（秒）</td>
  <td class="knowledge">ヒータ出力設計・熱容量計算</td>
</tr>
```

**解釈が定義の writing-back になっていないか毎回確かめる。**
定義を写しただけの解釈からは要求が 1 個も出てこない。

## Excel から意図して変えたところ

Excel は **列をずらすこと** で階層を表すが、HTML では 3 点だけ変えた。
理由はどれも「二重表現を作らない」ため。

| Excel | この HTML | なぜ |
|---|---|---|
| 下位要求は列を 1 つ右へずらす | 列は固定。階層は **番号のドットだけ** | 位置と番号の二重表現は必ず食い違う |
| 要求ID 欄がラベル（要求・理由）も兼ねる | ラベル欄（`要求` 列）と ID 欄を分ける | 機械が ID を一意に読めるようにする |
| 要求ID は任意の文字列（`pot-230QR`） | `REQ##` / `QUA##`（ファイル名と一致） | バックログと対応表なしで突き合わせる |

表示上の階層（インデント）は、要求一覧の生成時に **番号から計算** する。
手書きファイルにインデントを書かない。

## 成熟度との対応（薄さを保つ仕組み）

**USDM を入れても要求は薄いまま。** 深さを決めるのは成熟度で、
完了条件の正は `.claude/skills/agile-process/maturity.md` 。

| 成熟度 | 書く量 |
|---|---|
| **L1 動く** | 要求 **1 個** ・理由 **1 行** ・仕様 **1〜3 条**（正常系のみ）。グループ行は不要 |
| **L2 固い** | 同じ要求に仕様を追加（境界値・失敗経路・既定値）。仕様が増えたら `spec-group` で束ねる。下位要求が必要なら足す |
| **L3 整った** | 要求は変えない。構造を `docs/design.md` へ反映する |

**L1 で仕様を網羅しようとしない。** 上限を超えたら、書きすぎではなく
スライスが大きすぎる（`docs/backlog.md` で分割する）。

L2 に上げる反復で足す仕様の例:

```html
<tr class="spec">
  <td></td><td class="check">□</td><td class="id">2-2</td>
  <td class="body">一致行が 0 件なら「0 行」と出す（空でも異常終了しない）</td>
</tr>
<tr class="spec">
  <td></td><td class="check">□</td><td class="id">2-3</td>
  <td class="body">存在しない列名なら終了コード 1 と列名一覧を出す</td>
</tr>
```

品質要求は L1 では書かない（機能が通ってから）。

## 書き方の良い例と悪い例

### 要求は「〜したい」で書く

**悪い例**（主体と目的が消える）:

```html
<td class="body">フィルタ機能</td>
<td class="body">列を指定して絞り込むこと</td>
```

**良い例**:

```html
<td class="body">列を指定して絞り込みたい</td>
```

「機能」で終わる名詞句は要求ではなく実装の名前。
「〜すること」は仕様の語法であって要求の語法ではない。

### 理由は「なぜ困っているか」を書く

**悪い例**（何も言っていない）:

```html
<td class="body">必要だから</td>
<td class="body">仕様書に書かれているから</td>
<td class="body">絞り込みができないと不便だから</td>
```

3 つ目は一見それらしいが、要求を言い換えただけ。
**理由は要求の外側にある事実** でなければならない。

**良い例**（要求を消しても成立する事実）:

```html
<td class="body">実データが 5 万行あり、全件出ると目的の行を目で探すことになる</td>
<td class="body">現状は Excel に貼って手でフィルタしており、毎回 10 分かかる</td>
```

判定法: **理由を読んで、要求とは別の仕様を思いつけるか** 。
思いつけないなら、それは理由になっていない。

### 仕様は「入力 → 観測できる出力」で書く

**悪い例**（検証できない）:

```html
<td class="body">絞り込みが正しく動作する</td>
```

**良い例**:

```html
<td class="body">--col NAME=値 を渡すとその列が値と完全一致する行だけを数える</td>
```

クラス名・ライブラリ名は書かない（それは「薄い設計」の領分）。

### グループ名は「束ねる観点」を書く

`＜仕様1＞＜仕様2＞` のような連番はグループ名ではない。
`＜列指定＞` `＜0 件のとき＞` のように、 **束ねた観点** を書く。
束ねる観点が思いつかないなら、グループ行は要らない。

要求グループの分割方法は **時系列・構成・状態・共通** のいずれか
（Excel テンプレートと同じ）。どれにも当てはまらない分割は、
たいてい分割ではなく別のスライス。

## 機械検証（必ず実行する）

要求を書いたり直したりしたら実行する。前置コマンドはプロファイルの
「`.claude/tools/` の Python ツール実行」を使う（推測しない）。

```
<ツール実行コマンド> .claude/tools/build_usdm.py
<ツール実行コマンド> .claude/tools/build_usdm.py --check
```

検出される違反:

| 違反 | 意味 |
|---|---|
| `missing-reason` | 理由の欠落。USDM の核心ルール違反 |
| `no-spec` | 仕様が 0 条の要求。L1 でも仕様は 1 条必要 |
| `spec-number-mismatch` | 仕様番号の要求部分が親要求と違う（`REQ2` の下に `3-1`） |
| `duplicate-requirement` / `duplicate-spec` | 番号の重複 |
| `doc-number-mismatch` | ファイルの `S##`/`Q##` と最上位要求の番号が違う |
| `orphan-requirement` | 親要求が宣言されていない下位要求 |
| `spec-without-requirement` / `reason-without-requirement` | 要求の外に置かれた行 |
| `unknown-row` | class の無い / 未知の `<tr>` |
| `missing-id` | 要求ID・仕様ID の書式違反 |
| `bad-check` | 検証欄が `□` でも `☑` でもない |
| `kind-mismatch` | ファイル名（S/Q）と表の種別（functional/quality）が違う |
| `missing-characteristic` / `missing-interpretation` / `missing-metrics` | 品質要求の前提（定義・解釈・メトリクス）が欠けている |
| `missing-measure` | 品質要求の仕様に評価尺度がない |

**NG が出たまま反復を完了としない。**
`--check` は生成せず、要求一覧が要求より古い（STALE）ことを終了コード 1 で報告する。

記入例で動きを確かめられる:

```
<ツール実行コマンド> .claude/tools/build_usdm.py --source .claude/skills/usdm/example --out <一時パス>
```

## 表示（要求一覧）

`build_usdm.py` は手書きの要求 HTML を束ねて、1 枚の自己完結 HTML
（`docs/usdm/index.html`）に出力する。外部依存ゼロなので
`file://` でそのまま開ける。

- **手書きと同じ表** —— 機能要求 / 品質要求ごとに、同じ列で並ぶ
- **理由は常時表示** —— USDM の核心なので隠さない
- **折りたたみ 4 段階** —— 文書 / 要求グループ / 要求 / 仕様グループ。
  行頭の `▾` `▸` をクリックする。要求のキャレットが畳むのは
  **自分の詳細（理由・説明・仕様）だけ** なので、
  「すべて閉じる」で下位要求まで含めた **要求だけの一覧** になる
- **絞り込み** —— 仕様を「すべて / 未検証のみ / 検証済みのみ」で切り替える
- **全文検索** —— 要求・理由・仕様・評価尺度を対象にする。
  検索中は折りたたみを無視して開く（畳んだせいで結果が消えないように）

生成物は gitignore 対象（`docs/usdm/index.html`）。
要求を直したら再生成する（忘れても `--check` が検出する）。

**生成された `index.html` を手で編集しない。** 次の生成で消える。
見た目を直したいときは `build_usdm.py` の `_STYLE` と
`.claude/skills/usdm/template*.html` の `<style>` を **両方** 直す
（片方だけ直すと「手書きと同じ表」という約束が崩れる）。

## やってはいけないこと

- 理由を書かずに要求を足す（機械検証で落ちる）
- 理由に要求の言い換えを書く（機械検証では落ちないが、無意味）
- 要求の本文をスライス文書にも書き写す —— 二重管理になる。
  スライス文書に置くのは要求 HTML へのリンクだけ
- 行の位置やインデントで階層を表す（番号だけが正）
- 空の `<td></td>` を消す（列がずれる）
- L1 で仕様を網羅する・グループ行を作り込む（越権。次の反復の仕事）
- 生成された `docs/usdm/index.html` を手で編集する
- 評価尺度を空にしたまま品質要求を書く（測れないものは要求にしない）
