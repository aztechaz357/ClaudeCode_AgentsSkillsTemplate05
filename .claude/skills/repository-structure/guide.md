# 配置ガイド — 実例と例外ケース

SKILL.md の判定フローを、実例で補足するガイド。
**プロジェクトで実際に配置を決めたら、この表に実例を追記していく**
（このガイドを育てることが、次回の判断コストを下げる）。

## まず成熟度を確認する

| 成熟度 | 配置の考え方 |
|---|---|
| **L1 動く** | 下の基本パターンで **4 層に分ける**（1 層 1 ファイルでよい）。契約は外部 I/O があるときだけ 1 本 |
| **L2 固い** | 外部 I/O をすべて契約経由にし、配線を 1 か所に集める |
| **L3 整った** | 同 + 違反ゼロ・重複の統合 |

**分けるのは安い。契約を切るのは高い。** だから層は最初から分け、
契約だけを必要最小限にする。

## 配置の基本パターン（L2 以降）

| 機能の種類 | presentation | application | domain | infrastructure |
|---|---|---|---|---|
| 外部サービス連携 | — | 呼び出しの組み立て | 扱う値・判定 | HTTP / SDK 実装 |
| 永続化 | — | 保存・読み出しの手順 | 保存する値 | DB / ファイル実装 |
| 承認・権限 | 対話 UI | 判定の呼び出し | ポリシーの判定 | 既定ポリシーの読み込み |
| 観測（トレース・計測） | 表示コマンド | 計測の挿入点 | 計測する値 | 記録実装 |
| 共有状態（モード切替等） | 状態を操作する UI | 状態の参照 | 状態の値 | 状態ホルダ |

パターン: **判断と計算は domain・外部に触るものは infrastructure・
手順の組み立ては application・利用者に見せるものは presentation** 。
この分担が崩れる配置は設計から疑う。

**契約（Port）を切るのは外部 I/O があるときだけ** 。
ファイル・DB・ネットワーク・時刻・乱数に触るものは契約越しに呼ぶ
（`application` が `infrastructure` を直接 import するのは違反）。
純粋な計算に契約を切るのは意味の無い中間層なので禁止。

## 新しい種類のコードが来たときの例外判断

- **新しいフロントエンド**（HTTP サーバ・GUI 等）: presentation に
  サブディレクトリを作る
- **外部コマンド委譲**: 実装は infrastructure。コマンドの設定は設定ファイル
- **バッチ・スケジューラ**: 進行の組み立ては application（ユースケース）、
  起動トリガは presentation
- **設定の読み込み**: infrastructure（読んだ値を使う判断は domain）
- **どの層にも属さない気がするもの**: まず domain に置けないか疑う。
  駄目なら application に置いて負債に記録する。
  **`utils/` を作らない**（作ると全部そこへ流れ込み、層の意味が消える）
