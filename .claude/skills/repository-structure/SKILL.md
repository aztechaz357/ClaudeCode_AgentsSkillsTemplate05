# リポジトリ構造・配置スキル

クリーンアーキテクチャに基づく **新規ファイルの置き場所を正しく決める**
ためのガイドです。構造の正式な定義は現状設計書とプロファイルの
「ディレクトリ構成」節を参照（このスキルはその早見表であり、
矛盾があれば設計書とプロファイルが勝つ）。

## 配置の決め方（判定フロー）

新しいコードを書くとき、上から順に問う。 **最初に該当した層に置く** 。

1. **標準ライブラリ以外に依存しない契約（インタフェース）・値・純粋関数か？**
   → domain
2. **domain の契約だけを使って進行を組み立てるユースケースか？**
   → application
3. **契約の具体実装か？（外部 I/O・OS・プロセス・DB・状態ホルダ）**
   → infrastructure / {機能グループ}
4. **UI・入出力・表示・対話か？**
   → presentation
5. **生成と注入の配線・設定か？**
   → Composition Root

判定に迷う典型例:

- **対話が必要なコンポーネント**（ユーザー入力を取る実装）は presentation。
  I/O が無いものは infrastructure
- **出力に書かないデコレータ** は infrastructure、
  **出力に書くデコレータ** は presentation
- **共有状態ホルダ** は infrastructure（契約は domain）
- **どの層にも属さない気がするもの**: たいてい設計の問題。設計書に戻って
  レイヤー配置表を書き直す。「とりあえず utils/」は作らない

## テストの配置

- テストルートはソースの層構成をミラーする
- 層に属さないテスト: アーキテクチャテスト（依存ルールの機械検証）・
  設定・Composition Root のテスト
- 統合テストは専用ディレクトリに分ける（プロファイルの「統合テスト配置」）
- 新しい層ディレクトリを作ることは原則ない（作る判断は設計変更 =
  設計書とユーザー確認が先）

## 命名規則

- モジュール・ファイル名: プロファイルの言語慣習に従う
- infrastructure は機能グループのサブディレクトリに置く
  （1ファイルだけでもグループ化）
- 契約・状態ホルダ・デコレータの命名は development-guidelines スキルの
  命名規則に従う

## ディレクトリを増やすときの手順

1. 設計書の「位置づけ（レイヤー配置）」表に新ディレクトリを明記する
2. 実装時にテスト側にも同名ディレクトリを作る（ミラー維持）
3. 実装完了時に該当層の現状設計書と `./template.md`
   （構造スナップショット）を更新する

## 現在の構造スナップショット

./template.md にディレクトリツリーを記載（構造変更時に更新すること）。
実物と食い違っていたら実物が正（Glob で確認して template.md を直す）。
