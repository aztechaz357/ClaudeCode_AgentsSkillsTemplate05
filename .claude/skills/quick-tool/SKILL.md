# ツールをサクッと作る（quick-tool）

工房レーン（`workshop/tools/<name>/`）にツールを 1 本追加する手順。
レーンの定義・置き場所・status・昇格判断は `workshop` スキルを正とする。

**この手順で作らないもの**: 要求仕様書・設計書・作業計画（`.steering/`）・
層構成・統合テスト・全体像の同期。これらは本開発レーン（`/add-feature`）
の工程であり、思いつきのツールには重すぎる。

**それでも省かないもの**: テスト先行と README の実行例。
理由は `workshop` スキルの「工房レーンで省くのは前工程と構造であって、
テストではない」を参照。

## 手順

### 0. 重複を確認する（30 秒）

```
powershell -File .claude/tools/index_workshop.ps1 -Check
```

`workshop/CATALOG.md` を読み、同じことをするツールが既に無いか見る。
あれば **新しく作らず、既存のツールに引数を足す** 。

### 1. 一言で書けるか確かめる

作る前に、`summary` に入る **1 行** を先に書く。

- 良い例: 「2つの CSV の差分を行単位で出す」
- 悪い例: 「CSV を色々と便利に扱う」 —— 1 行にならないものは範囲が広すぎる。
  **今まさに困っている 1 つの用途** まで絞る

絞れないときは、ツールではなくノート（`/note`）で考えを整理してから戻る。

### 2. 雛形を作る

```
powershell -File .claude/tools/new_tool.ps1 -Name <kebab-name> -Summary <1行> -Lang <py|ps1|sh> -Tags "a,b"
```

`README.md` / `main.<ext>` / `test_main.<ext>` の 3 点が生成される。
既に同名があれば終了コード 1 で拒否される（上書きしない）。

`-Lang` の既定は `py`。プロファイルの主言語に合わせて選ぶ。

### 3. テストを先に書く（Red を確認する）

雛形のテストは「未実装だから落ちる」だけの仮の Red。
**これを、実際に欲しい振る舞いのテストへ置き換える** 。

- 最初は **1 ケースだけ** 。一番典型的な入力と期待出力
- テスト docstring には 4 項目（テスト対象・入力・期待値・理由）を書く
- 書いたらテストを実行し、 **落ちることを目で確認する**
  （通ってしまったら、テストが何も検証していない）

```
<プロファイルのテスト（範囲指定）コマンド> workshop/tools/<name>/
```

### 4. 実装して通す（Green）

そのテストを通す **最小限** を書く。先回りの汎用化をしない。
オプションは「今この瞬間に必要なもの」だけ足す。

### 5. 落とし穴を 1 ケース足す

典型ケースが通ったら、 **失敗させてみる** 。空入力・ファイルが無い・
文字コードが違う・引数が足りない —— 実際に踏みそうなものを 1 つ選び、
テストを足して期待どおりの失敗になることを確認する。

工房のツールでも「静かに間違った答えを返す」のが一番損害が大きい。

### 6. README を実際に動かしながら書く

`README.md` の各節を埋める。 **実行例の出力は必ず実際に動かして貼る** 。

- 「2. 最小の実行例」: コピーして貼れば動く最短の呼び出しと、その実出力
- 「3. 引数」: 表を埋める。物理量には単位を書く
- 「4. 落とし穴」: 手順 5 で踏んだものをそのまま書く
- front matter の `status` を `draft` から `working` へ上げる
- `updated` を今日の日付にする

書式の詳細は `writing-conventions` スキルの `guides/manual.md`（工房簡易版）。

### 7. カタログへ登録する

```
powershell -File .claude/tools/index_workshop.ps1
```

`workshop/CATALOG.md` に行が増えたことを確認する。

### 8. コミットする

ツール 1 本 = 1 コミット。

```
実装: <name>（<summary>）を工房に追加

- workshop/tools/<name>/ に実装・テスト・README を追加
- テスト: <件数> passed（Red → Green 確認済み）
- 実行例の出力は実機で確認して README に貼付
- CATALOG.md を再生成
```

## 完了チェックリスト

- [ ] `summary` が 1 行で書けている
- [ ] テストを先に書き、落ちることを確認してから実装した
- [ ] 典型ケース + 失敗ケースの最低 2 ケースがある
- [ ] テスト docstring に 4 項目を書いた
- [ ] README の実行例を **実際に動かして** 出力を貼った
- [ ] `status` を `working` にし、`updated` を今日にした
- [ ] `index_workshop.ps1` を実行し、CATALOG.md に載った
- [ ] コミットした

## やりすぎのサイン

作っている途中で次のどれかに気づいたら、手を止めて `workshop` スキルの
「昇格の判断」を読む。工房で続けるべきでない可能性が高い。

- ファイルを 2 つ以上に分けたくなった
- 他のツールの関数を import したくなった
- 設定ファイル・DB・永続状態を持たせたくなった
- 「将来こう拡張できるように」と考え始めた

## `.claude/tools/` との違い

同じ「ツール」でも置き場所が 2 つある。混同しない。

| | `workshop/tools/` | `.claude/tools/` |
|---|---|---|
| 目的 | 自分の作業を助ける道具 | **開発プロセス自体** を機械化する道具 |
| 使う人 | ユーザー | エージェント（規約の機械検証など） |
| 作る手順 | このスキル | `tool-authoring` スキル |
| 判断基準 | 思いついたら作ってよい | 反復性・決定論性・事故実績の 3 つを満たすとき |

開発プロセスを決定論化する道具（検証スクリプト・生成スクリプト）は
`tool-authoring` へ。工房で作ったツールが後者だと分かったら、
`/promote` ではなく `.claude/tools/` へ移す。
