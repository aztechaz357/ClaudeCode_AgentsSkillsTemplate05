# Steering スキル

ステアリングファイル（`.steering/`）に基づいた実装を支援し、tasklist.md の
進捗管理を確実に行うスキルです。 **設計そのものは書きません** —— 設計の正は
`docs/design/proposals/P##-<name>.md` であり、steering は「その設計書を
どの順で実装するか」の作業管理を担います。

`.steering/` は **エージェント間の唯一の情報共有手段** であり、同時に
「環境・行動・知覚の記録」でもあります。コンテキストが圧縮されても、
セッションが切れても、ここを読めば同じ位置から再開できる状態を保ちます。

## 前提

- `.steering/` は gitignore 対象（ローカルの作業メモ。コミットしない）
- ディレクトリ名: `.steering/[YYYYMMDD]-[P##-機能名]/`
  （例: `.steering/20260719-P03-user-auth/`）
- ファイル構成（構造化ノート）:

```text
.steering/[YYYYMMDD]-[P##-機能名]/
     ├── requirements.md      # 要求内容（docs/requirements/P##-*.md からの作業向け抜粋）
     ├── design.md            # 設計書への参照と実装中の判断メモ
     ├── tasklist.md          # タスクリスト（進捗の正）
     ├── blockers.md          # （必要時）ブロッカーの記録
     ├── decisions.md         # （必要時）重要な決定事項の記録
     └── reports/             # サブエージェントのレポート置き場
          └── [NN]-[エージェント名].md
```

- 必須は最初の 3 ファイル。blockers.md / decisions.md は発生時に作成し、
  日付付きで追記していく（テンプレートは `./templates/`）
- タスクの粒度は **マイクロコミット単位** 。1タスク = テスト作成 → Red 確認 →
  実装 → Green 確認 → コミット、まで

## レポート駆動（サブエージェントとの情報共有）

エージェント間でコンテキストは共有されない。サブエージェント
（`.claude/agents/` 配下）との情報共有は、この steering ディレクトリの
構造化ノートを介して行う:

- **起動時**: プロンプトに steering ディレクトリのパスを必ず含める。
  サブエージェントは共通プロトコル（`.claude/agents/report-protocol.md`）に
  従い、ノートを読んでコンテキストを回復してから作業する
- **受領時**: サブエージェントの応答は「レポートパス + 要約」だけ。
  要約で足りるならレポート本文は読まない（親のコンテキスト節約）。
  対処が必要なときだけ該当レポートを読む
- **決定・ブロッカー**: 自分（親）が重要な決定をしたら decisions.md に、
  作業を止める問題は blockers.md に日付付きで追記する。コンテキスト圧縮で
  失われてはいけない情報は、会話ではなくノートに置く

## モード1: 作業計画（ステアリングファイル作成）

1. 参照文書を読む: `CLAUDE.md`（プロジェクトプロファイル含む）→
   該当の要求仕様書（`docs/requirements/P##-*.md`）→ 該当の設計書
   （`docs/design/proposals/P##-*.md`。無ければ先に functional-design スキルで作成）
2. `./templates/` の3テンプレートを読み、プレースホルダーを具体化して
   `.steering/[日付]-[P##-機能名]/` に3ファイルを作成する
3. tasklist.md は設計書の「テスト観点」を出発点に、
   マイクロコミット1回分ずつのタスクへ分解する
   - 各タスクに対象ファイル（テスト側とソース側）を明記
   - 実装の順序は設計書の依存関係に従う
   - 末尾に統合テスト（要求仕様書の受け入れ条件 → integration-tester）の
     タスクを必ず置く

## モード2: 実装（最重要）

### 原則（MUST / NEVER）

**MUST**:
- タスク完了のたびに Edit で tasklist.md の `[ ]` → `[x]` をリアルタイム更新する
- 各タスクは TDD で進める（テスト先行・Red 確認 → 実装 → 全緑確認）
- 全緑を確認してからコミットする（プロファイルのコミット規約）
- 全タスクが `[x]` になるまで作業を継続する

**NEVER**:
- tasklist.md を見ずに実装を進める（TodoWrite は補助。tasklist.md が正式）
- 複数タスクをまとめて更新する
- 「時間の都合」「難しいから後で」を理由にタスクをスキップする
- 未完了タスク（`[ ]`）を残したまま振り返りを書く

### タスクが大きすぎる場合

タスクを小さなサブタスクに分割して tasklist.md に追記し、1つずつ完了させる。

### 技術的理由によるスキップ（唯一の例外）

実装方針・アーキテクチャ・依存関係の変更でタスク自体が不要になった場合のみ、
`- [x] ~~タスク名~~（不要: 具体的な技術的理由）` の形式でスキップできる。
理由は振り返りにも記録する。

### 設計と実装が矛盾したら

設計書と実装が食い違う判断が必要になったら、 **作業を止めてユーザーに
確認する**（勝手にどちらかへ合わせない）。確認結果は design.md の判断メモと
設計書の修正に反映してから再開する。

### 実装フロー

1. tasklist.md を読み、先頭の未完了タスクを特定
2. テストを書き、失敗（Red）を確認
3. 実装し、プロファイルのテストコマンドで全緑（Green）を確認
4. コミット（1タスク = 1コミット）
5. Edit で tasklist.md の該当タスクを `[x]` に更新
6. 1 に戻る（未完了タスクが無くなるまで）

## モード3: 振り返り（プロセス改善の入口）

全タスク完了後、tasklist.md の「実装後の振り返り」セクションに記録する:

- 実装完了日 / 計画と実績の差分 / テスト結果 / 学んだこと
- **プロセス改善提案**: 今回の `reports/` の知覚・行動ログを読み返し、
  次のいずれかに該当する事象があれば具体的に書く。これがエージェント・
  スキル・ツールを育てる材料になる:
  - 同じ手作業を 2 回以上繰り返した → **ツール化の候補**（tool-authoring）
  - エージェントが判断に迷った・手戻りした → **定義の曖昧さ**（該当
    エージェント定義またはスキルの手順を具体化する）
  - LLM に考えさせすぎた箇所 → **決定論化の候補**（チェックリスト・
    テンプレート・機械検証への置き換え）
  - プロファイルに無くて推測した項目 → **CLAUDE.md プロファイルの不足**
- ここで出た設計変更は、現状設計書・設計書への反映漏れがないか併せて確認する
  （反映は architecture-design スキルの領分）

## セルフチェック（5タスクごと）

- [ ] tasklist.md の更新が実装に追随しているか
- [ ] コミット漏れのタスクがないか（1タスク = 1コミット）
- [ ] ユーザーが tasklist.md を見て進捗を把握できるか
