# Steering スキル（役割間の受け渡しと作業ノート）

`.steering/` は **役割エージェント間の唯一の情報共有手段** であり、
同時に「環境・行動・知覚の記録」でもある。

## いつ作るか: 反復ごとに必ず作る

8 点セットは 8 つの役割で回す。役割の間でコンテキストは共有されないので、
受け渡しの場所が要る。 **薄い反復でも作る** （以前の「薄い反復では作らない」
は廃止した —— 役割を分けた時点で、受け渡しの記録が無いと前の役の判断が
次の役に届かなくなるため）。

| 状況 | `.steering/` |
|---|---|
| 反復（`/iterate`） | **作る** |
| 骨組み（`/skeleton`） | **作る** |
| 厚い経路（`/add-feature`） | **作る**（tasklist で実装ループを管理する） |
| リファクタリング（`/refactor`） | **作る** |
| 工房レーン（`/tool` `/note`） | 作らない（成果物と git 履歴が記録） |

**進捗の正は常に `docs/backlog.md`** 。`.steering/` はローカルの作業メモで、
gitignore 対象（コミットしない）。反復が終われば捨ててよい。
食い違ったら **バックログが正** 。

## 構成

ディレクトリ名: `.steering/[YYYYMMDD]-[S##-機能名]/`
（例: `.steering/20260806-S03-csv-filter/`）

```text
.steering/[YYYYMMDD]-[S##-機能名]/
     ├── tasklist.md          # 8 点セットのチェックリスト（必須）
     ├── INDEX.md             # 誰が何をしたかの 1 行ログ（必須・追記のみ）
     ├── decisions.md         # （必要時）重要な決定事項
     ├── blockers.md          # （必要時）ブロッカー
     ├── intake/              # （伴走のみ）ユーザーが自分で書く用紙
     │    ├── S##-要求.md     #   段1 用（正: intake スキル）
     │    └── S##-設計.md     #   段2 用
     └── reports/             # 役割ごとのレポート
          └── [NN]-[エージェント名].md
```

- **必須は tasklist.md と INDEX.md の 2 枚** 。要求・設計を写した中間
  ファイルは作らない（正は `docs/` にある。写すとドリフトして事故になる）
- `intake/` は例外だが、写しではない —— **正式文書がまだ無い段階で、
  その材料をユーザーから受け取る器** （向きが逆）。
  `docs/` へ落とし切った時点で `> **取り込み済み**` を書いて閉じ、
  以降は読まない（正が 2 か所になった瞬間にドリフトが始まる）
- decisions.md / blockers.md は発生時に作成し、日付付きで追記する
  （テンプレートは `./templates/`）

## 受け渡しの順序（この順に動かす）

各役は **前の役のレポートを読んでから** 始める。

| 段 | 役割 | 読むもの | 作る成果物 | 書くレポート |
|---|---|---|---|---|
| 1 | `requirement-writer` | backlog・concept | 要求仕様書 | `01-requirement-writer.md` |
| 2 | `designer` | 01・要求 HTML | 設計書 | `02-designer.md` |
| 3 | `unit-tester` | 01・02 | 単体テスト（**Red 確認まで**） | `03-unit-tester.md` |
| 4 | `coder` | 02・03 | 実装（Green まで） | `04-coder.md` |
| 5 | `integration-tester` | 01・04 | 統合テスト | `05-integration-tester.md` |
| 6 | `test-summarizer` | 03・04・05 | テスト結果まとめ | `06-test-summarizer.md` |
| 7 | `manual-writer` | 01・06 | マニュアルの節 | `07-manual-writer.md` |
| 8 | `implementation-validator` → `doc-syncer` | すべて | 判定・記録の同期 | `08-*.md` / `09-doc-syncer.md` |

**委譲するかは規模で決めてよい。ただし委譲しなくても同じレポートを残す。**
誰がやったかにかかわらず、受け渡しの形は変えない
（形が変わると、次の反復で委譲したときに前提が崩れる）。

## 起動プロンプトに必ず書く 5 つ

サブエージェントを起動するとき、次を **省略しない** 。

1. `.steering/` 作業ディレクトリのパス
2. 対象スライスと **目標成熟度**（例: 「S03、現在 L1、目標 L2」）
3. **関与モード**（例: 「関与モード: 伴走」。`CLAUDE.md` の
   「関与モード」節が正。反復の引数 `--伴走` があればそれが優先）
4. 読むべき前の役のレポートパス
5. 期待するレポートパス（`reports/NN-<name>.md`）と
   「応答はレポートパスと 5 行以内の要約のみ」

**目標成熟度を書き忘れると、エージェントは最上位の基準で判定し、
完璧の積み上げが始まる。** これが最も多い事故。

**関与モードを書き忘れると、エージェントは決めてから説明する。**
成果物は出るが、ユーザーに判断の経験が積まれない
（`伴走` を選んでいるのに置いてけぼりになる原因はほぼこれ）。

受領時は「レポートパス + 要約」だけを見る。要約で足りるなら本文は読まない
（親のコンテキスト節約）。対処が必要なときだけ読む。

## INDEX.md（追記のみ・1 行 1 行動）

**ユーザーが後から追える履歴** 。各役は自分の作業を終えたら 1 行足す。

```markdown
# S03 反復ログ

| 時刻 | 段 | 誰が | 何をした | 触ったもの |
|---|---|---|---|---|
| 10:12 | 1 | requirement-writer | 要求 1・仕様 3 条を書いた | docs/usdm/src/S03-filter.html |
| 10:31 | 2 | designer | 契約 CsvReader を切ると決めた | docs/design/S03-filter.md |
| 10:58 | 3 | unit-tester | Red 3 件を確認 | test/application/test_filter.py |
```

**書き換えない。追記だけ。** 途中で方針が変わったら、変わったことを
新しい行として足す（消すと経緯が消える）。

## ユーザーへの節目報告（3 か所だけ）

エージェントに任せるとユーザーが大枠を見失う。 **承認は求めず、
短い要約だけを出す** 。止まらないので速度は落ちない。

| 節目 | 出すもの |
|---|---|
| 段 1 の後（要求が固まった） | 要求 1 行・理由 1 行・仕様の数 |
| 段 2 の後（設計が固まった） | 層と契約の要点 1 行 ＋ **却下した案 1 行** |
| 段 8 の後（全緑・記録済み） | 5 行サマリ（`/status` と同じ形） |

```
[段2完了] S03 設計: application に CsvReader 契約を 1 本置いて注入する
          他案: infrastructure を直接呼ぶ（テストが遅くなるため却下）
```

**ユーザーが止めたいときに止められる形** にするのが目的。
返事を待たずに次の段へ進む（`.steering/local-mode.md` があるときを除く）。

## モード1: 作業計画（tasklist.md）

反復の最初に `./templates/tasklist.md` を写して置く。
既定の中身は **8 点セットのチェックリスト** で、行は増やさない。
厚い経路（`/add-feature`）だけ、段 3〜4 をマイクロコミット単位に分解する。

- 各タスクに対象ファイル（テスト側とソース側）を明記する
- 完了のたびに `[ ]` → `[x]` に **リアルタイム更新** する
  （まとめて更新しない）

## モード2: 実装

### 原則（MUST / NEVER）

**MUST**:
- 段の順序を守る（要求 → 設計 → 単体テスト(Red) → 実装 → 統合 → まとめ → マニュアル）
- 各タスクは TDD で進める（テスト先行・Red 確認 → 実装 → 全緑確認）
- 全緑を確認してからコミットする（プロファイルのコミット規約）
- **目標成熟度の範囲内で作業する**（`agile-process/maturity.md`）
- 自分の段が終わったら INDEX.md に 1 行足す

**NEVER**:
- 目標より上のレベルの作業（L1 で失敗経路を網羅する・文書を整える）
- **8 点のうち 1 つを次の反復へ送る**（送ったものは二度と書かれない）
- 実装を先に書き、後から要求・設計を書き写す
- 複数タスクをまとめて更新する
- 「時間の都合」「難しいから後で」を理由にタスクをスキップする
- 手抜きを記録せずに残す

### タスクが大きすぎる場合

サブタスクに分割して tasklist.md に追記し、1 つずつ完了させる。
分割しても半日を超えるなら、 **スライスの切り方が大きすぎる** ので
`docs/backlog.md` でスライスを分割する。

### 技術的理由によるスキップ（唯一の例外）

方針・依存関係の変更でタスク自体が不要になった場合のみ、
`- [x] ~~タスク名~~（不要: 具体的な技術的理由）` の形式でスキップできる。
理由は振り返りにも記録する。 **8 点セットの成果物はこの例外に含まれない** 。

### 仕様と実装が矛盾したら

**作業を止めてユーザーに確認する** （勝手にどちらかへ合わせない）。
確認結果を要求 HTML または設計書に反映してから再開する。

## モード3: 振り返り（プロセス改善の入口）

反復の完了後に tasklist.md の末尾へ記録する。

- 実装完了日 / 計画と実績の差分 / テスト結果
- **反復にかかった時間**（半日を超えたなら、なぜ超えたか）
- **段ごとの所要**（どの段が重かったか。8 点のうち詰まるのはどこか）
- **プロセス改善提案**: 次のいずれかに該当する事象があれば具体的に書く:
  - 同じ手作業を 2 回以上繰り返した → **ツール化の候補**（tool-authoring）
  - エージェントが判断に迷った・手戻りした → **定義の曖昧さ**
  - LLM に考えさせすぎた箇所 → **決定論化の候補**
  - プロファイルに無くて推測した項目 → **プロファイルの不足**
  - 目標より上のレベルの作業をしてしまった → **成熟度の指示漏れ**
  - 成果物を 1 つ落としかけた → **段の飛ばし**（最も重い失敗）
  - スライスが半日で終わらなかった → **切り方の失敗**

最後の 3 つは、このプロセス特有の失敗パターン。優先して記録する。
