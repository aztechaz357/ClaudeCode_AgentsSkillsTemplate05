# Steering スキル（作業ノートとレポート交換）

`.steering/` は **サブエージェント間の唯一の情報共有手段** であり、
同時に「環境・行動・知覚の記録」でもあります。

## いつ作るか（作らないことが既定）

| 状況 | `.steering/` を作るか |
|---|---|
| 薄い反復（`/iterate`）を自分で完結させる | **作らない** 。スライス文書と `docs/backlog.md` で足りる |
| サブエージェントに委譲する | **作る**（レポートの受け渡しに必要） |
| 厚い経路（`/add-feature`） | **作る**（tasklist で実装ループを管理する） |
| リファクタリング（`/refactor`） | 委譲するなら作る。自分でやるなら不要 |

**進捗の正は常に `docs/backlog.md`** 。`.steering/` はローカルの作業メモで、
gitignore 対象（コミットしない）。反復が終われば捨ててよい。

`docs/backlog.md` と `.steering/` が食い違ったら **バックログが正** 。

## 構成

ディレクトリ名: `.steering/[YYYYMMDD]-[S##-機能名]/`
（例: `.steering/20260730-S03-csv-filter/`）

```text
.steering/[YYYYMMDD]-[S##-機能名]/
     ├── tasklist.md          # タスクと進捗（厚い経路では必須）
     ├── decisions.md         # （必要時）重要な決定事項
     ├── blockers.md          # （必要時）ブロッカー
     └── reports/             # サブエージェントのレポート置き場
          └── [NN]-[エージェント名].md
```

- **必須は tasklist.md だけ** （厚い経路のとき）。requirements.md / design.md は
  作らない —— 要求と設計の正はスライス文書（薄い経路）または
  `docs/requirements/` `docs/design/proposals/`（厚い経路）にある
- decisions.md / blockers.md は発生時に作成し、日付付きで追記する
  （テンプレートは `./templates/`）

## レポート駆動（サブエージェントとの情報共有）

エージェント間でコンテキストは共有されない。共有はこのディレクトリの
構造化ノートを介して行う。

- **起動時**: プロンプトに次を必ず含める:
  1. `.steering/` 作業ディレクトリのパス
  2. 対象スライスと **目標成熟度**（例: 「S03、現在 L1、目標 L2」）
  3. 期待するレポートパス（`reports/NN-<name>.md`）
  4. 「応答はレポートパスと 5 行以内の要約のみ」

  **目標成熟度を書き忘れると、エージェントは最上位の基準で判定し、
  完璧の積み上げが始まる。** これが最も多い事故。

- **受領時**: 応答は「レポートパス + 要約」だけ。要約で足りるなら本文は
  読まない（親のコンテキスト節約）。対処が必要なときだけ読む
- **決定・ブロッカー**: 自分が重要な決定をしたら decisions.md に、
  作業を止める問題は blockers.md に日付付きで追記する

## モード1: 作業計画（厚い経路のときだけ）

1. 参照文書を読む: `CLAUDE.md`（プロファイル）→ `agile-process/maturity.md` →
   `docs/requirements/S##-*.md` → `docs/design/proposals/S##-*.md`
2. `./templates/tasklist.md` を写して `.steering/[日付]-[S##-機能名]/` に置く
3. 設計書の「テスト観点」を出発点に、マイクロコミット 1 回分ずつのタスクへ分解する
   - 各タスクに対象ファイル（テスト側とソース側）を明記する
   - 末尾に E2E（受け入れ条件 → integration-tester）のタスクを必ず置く

薄い反復では **この工程を飛ばす** 。スライス文書の「薄い設計」が計画そのもの。

## モード2: 実装

### 原則（MUST / NEVER）

**MUST**:
- 各タスクは TDD で進める（テスト先行・Red 確認 → 実装 → 全緑確認）
- tasklist.md がある場合は、タスク完了のたびに `[ ]` → `[x]` を
  リアルタイム更新する
- 全緑を確認してからコミットする（プロファイルのコミット規約）
- **目標成熟度の範囲内で作業する**（`agile-process/maturity.md`）

**NEVER**:
- 目標より上のレベルの作業（L1 で層を切る・失敗経路を網羅する・文書を整える）
- 複数タスクをまとめて更新する
- 「時間の都合」「難しいから後で」を理由にタスクをスキップする
- 手抜きを記録せずに残す

### タスクが大きすぎる場合

サブタスクに分割して tasklist.md に追記し、1 つずつ完了させる。
分割しても半日を超えるなら、 **スライスの切り方が大きすぎる** ので
`docs/backlog.md` でスライスを分割する。

### 技術的理由によるスキップ（唯一の例外）

方針・依存関係の変更でタスク自体が不要になった場合のみ、
`- [x] ~~タスク名~~（不要: 具体的な技術的理由）` の形式でスキップできる。
理由は振り返りにも記録する。

### 受け入れ条件と実装が矛盾したら

**作業を止めてユーザーに確認する** （勝手にどちらかへ合わせない）。
確認結果はスライス文書（または設計書）の修正に反映してから再開する。

## モード3: 振り返り（プロセス改善の入口）

反復（または厚い経路）の完了後に記録する。tasklist.md があればその末尾、
無ければ `.steering/[日付]-retrospective.md` に書く。

- 実装完了日 / 計画と実績の差分 / テスト結果
- **反復にかかった時間**（半日を超えたなら、なぜ超えたか）
- **プロセス改善提案**: 次のいずれかに該当する事象があれば具体的に書く:
  - 同じ手作業を 2 回以上繰り返した → **ツール化の候補**（tool-authoring）
  - エージェントが判断に迷った・手戻りした → **定義の曖昧さ**
  - LLM に考えさせすぎた箇所 → **決定論化の候補**
  - プロファイルに無くて推測した項目 → **プロファイルの不足**
  - 目標より上のレベルの作業をしてしまった → **成熟度の指示漏れ**
  - スライスが半日で終わらなかった → **切り方の失敗**（分割基準を見直す）

最後の 2 つは、このプロセス特有の失敗パターン。優先して記録する。

## セルフチェック

- [ ] `docs/backlog.md` の成熟度が実態と一致しているか（バックログが正）
- [ ] tasklist.md の更新が実装に追随しているか（ある場合）
- [ ] コミット漏れのタスクがないか（1 タスク = 1 コミット）
- [ ] サブエージェントの起動プロンプトに目標成熟度を書いたか
- [ ] 残した手抜きを負債表に転記したか
