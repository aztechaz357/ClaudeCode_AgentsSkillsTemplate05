# 検証できる記録（verifiable-claims）

## 知見: 人はいつ「わかった」と感じるか

この規約の形は、次の 4 つの観察から決まっている。 **記法が目的ではない。**

### 1. 理解は、同意ではなく「反証の失敗」から生まれる

読んで頷いた内容は残らない。「これ、空リストのとき破れるのでは？」と疑い、
確かめ、破れなかった —— そのとき理解が定着する。
だから記録は **攻撃されうる形** で書く。散文は攻撃点が無いので、
読者は頷くしかなく、頷きは理解にならない。

→ **反例の形を必ず書く**（読者に攻撃の入口を渡す）。

### 2. 読まれないのは量のせいではなく、検証できないから

散文は 1 文ごとに「信じる」か「自分で再導出する」しか選択肢が無い。
どちらも高い。だから量が増えると読まれなくなる。
短くしても **信じる量が減るだけ** で、判断できるようにはならない。

→ **短い散文より、検証できる 1 行** 。

### 3. 人は「尽きている」と分かったときに安心する

「3 通りある」では落ち着かない。「3 通りで尽きている、4 つ目は無い」で落ち着く。
散文はこの網羅性を表現できない。記号はできる。

→ **場合分けを `⊔`（排他かつ網羅）で書く** 。

### 4. 散文は「壊れやすい区別」を 1 語に潰す

「フィルタする」は **健全性**（余計なものを出さない）と
**完全性**（取りこぼさない）を 1 語に潰す。実際のバグは
**片方だけ壊れる** ものが最も多いのに、散文では区別すら見えない。

→ **主張を 1 行 1 主張に割る** （潰さない）。

## 契約式の形（設計書に 1 節）

```markdown
## 主張（契約式）

| ID | 種別 | 主張 | assert | 状態 | 根拠 |
|---|---|---|---|---|---|
| P1 | 事前 | `pred` は全域関数 | `assert callable(pred)` | ⊢ | `test_pred_callable` |
| Q1 | 事後 | `∀r ∈ out. r ∈ in ∧ pred(r)` | `assert all(r in inp and pred(r) for r in out)` | ⊢ | `test_only_matching` |
| Q2 | 事後 | `∀r ∈ in. pred(r) → r ∈ out` | `assert all(r in out for r in inp if pred(r))` | ⊬ | 未（D02） |
| I1 | 不変 | `\|out\| ≤ \|in\|` | `assert len(out) <= len(inp)` | ⊬ | 未 |

**場合**: `in = ∅ ⊔ 全通過 ⊔ 一部通過 ⊔ 全落ち`（`⊔` は排他かつ網羅）

**反例**: Q2 が破れるなら —— `pred(r)` が真なのに `out` に無い `r` が 1 つ
```

**表の列と順序を変えない。** `build_claims.py` がこの形で読む。

### ID は 3 種だけ

| 接頭辞 | 種別 | 何を言うか |
|---|---|---|
| `P#` | 事前 | 呼ぶ側が守るべきこと（破ったら呼ぶ側の責任） |
| `Q#` | 事後 | 呼ばれた側が保証すること（破ったらこちらのバグ） |
| `I#` | 不変 | 前後で変わらないこと |

増やさない。3 種で足りないと感じたら、スライスが大きすぎる。

## 記法（小さな固定語彙・1 行・assert 併記）

**使ってよい記号はこれだけ。** 学習コストを 1 つの表に収める。

| 記号 | 読み | 例 |
|---|---|---|
| `∀x ∈ S.` | S のすべての x について | `∀r ∈ out. pred(r)` |
| `∃x ∈ S.` | S のある x について | `∃r ∈ in. ¬pred(r)` |
| `∈` `∉` | 含まれる / 含まれない | `r ∈ out` |
| `→` | ならば | `pred(r) → r ∈ out` |
| `∧` `∨` `¬` | かつ / または / でない | `a ∧ ¬b` |
| `≤` `<` `=` `≠` | 大小・等値 | `\|out\| ≤ \|in\|` |
| `∅` | 空 | `in = ∅` |
| `⊔` | 排他かつ網羅な場合分け | `A ⊔ B ⊔ C` |
| `⊢` `⊬` | 証明済み / 未証明 | 状態列 |
| `\|S\|` | 要素数 | `\|out\|` |

3 つの制約を守る。

1. **1 主張 1 行** —— 折り返したら 2 つの主張が混ざっている。割る
2. **量化子の入れ子は 1 段まで** —— 2 段必要なら仕様が複雑すぎる
3. **assert を必ず併記する** —— 記号が読めない人・読む気力が無い日でも
   意味が取れる。 **式と assert が食い違ったら assert が正**
   （動かせるほうを信じる）

## 証明状態（`⊢` / `⊬`）と成熟度

**`⊬` は「主張しているが未証明」。これがそのまま負債。**

| 目標 | 条件 | 判定 |
|---|---|---|
| L1 動く | 主経路の事後条件が **1 本以上 `⊢`** | 機械 |
| L2 固い | **事後条件が全部 `⊢`** ＋ 場合分けが `⊔` で閉じている | 機械 |
| L3 整った | **`⊬` が 0 件**（不変条件も証明済み） | 機械 |

成熟度が判断ではなく **数え上げ** になる。これが最大の効き目
（「L2 と言っていいか」で悩む時間が消える）。

`⊬` の主張は `docs/backlog.md` の負債表にも 1 行足す
（負債 ID を根拠列に書いて対応付ける）。

## 書く場所は分散、読む場所は 1 枚

主張を 7 点セットに散らしたままだと、追いつけない問題は解けない。
**書くのは設計書、読むのはツールが集めた 1 枚。**

| | どこ | 誰が |
|---|---|---|
| 書く | `docs/design/S##-*.md` の「## 主張（契約式）」 | `designer`（段2） |
| 証明する | テストを書き、根拠列にテスト名を入れて `⊬` → `⊢` | `unit-tester`・`test-summarizer` |
| 一覧で読む | `/status`（`build_claims.py`） | 人 |
| 差分で読む | `/catchup`（`build_claims.py --diff`） | 人 |

```
<ツール実行コマンド> .claude/tools/build_claims.py            # 台帳
<ツール実行コマンド> .claude/tools/build_claims.py --diff     # 既読地点からの差分
<ツール実行コマンド> .claude/tools/build_claims.py --mark     # いまを既読にする
```

### 差分が本体（追いつくための道具）

席を外した後に要るのは「何が書かれたか」ではなく
**「いま何が保証されていて、それがどう変わったか」** 。

```
弱まった保証（⊢ → ⊬。最優先で見る）: 1 件
  ⊬ S03.Q1 ∀r ∈ out. r ∈ in ∧ pred(r)   … 未
追加された保証: 1 件
  ⊢ S04.Q1 ∀x. sum(x) = Σx
未証明のまま（据え置き。変化ではないが放置の指標）: 1 件
  ⊬ S03.I1 |out| ≤ |in|   … 未
```

**`⊢` → `⊬` の後退と、主張が消えたことは、散文の差分では絶対に気づけない。**
行が増えたことには気づけても、保証が減ったことには気づけないため。
ここを機械で見せるのがこのツールの存在理由。

`未証明のまま` は **変化ではないので差分の件数に数えない**
（据え置きを差分と呼ぶと毎回赤が出て、差分そのものが読まれなくなる）。

## やってはいけないこと

- **反例を書かない** —— 攻撃点が無い主張は検証できず、散文に戻る
- **`⊢` を根拠（テスト名）なしで書く** —— 証明済みの嘘は無いより悪い
- 記号を語彙表の外から持ち込む（時相論理・型付け・入れ子の量化子）
- **1 行に 2 つの主張を詰める**（健全性と完全性を潰すのが典型）
- assert を省く（記号が読めない日には読まれなくなる）
- **台帳（`/status` の出力）を文書として保存する** ——
  正は設計書。集めたものを書き写すと二重管理になる
- 主張を黙って消す（消えたことは差分に出る。消すなら理由を設計書に残す）
- 散文の説明を式の **代わり** に書く（式の下に足すのはよい）
