# ゴール定義スキル（concept-definition）

`docs/concept.md` は **「なぜ作るか・何ができたら終わりか・何を捨てるか」**
の正。反復開発の出発点であり、迷ったときに立ち返る場所です。

```
ゴールと完走の定義（この文書）→ バックログ → 骨組み → 反復
docs/concept.md                docs/backlog.md
```

## 最初に埋めるのは 2 つだけ

**この文書を全部埋めてから開発を始めない。** 着手に必要なのは次の 2 つ。

| 節 | なぜ最初に必要か |
|---|---|
| **一行で言うと** | ゴールがぶれると反復の方向がぶれる |
| **完走の定義** | 骨組みが決まらないと `/skeleton` が始まらない |

残り（非目標・割り切り・脅威モデル）は、それが必要になった反復で埋める。
埋まっていない節は「未定（{いつ決めるか}）」と書いておく
（空欄はエージェントが推測を始める原因になる）。

## 完走の定義（最重要）

**「何ができたら、このプロジェクトは通ったと言えるか」を 1 文で書く。**

```
完走の定義: `<コマンド・操作>` を実行すると、<入力> から <観測できる出力> が出る
```

条件:

- [ ] 入口と出口が具体的（コマンド名・出力の形が書かれている）
- [ ] **その場で実行して確かめられる**（E2E テストに翻訳できる）
- [ ] 品質・網羅・性能の要求が入っていない（それは成熟度 L2・L3 の話）

**悪い例**（実行して確かめられない）:

```
完走の定義: 使いやすく高速な CSV 集計ツールが完成すること
```

**良い例**（骨組みがそのまま決まる）:

```
完走の定義: `tool count data.csv` を実行すると、データ行数が `N 行` の形で
標準出力に出る
```

この 1 文がそのまま `docs/backlog.md` の「完走の定義」と S01（骨組み）になり、
最初の E2E テストになります。

## 出力先

```
docs/concept.md   （プロジェクトに 1 つ）
```

プロファイルの「ドキュメント構成」表に沿う。パスが違うプロジェクトでは
表のほうを正とする。

## 他文書との分担（重複させない）

| 文書 | 持つもの | 持たないもの |
|---|---|---|
| **この文書** | なぜ作るか・完走の定義・非目標・割り切り・脅威モデル | 進捗・成熟度・受け入れ条件・設計 |
| `docs/backlog.md` | スライスの優先順位・成熟度・負債 | 理由・ゴールの根拠 |
| `docs/slices/S##-*.md` | 受け入れ条件・薄い設計・実績 | 製品全体の方針 |

同じことを 2 か所に書かない。 **この文書に進捗を書くと必ず腐る。**

## 進め方

1. **知覚**: ユーザーの要望、既存の `README`・`CLAUDE.md`・元資料
   （凍結文書があればそれ）を読む。既に動いているコードがあるなら実物の
   機能も確認する（「作るつもり」と「もうある」を混同しない）
2. **完走の定義を確定させる**: 上の条件を満たす 1 文にする。
   書けないなら典型シナリオが具体的でないので、AskUserQuestion で
   「どのコマンドで何が出れば通ったと言えるか」を聞く
3. **薄く埋める**: `./template.md` の残りは分かる範囲で埋め、
   分からない節は「未定（{いつ決めるか}）」にする
4. **出力**: `docs/concept.md` を書き、続けて `/backlog init` で
   スライスに割る。コミット接頭辞は `docs:`

## 書き方の要点

### 非目標と割り切りは「膨らんできたら」書く

反復開発ではスコープの膨張はバックログで止められます
（「今回のゴールの外」表）。したがってこの文書の非目標は、
**同じ要望を 2 回断ったときに書けば十分** 。最初から完璧に列挙しようとすると、
ここで日が暮れます。

書くときは捨てたものが分かる形にする:

```markdown
| 捨てるもの | 得るもの | 見直す条件 |
|---|---|---|
| 汎用性（他分野への転用） | 中核アルゴリズムが読める単純さ | 別分野の要求が 2 件出たとき |
```

### 脅威モデルは「守らないもの」まで書く

プロファイルの「安全機構」節と `security-checker` の検査範囲は、ここを
根拠に決まります。「悪意ある第三者は対象外（ローカル専用のため）」と
明記されていれば、過剰な防御を作らずに済みます。
ローカル専用の個人ツールなら **1 行で足ります** 。

### スライスの当たりは 3〜8 本

典型シナリオを縦切り（入口から出口まで通る単位）に割った当たりを書く。
状態・成熟度は `docs/backlog.md` が正なので、ここには **ねらいと順序の理由**
だけを書く。8 本を超えるならゴールが大きすぎるので分割を提案する。

### 図・数式

必要になるまで書かない。書く場合は `writing-conventions` の作図言語
（迷ったら Mermaid）で、番号とキャプションを付けて本文から参照し、
図・番号の検証ツールを実行する。

## 更新のルール

- **反復ごとには更新しない** 。ここが動くのは方針が変わったときだけ
- 更新したら冒頭の「最終更新」に **日付と更新理由** を書く
- **完走の定義を変えるときは必ずユーザーに確認する**
  （ゴールの変更であり、バックログの並びが変わる）
- 実装がゴールと矛盾したら、勝手にどちらかへ寄せない（絶対ルール 3）

## 品質チェック（作成後）

- [ ] 一行要約が専門用語なしで読めるか
- [ ] **完走の定義が実行して確かめられる形か**（E2E に翻訳できるか）
- [ ] 完走の定義に品質・網羅・性能の要求が混ざっていないか
- [ ] 埋まっていない節が「未定（いつ決めるか）」になっているか（空欄でないか）
- [ ] 進捗・成熟度・受け入れ条件・設計を書き込んでいないか（役割の重複）
- [ ] スライスの当たりが 3〜8 本か
