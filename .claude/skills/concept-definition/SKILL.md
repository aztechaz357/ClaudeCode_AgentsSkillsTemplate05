# 全体構想スキル（concept-definition）

開発プロセスの **工程0** 。要求仕様書より上位の文書で、
「なぜ作るか・何を捨てるか」を確定させます。

```
全体構想 → 要求仕様書 → 設計書 → TDD 実装 → 統合テスト
（この文書）  （P## ごと）
```

全体構想が無いまま P01 を始めると、フェーズごとにスコープが揺れ、
「これは今回やるべきか」の判断が毎回ゼロから発生します。
**この文書の役割は、後続の全工程で判断を早くすること** です。

## 出力先

```
docs/concept.md   （プロジェクトに 1 つ）
```

`CLAUDE.md` プロファイルの「ドキュメント構成」表に沿う。パスが違う
プロジェクトでは表のほうを正とする。

## 他文書との分担（重複させない）

| 文書 | 持つもの | 持たないもの |
|---|---|---|
| **全体構想** | なぜ作るか・非目標・割り切り・脅威モデル・フェーズの順序と理由 | 進捗・受け入れ条件・クラス設計 |
| ロードマップ表 | フェーズの状態（📝/🔧/✅） | 理由 |
| 要求仕様書 | フェーズごとの受け入れ条件 | 製品全体の方針 |
| 設計書 | 実装方式・却下案 | 製品全体の方針 |

同じことを 2 か所に書かない。全体構想に進捗を書くと必ず腐る。

## 進め方

1. **知覚**: ユーザーの要望、既存の `README`・`CLAUDE.md`・元資料
   （凍結文書があればそれ）を読む。既に動いているコードがあるなら
   実物の機能も確認する（「作るつもり」と「もうある」を混同しない）
2. **構造化**: `./template.md` の見出しに沿って埋める
3. **確認**: 埋まらない項目は **推測せず AskUserQuestion で聞く** 。
   特に次の 3 つは後工程すべてに効くので、曖昧なまま進めない:
   - **非目標**（やらないこと）
   - **割り切り**（何を捨てて何を取るか）
   - **脅威モデル**（誰から何を守るか / 守らないか）
4. **出力**: `docs/concept.md` を書き、フェーズ計画の行を
   ロードマップ表にも「🕐 候補・未着手」として反映してコミットする
   （コミット接頭辞は `docs:`）

## 書き方の要点

### 非目標と割り切りが本体

目標だけの構想文書は役に立ちません。 **書いた人が何を捨てたか** が
分かるから、後で判断できます。

**悪い例**（何も決まっていない）:

```markdown
- 使いやすく、拡張性が高く、高速なツールを目指す
```

**良い例**（捨てたものが分かる）:

```markdown
| 捨てるもの | 得るもの | 見直す条件 |
|---|---|---|
| 汎用性（他分野への転用） | 中核アルゴリズムが読める単純さ | 別分野の要求が 2 件出たとき |
| 実行速度 | 途中経過を全部残せること | 1 実行が 10 秒を超えたとき |
```

### 脅威モデルは「守らないもの」まで書く

`CLAUDE.md` の「安全機構」節と security-checker の検査範囲は、ここを
根拠に決まります。「悪意ある第三者は対象外（ローカル専用のため）」と
明記されていれば、過剰な防御を作らずに済み、公開に踏み切るときに
**何を見直すべきか** も分かります。

### フェーズ計画は順序の理由まで書く

「P02 が P01 の何に依存するか」が書いてあると、フェーズの入れ替えや
分割の判断が速くなります。状態（📝/🔧/✅）はロードマップ表の役割なので
ここには書きません。

### 図・表の扱い

全体像を図にする場合は 開発ルール 8 の作図言語（迷ったら Mermaid）で書き、
番号とキャプションを付けて本文から参照する（開発ルール 7）。
書いたら図・番号の検証ツールを実行する。

## 更新のルール

- **フェーズごとには更新しない** 。ここが動くのは方針が変わったときだけ
- 更新したら冒頭の「最終更新」に **日付と更新理由** を書く
- 割り切りを見直したときは、表の「見直す条件」が実際に満たされたのか、
  それとも判断を変えたのかを本文に残す（後から経緯を追えるように）
- 実装が全体構想と矛盾したら、 **勝手にどちらかへ寄せない** 。
  ユーザーに確認する（`CLAUDE.md` 絶対ルール3）

## 品質チェック（作成後）

- [ ] 一行要約が専門用語なしで読めるか
- [ ] 非目標が **具体的に** 書かれているか（「〜は作らない」の形）
- [ ] 割り切りの表に「見直す条件」まで入っているか
- [ ] 脅威モデルに「守らない対象」が書かれているか
- [ ] フェーズ計画に順序の理由があるか
- [ ] 進捗・受け入れ条件・クラス設計を書き込んでいないか（役割の重複）
- [ ] ロードマップ表にフェーズ候補の行を反映したか
