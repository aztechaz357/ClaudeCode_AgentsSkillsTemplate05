# テスト結果まとめ（test-reporting）

**8 点セットの 7 番目。** スライス 1 本につき 1 枚
（`docs/test-reports/S##-<name>.md`）を必ず作り、反復のたびに更新する。

## この 1 枚だけが答えられる問い

- 今このスライスは **本当に緑か** （何件通って、何件飛ばしたか）
- **どの仕様が、どのテストで** 検証されたか（`☑` の根拠）
- どの仕様が **まだテストで押さえられていないか**
- 実物を動かすと **実際に何が出るか**

バックログは進捗を、要求はやりたいことを持つ。
**証拠を持つのはこの 1 枚だけ** 。

## 絶対の掟: 実測しか書かない

**推測で書いた数字と出力は嘘になる**（絶対ルール 7）。

- 件数は **プロファイルの「テスト件数の数え方」** で数える。手計算しない
- 出力は実行して得たものを **そのまま** 貼る。整形も要約もしない
- 実行していないコマンドを「実行した」ように書かない
- 落ちているテストがあるなら **落ちていると書く** 。隠して緑と書かない

> 実例: 手書きの期待出力は、人もエージェントも正確には覚えていない。
> このテンプレートで最初に照合ツールを入れたとき、既に 2 か所が
> 実際の出力と食い違っていた。

## テンプレート

`./template.md` を `docs/test-reports/S##-<name>.md` に写して埋める。
持つ節は 5 つだけ。

| 節 | 中身 |
|---|---|
| 実行環境 | 使ったコマンド（プロファイルから写す）と実行日 |
| 結果の要約 | passed / failed / skipped の実測値。全体と、このスライス分 |
| 仕様とテストの対応 | 仕様番号 → テスト名 → 結果。 **未カバーの仕様も行に残す** |
| 実物の出力 | 動作確認コマンドの出力をそのまま |
| 気づいたこと | 不安定なテスト・遅いテスト・skip の理由（無ければ「なし」） |

## 成熟度別の深さ

| 成熟度 | 書く量 |
|---|---|
| **L1 動く** | 全体の件数 ＋ 仕様 1〜3 条の対応 ＋ 実物の出力 1 つ |
| **L2 固い** | ＋ 境界値・失敗経路の結果。 **未カバーの仕様 0 件** |
| **L3 整った** | ＋ 回帰の結果（骨組みの E2E を含む）・アーキテクチャテストの結果 |

## 書く手順

1. **走らせる**（プロファイルのコマンド。全体と統合テストの両方）
2. **数える**（プロファイルの「テスト件数の数え方」。手計算しない）
3. **実物を動かす**（プロファイルの「動作確認」。緑だけでは証拠にならない）
4. **対応表を埋める**（仕様番号は USDM の番号をそのまま使う）
5. **要求 HTML を更新する**: 緑になった仕様の検証欄を `□` → `☑` にし、
   **トレース表の「単体テスト」「統合テスト」列** にテスト名を書く
6. **検証する**:

   ```
   <ツール実行コマンド> .claude/tools/build_usdm.py
   ```

   `missing-trace` が出たら、`☑` にした仕様のどこかの線が切れている。
   埋めてから完了とする

## 落ちているときの扱い

**赤いまま「まとめ」を書いて反復を終わらせない。**

| 状況 | どうするか |
|---|---|
| 実装の不備で落ちている | 実装（`coder`）に差し戻す。まとめは書き直す |
| 仕様と実装が矛盾している | **止まってユーザーに確認する**（絶対ルール 3） |
| 骨組みの E2E が落ちた | 回帰。最優先で直す。ここは全反復の安全網 |
| 環境の都合で skip した | skip の理由を「気づいたこと」に必ず書く（黙って飛ばさない） |

## 品質チェック

- [ ] 件数が **実測** か（コマンドの出力を見て書いたか）
- [ ] 実物を動かした出力が貼られているか
- [ ] 仕様番号 → テスト名の対応が全条について書かれているか（未カバーも行に残す）
- [ ] `☑` にした仕様のトレース表の 5 列すべてが埋まっているか（`build_usdm.py` が 0）
- [ ] skip / failed を隠していないか
- [ ] このスライスの節がマニュアル（`docs/manual.md`）にもあるか
