# 可視化とデバッグのしやすさ（visual-debugging）

**「動いた／落ちた」だけを返すコードは、直すのに時間がかかる。**
このスキルは、実行の中身を後から目で追えるようにするための規約。

目的は 3 つ。

1. **落ちた理由が、ログを読み直さずに分かる**（失敗時に証拠が残っている）
2. **数値の列ではなく形で分かる**（時系列・分布・状態遷移をグラフで見る）
3. **条件を変えた結果をすぐ比べられる**（パラメータを差し替えて再実行できる）

## どこまでやるか（成熟度別）

可視化は目的ではなく手段。 **骨組みより先に凝らない** 。

| 成熟度 | やること |
|---|---|
| **L1 動く** | 構造化トレースを 1 本通す（入口・出口・主要な分岐）。失敗時に入力を残す |
| **L2 固い** | トレースからグラフを 1 枚出せる。失敗テストがアーティファクトを残す |
| **L3 整った** | パラメータを差し替えて再実行できる 1 枚（インタラクティブ HTML）を持つ |

L1 で凝った可視化を作るのは越権。ただし **トレースの 1 本だけは L1 から**
通す —— 後から入れると、入れる場所を探すのに実装を読み直すことになる。

## 1. 構造化トレース（すべての土台）

人が読む文字列ではなく、 **機械が読める 1 行 1 レコード** で出す。
文字列を後から正規表現で解析するのは、可視化を諦めさせる一番の原因。

- 形式: 1 行 1 JSON（JSON Lines）。プロファイルの「ログの出力先・形式」に従う
- 最低限の項目: `t`（時刻・単位を名前に入れる）・`event`・`slice`（S##）・
  値（物理量は単位を接尾辞に。`dt_s` `mass_kg`）
- **出力は infrastructure 層に閉じる** 。domain / application は
  「何を記録するか」を決めるだけで、書き込みは契約（Port）越しに行う
  （`layered-architecture` の契約の切り方に合う典型例）
- テスト時はフェイクのトレース先に差し替える。 **本番のログを汚さない**

```
{"t_s": 0.0,  "event": "boil.start", "slice": "S02", "temp_c": 12.4}
{"t_s": 61.2, "event": "boil.done",  "slice": "S02", "temp_c": 100.0}
```

トレースは **テストの検証対象にもなる** （「この順で起きたか」を
イベント列で確かめられる）。文字列比較より壊れにくい。

## 2. グラフ化（数値の列を形にする）

トレースから静止画・HTML を生成する **小さなツール** を工房レーンに作る
（`/tool`。`workshop/tools/<name>/`）。本体のソースに可視化コードを
混ぜない —— 混ぜると、可視化の都合で業務ロジックが歪む。

| 見たいもの | 向いている形 |
|---|---|
| 時間で変わる量（温度・件数・メモリ） | 折れ線。横軸に単位を必ず書く |
| 分布・ばらつき（所要時間・誤差） | ヒストグラム。外れ値を切らない |
| 状態の移り変わり | 状態遷移図（Mermaid `stateDiagram-v2`）を生成する |
| 呼び出しの順序 | シーケンス図（Mermaid `sequenceDiagram`）を生成する |
| 依存の形 | `flowchart TD`（層の色は `guides/diagrams.md` の規約に従う） |

**トレースから図を生成できるなら、設計書の図も生成に寄せる。**
手で描いた図は実装とずれるが、生成した図はずれない。

## 3. アニメーションと対話（条件を変えて比べる）

「1 回動かした結果」より **「条件を変えた結果の差」** のほうが情報量が多い。

- 時間発展のあるものは **コマ送り** にする（フレームごとの状態を
  トレースから作り、HTML の `<input type="range">` で行き来する）
- パラメータは **コードに埋めない** 。引数・設定・関数の既定値として
  外に出し、値を変えて再実行できる形にする
  （これは可視化のためだけでなく、契約とテストのしやすさにも効く）
- 生成する 1 枚は **自己完結 HTML** にする（外部 CDN を参照しない）。
  `file://` で開けること。同じ方針の実例が
  `.claude/tools/build_usdm.py` と `build_status.py`
- 重い依存（可視化ライブラリ）は **工房レーンのツール側に閉じる** 。
  本体の依存に足さない

> やりすぎの線引き: 可視化に **本体の設計を変えさせない** 。
> 「グラフを出すために domain が I/O を持つ」は本末転倒。
> トレースを出す口（契約）だけを本体に置き、描く側は外に置く。

## 4. 失敗が残す証拠（アーティファクト）

**落ちたテストは、落ちた瞬間の状態を残す。** 再現手順を人が組み直す
時間が、デバッグで最も長い。

| 残すもの | どこに |
|---|---|
| 入力（生成した乱数・一時ファイルの中身） | テストのアーティファクト置き場（gitignore） |
| そのときのトレース（JSON Lines） | 同上。テスト名でファイルを分ける |
| 生成した図・HTML | 同上 |
| 期待と実際の差分 | テストの失敗メッセージに直接書く（探させない） |

- 置き場所はプロファイルの「ログの出力先」配下に `test-artifacts/` を作る
  （無ければ `logs/test-artifacts/`）。 **gitignore する**
- **失敗メッセージに証拠のパスを書く** 。書かないと誰も見に行かない
- 乱数・時刻に依存するテストは **種（seed）を失敗メッセージに出す**
  （再現できない失敗は、無いのと同じくらい直せない）

## 5. テストコードも読めるようにする

- テスト名は日本語で「何をしたら何になるか」を書く
  （`test_空ファイルなら0行と出る`）。名前が仕様になっていれば、
  落ちた一覧を読むだけで壊れた仕様が分かる
- docstring は 4 項目（テスト対象・入力・期待値・理由）。
  **理由** を書くのは、後から消してよいテストかを判断できるようにするため
- 表形式のケース（パラメータ化テスト）は、ケースに名前を付ける。
  番号だけだと落ちたときに何のケースか分からない
- 1 つのテストで 1 つのことだけ確かめる。複数の assert を並べるときは、
  どれが落ちたか分かるメッセージを付ける

## セルフチェック

- [ ] トレースが 1 行 1 レコードの機械可読な形か（文字列の解析に頼っていないか）
- [ ] トレースの出力が infrastructure に閉じているか（domain が汚れていないか）
- [ ] 可視化のコードが本体ではなく工房レーンのツールにあるか
- [ ] パラメータが外から変えられるか（コードに埋まっていないか）
- [ ] 失敗したテストが証拠を残し、そのパスを失敗メッセージに書いているか
- [ ] 乱数・時刻に依存するテストが種を出しているか
- [ ] 生成した HTML が外部参照ゼロで `file://` で開けるか
- [ ] （L1 のとき）可視化に凝りすぎていないか —— 骨組みが先
