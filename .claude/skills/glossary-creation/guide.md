# 用語集作成ガイド

## 定義の書き方

プロジェクトでの意味に限定して書く。一般論で終わらせない。

**悪い例**:

```markdown
### 承認（Approval）
**定義**: 操作を許可すること。
```

**良い例**:

```markdown
### 承認（Approval）
**定義**: 実行前に可否を確認する仕組み。`BaseApprovalPolicy.review()` が
判断し、読み取り系は自動許可集合として確認なしで通る。拒否は失敗ではなく
結果値として呼び出し元に渡る。
**関連用語**: [[自動許可集合]]、[[フェイルセーフ]]
**関連コード**: `domain/approval.py`
```

ポイント:

- どのクラス・仕組みがその概念を担うかまで書く（ただしフィールドの列挙は
  reference.md の仕事）
- 「〜ではない」も有効（例: フェイルソフトとフェイルクローズの違いは
  対で書くと明確になる）

## 表記ゆれの検出

用語集の更新時に、各文書で同じ概念が別の表記になっていないかを確認する。
Grep で候補表記を横断検索し、工程をまたいで一貫しているかを見る:

- 要求仕様書のドメイン用語が、設計書・コードで別名になっていないか
- 似た概念（フェイルセーフ / フェイルソフト等）の使い分けが一貫しているか

ゆれを見つけたら、用語集に正の表記を定め、文書側の修正はユーザーに提案する
（凍結文書は修正対象外。ゆれの記録だけ残す）。

## 更新のタイミング

- 新しいスライスで新しいドメイン用語が出たとき
- 設計で新しい概念（契約・パターン）を導入したとき
- レビュー（doc-reviewer）で用語の不一致が指摘されたとき
- 定期的な棚卸しはしない（実装・設計の変化に追随して更新する）
