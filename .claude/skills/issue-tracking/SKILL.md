# Issue 駆動スキル（issue-tracking）

GitHub Issue を **開発の窓** として使うための規約。
このスキルは **既定では効かない** —— プロジェクトごとに on / off を設定し、
`off` のあいだは全エージェントが Issue に一切触れない。

## 大原則: 二重管理を作らない

| | 役割 | 正か |
|---|---|---|
| `docs/backlog.md` | 進捗・優先順位・負債・成熟度 | **正（唯一）** |
| GitHub Issue | 外から見る窓・外から受ける口 | 写し（正ではない） |

**Issue は backlog の写しであって、進捗の正ではない。**
成熟度・着手中・次の一手をどこで確かめるかは、Issue が on でも off でも
`docs/backlog.md` のまま変わらない（CLAUDE.md の絶対ルールを壊さない）。

同期の向きは 2 つだけ:

```
docs/backlog.md  ──(push)──▶  GitHub Issue     … S## / D## を写す
docs/backlog.md  ◀──(pull)──  GitHub Issue     … 外から来た起票を取り込む
```

`pull` は **Issue をそのまま backlog へ書き込まない** 。
「今回のゴールに寄与するか」を `docs/concept.md` で判定してから、
スライス表・負債表・「今回のゴールの外」表のどれかへ入れる（`/backlog` と同じ判定）。

### 判断の記録

- **採用**: バックログを正とし、Issue は写し（片方向 push + 判定つき pull）。
  **そう考えた理由**: このテンプレートの絶対ルールは「進捗の正は
  `docs/backlog.md` だけ」であり、`off` にできる仕組みを正の側に置くと、
  off にした瞬間に進捗の正が消える
- **他の選択肢 1**: Issue を正にし backlog を生成物にする。
  **メリット** = 外部協業が自然・GitHub の機能（マイルストーン・Projects）に乗れる。
  **デメリット** = off にできない（off = 正が消える）・オフラインで進捗が読めない・
  既存の全エージェントとツール（`check_deliverables.py` ほか）が backlog を読む前提
- **他の選択肢 2**: 双方向同期。 **メリット** = どちらで編集してもよい。
  **デメリット** = 競合解決の規則が要り、決定論性が落ちる（設計思想 8 に反する）
- **却下の決め手**: 「途中で on / off を切り替えられること」が要求なので、
  **off にしても何も失われない構造** が必須だった

## 設定（プロジェクトごと・途中で切り替え可）

正は **`CLAUDE.md` のプロジェクトプロファイルの「Issue 追跡（GitHub Issues）」節** 。

```markdown
### Issue 追跡（GitHub Issues）

- 使用: off
- リポジトリ: なし
- ラベル: slice / debt / L1 / L2 / L3
```

- `使用:` の行だけが機械が読む値（`on` / `off`）。ここ以外に状態を置かない
- 読み書きは推測せずツールで行う（下の「ツール」節）
- CLAUDE.md はコミットされるので、設定は **チーム全体で共有される** 。
  「自分の環境だけ off」は用意しない（環境ごとに挙動が変わるほうが事故が多い）

### 切り替え手順

| やること | コマンド | 起きること |
|---|---|---|
| 現在の設定を見る | `/issue status` | 使用・リポジトリ・未同期の差分を報告 |
| 使い始める | `/issue on` | `使用: on` に書き換え、リポジトリを確定し、既存 backlog との差分を出す |
| やめる | `/issue off` | `使用: off` に書き換える。 **開いている Issue は消さない** |

**途中で on にしたとき** —— それまでに進んだスライスも Issue にする。
既に L3 のスライスは `--include-done` を付けたときだけ作り、作った直後に閉じる
（履歴として残す意味がある場合のみ。既定では作らない）。

**途中で off にしたとき** —— 開いている Issue には
「このリポジトリは Issue 追跡を停止した。進捗は `docs/backlog.md` を見る」と
コメントを 1 件付けてから止める。 **黙って放置しない**（外から見た人が
生きている Issue だと誤解する）。閉じるかどうかはユーザーが決める（勝手に閉じない）。

## 単位と対応付け

**Issue 1 本 = バックログの 1 行。** それ以外の粒度を作らない。

| バックログの行 | Issue のタイトル | ラベル |
|---|---|---|
| スライス `S03 CSV のフィルタ` | `S03: CSV のフィルタ` | `slice`・成熟度（`L1` 等） |
| 負債 `D02 逆流している` | `D02: 逆流している` | `debt` |

対応付けは **タイトルの接頭辞（`S##:` / `D##:`）だけ** で行う。
対応表のファイルを別に持たない（持つと必ず実物とずれる）。

- 反復の 8 段ごとに Issue を切らない（Issue が 8 倍に増えて窓の役を果たさない）。
  段の進行は Issue 本文のチェックリストで表す
- 1 スライスの作業が大きすぎて Issue を割りたくなったら、それは
  **スライスの切り方の失敗** 。バックログ側でスライスを割る

## Issue の本文

**本文の正は `sync_issues.py` が生成する形** （手で書いた本文とツールの本文が
ずれないよう、雛形はツール側に 1 つだけ置く）。含まれるのは次の 4 つ:

1. スライス名と目標成熟度
2. 7 点セットのチェックリスト（要求・設計・単体テスト・実装・統合テスト・
   テスト結果まとめ・マニュアル）
3. `docs/backlog.md` と `docs/slices/S##-*.md` への相対リンク
4. **「進捗の正は `docs/backlog.md`。この Issue は写し」** の 1 行

手で Issue を書くときも、この 4 つを外さない。

## 反復のどこで何をするか（`使用: on` のとき）

`/iterate` の段に **追加で** 乗る動作。段そのものは増やさない。

| 段 | Issue 側の動作 | 誰が |
|---|---|---|
| 段0 選ぶ | 対象 Issue が無ければ作る。自分に assign し、`いま着手中` と同じ内容をコメント | `issue-manager` |
| 段1〜7 | **触らない**（コミットメッセージ末尾に `refs #<番号>` を書くだけ） | 各担当 |
| 段8 記録 | チェックリストを実測で更新し、到達成熟度のラベルを張り替え、完了報告をコメント | `issue-manager` |
| L3 到達 | Issue を閉じる（`/issue close S##`。 **L1・L2 では閉じない** ） | `issue-manager` |

- 段1〜7 で Issue を触らないのは、 **7 点セットの担当が本業から逸れないため** 。
  Issue の更新は段0 と段8 に集約する
- 閉じるのは L3 のときだけ。L1・L2 は「動く・固い」であって完了ではない

## `使用: off` のときの振る舞い

- 全エージェントは `gh issue` を **1 回も呼ばない** （読み取りも含む）
- コミットメッセージに `refs #` を書かない
- `/issue` 以外のコマンドは Issue に言及しない（`/status` の表示も変わらない）
- `sync_issues.py` は終了コード 2 で拒否する（うっかり実行しても外部に出ない）

**off が既定** 。GitHub を使わないプロジェクト・ローカル専用のツール・
まだリモートが無い段階で、Issue の存在が前提になる箇所を作らない。

## コミット・PR との紐づけ

- コミットメッセージの **末尾** に `refs #12` を書く（接頭辞は既存のまま
  `実装:` `テスト:` などを使う）
- **`fixes #12` / `closes #12` を書かない** —— GitHub が自動で閉じてしまい、
  「閉じるのは L3 のときだけ」という規約を機械が破る
- PR を作るかどうかはプロファイルの「push / PR」の値に従う（このスキルは変えない）

## ツール

前置コマンドはプロファイルの「`.claude/tools/` の Python ツール実行」。

| ツール | 用途 | 終了コード |
|---|---|---|
| `issue_mode.py` | `使用:` の行を読む / 書き換える | 0 = on、1 = off、2 = 判定不能 |
| `sync_issues.py` | backlog と Issue の差分を出す（既定は dry-run） | 0 = 差分なし、1 = 差分あり / 適用失敗、2 = エラー・off |

```
<ツール実行コマンド> .claude/tools/issue_mode.py                    # 現在の設定
<ツール実行コマンド> .claude/tools/issue_mode.py --set on --repo owner/repo
<ツール実行コマンド> .claude/tools/sync_issues.py                   # 差分（送信しない）
<ツール実行コマンド> .claude/tools/sync_issues.py --apply           # 差分を GitHub へ反映
```

`--apply` は **外部への書き込み** 。エージェントは実行前に必ずユーザーへ
「何本作る / 何本更新する / 何本閉じる」を提示して確認を取る（絶対ルール 4）。

### 実際の出力（このテンプレートで動かしたもの）

差分を見る（送信しない）:

```
差分: 作成 1 / 更新 0 / 閉じる 0 / 再オープン 0 / 取り込み候補 0
  作成      S01: Issue 駆動の動作確認  [slice, L0]
RESULT: 差分あり（未送信）。承認を得てから --apply する
```

承認を得てから反映する:

```
OK: create S01 https://github.com/aztechaz357/ClaudeCode_AgentsSkillsTemplate05/issues/1
RESULT: 反映した
```

同じコマンドをもう一度実行しても、二重に起票されない（冪等）:

```
差分: 作成 0 / 更新 0 / 閉じる 0 / 再オープン 0 / 取り込み候補 0
RESULT: 同期済み（送信するものは無い）
```

## やってはいけないこと

- **Issue に進捗を書いて backlog を更新しない**（正が 2 つになる。最も重い違反）
- Issue を段ごとに切る・タスクごとに切る（窓ではなく作業ログになる）
- `使用: off` のまま `gh issue` を呼ぶ
- 外から来た Issue を判定せずにバックログへ入れる（ゴールが溶ける）
- `fixes #` でコミットして GitHub に自動で閉じさせる
- L1・L2 で Issue を閉じる
- 対応表のファイルを別に作る（タイトルの接頭辞だけで足りる）
