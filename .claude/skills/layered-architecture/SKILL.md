# レイヤードアーキテクチャ（layered-architecture）

このプロジェクトの構造は **レイヤードアーキテクチャ** 。
クリーンアーキテクチャ（依存性逆転・契約中心）は要求しない。
理由: 反復のたびに契約を切るコストが、骨組みを通す速度を殺すため。

## 層と依存の向き

依存は **上から下への一方向だけ** 。

```
presentation   … 入出力・表示・CLI・HTTP ハンドラ
      ↓
application    … ユースケース・進行の組み立て
      ↓
domain         … 業務ロジック・値・計算（純粋）
      ↓
infrastructure … 外部 I/O・ファイル・DB・プロセス・ネットワーク
```

具体的なパスはプロファイルの「層構成」表を正とする。

| 層 | import してよいもの |
|---|---|
| presentation | 標準ライブラリ + application + domain + infrastructure |
| application | 標準ライブラリ + domain + infrastructure |
| domain | 標準ライブラリのみ |
| infrastructure | 標準ライブラリ + domain（+ プロファイル許可の外部ライブラリ） |

**クリーンアーキテクチャとの違い**: application が infrastructure を
**直接呼んでよい** （契約を切って注入しなくてよい）。
domain が純粋であることだけは維持する —— ここが崩れるとテストが遅くなる。

## 唯一のルール: 逆流禁止

覚えるのはこれ 1 つ。

> **下の層が上の層を import してはいけない。同じ層内で循環してはいけない。**

- `domain` が `application` を import → 違反
- `infrastructure` が `presentation` を import → 違反
- `application` が `infrastructure` を import → **違反ではない**

この 1 ルールだけを機械検証する（アーキテクチャテスト）。
検証コマンドはプロファイルの「アーキテクチャテスト」を使う。

## 成熟度に応じた守り方

| 成熟度 | 層の扱い |
|---|---|
| **L1 動く** | **1 ファイルに全部書いてよい** 。層を分けなくてよい。逆流していてもよい（ただし負債に記録する） |
| **L2 固い** | 層に分かれている。逆流があれば負債表に記録済み |
| **L3 整った** | 逆流ゼロ。アーキテクチャテストが緑 |

骨組み（`/skeleton`）の段階で層を切ろうとしないこと。
**通ってから分ける** 方が、分けてから通すより速く、やり直しが少ない。

## 置き場所の決め方（上から順に問い、最初に該当した層へ）

1. **標準ライブラリ以外に依存しない計算・値・判定か？** → domain
2. **外部（ファイル・DB・ネットワーク・OS・プロセス）に触るか？** → infrastructure
3. **複数の部品を順に呼んで 1 つの仕事を成立させるか？** → application
4. **利用者に見せる・利用者から受け取るか？** → presentation

迷う典型例:

- **入力を受け取る実装** → presentation（I/O が無いなら infrastructure）
- **設定の読み込み** → infrastructure（読んだ値を使う判断は domain）
- **ログ出力** → infrastructure（出力の書式を決めるのは presentation）
- **どの層にも見えないもの** → L1 なら presentation に置いて負債に記録。
  L2 で分ける。 **`utils/` を作らない**（作ると全部そこへ流れ込む）

## テストの置き場所

- テストルートはソースの構成をミラーする
- E2E / 統合テストはプロファイルの「統合テスト」パスに分ける
- domain のテストは外部依存を持たない（速いこと。ここが遅いと反復が遅くなる）
- infrastructure のテストは一時ディレクトリ・フェイクサーバを使う。
  本物の外部サービスに触らない

## クリーンアーキテクチャへ育てる（必要になったときだけ）

レイヤードのまま困らないなら、そのままでよい。
次の症状が出た層に限り、その部分だけ依存性逆転を入れる。

| 症状 | 打ち手 |
|---|---|
| 同じ処理の実装を切り替えたい（本番 / フェイク / 別ベンダ） | domain に契約を置き、infrastructure に実装、呼び出し側で注入 |
| application のテストが外部 I/O のせいで遅い・不安定 | 同上（契約 + フェイク） |
| infrastructure の変更で application が毎回壊れる | 同上 |
| 実装が 3 種類以上に増えた | 同上 + 配線を 1 か所（Composition Root）に集める |

**症状が出ていないのに先に契約を切ることは禁止** （先回りの抽象化）。
これは `/refactor` の仕事であり、負債表に「返す条件」として書いておく。

## 家風パターンとの関係

プロファイルの「家風パターン」に `core 無変更` がある場合、その対象は
**L3 に到達したファイルだけ** 。L1・L2 のファイルは自由に書き換えてよい。
凍結対象は `.claude/core_files.txt` に列挙し、L3 到達時に追加する。
