# 要求仕様書作成スキル

開発プロセスの起点は **要求仕様書** です（要求仕様書 → 設計書 → TDD 実装 →
統合テスト）。このスキルは、ユーザーの要望を「設計を書ける精度」かつ
「統合テストに翻訳できる精度」まで構造化します。

要求仕様書の最重要要素は **受け入れ条件** です。これは後の工程で
integration-tester がそのまま統合テストに翻訳する契約であり、
曖昧な受け入れ条件は工程全体の決定論性を壊します。

## 出力先と採番

```
docs/requirements/P##-<name>.md   （1フェーズ1ファイル）
```

- P## はロードマップ表（プロファイルの「ロードマップ表」の場所を参照）の
  次番号。作成と同時にロードマップ表へ「📝 要求のみ」の行を追加する
- 設計書（`docs/design/proposals/P##-<name>.md`）は同じ番号を使う

## 進め方

1. **知覚**: 全体構想（`docs/concept.md`）・ロードマップ表と既存の
   要求仕様書・設計書を読み、既存の実装・候補と突き合わせる
   （「実装済みの機能を無いと誤認」を防ぐ）。全体構想の **非目標・割り切り**
   に触れる要望なら、要求に落とす前にユーザーへ確認する
2. **構造化**: `./template.md` の観点で整理する:
   - 背景と課題（なぜ欲しいのか。今できなくて何に困っているか）
   - ユーザー価値（できるようになると何が変わるか。実装手段ではなく体験で）
   - **受け入れ条件**（後述。最重要）
   - スコープと対象外（今回入れる範囲・意図的に入れない範囲）
   - 既存機能との関係（重複・競合・依存）
   - 制約（プロファイルの技術制約・非機能要件）
   - フェーズ分割の当たり（大きい場合。独立してマージ可能な単位へ）
3. **確認**: **曖昧な点は AskUserQuestion でユーザーに確認する**
   （勝手に仮定して設計に進まない）。要求段階の確認は自律実行の停止例外
4. **出力**: 要求仕様書を書き、ロードマップ表に行を追加してコミットする
   （コミット接頭辞は `要求:`）

## 受け入れ条件の書き方（最重要）

受け入れ条件は **統合テストのテストケース名になる粒度** で書く。

**悪い例**（検証不能）:

```markdown
- [ ] ユーザーが快適にログインできること
- [ ] エラー処理が適切であること
```

**良い例**（統合テストに翻訳できる）:

```markdown
- [ ] 有効な認証情報で POST /login すると 200 とセッション Cookie が返る
- [ ] 誤ったパスワードで 5 回連続失敗すると、6 回目は正しい情報でも 429 を返す
- [ ] セッション有効期限（既定 30 分）を過ぎた Cookie では 401 を返す
```

チェックポイント:

- 「入力 → 期待される観測結果」の形になっているか
- 数値・境界値が入っているか（既定値・上限・タイムアウト）
- 失敗経路の条件が含まれているか（正常系だけになっていないか）
- 実装手段（クラス名・ライブラリ名）を書いていないか（それは設計の領分）

## 注意

- 要求整理の段階で **実装方式を確定させない**（方式の決定と却下案は設計書の領分）
- 大きすぎる要望は 1 フェーズに詰め込まず、フェーズ分割案を提示して
  ユーザーに確認する
- 製品企画の枠組み（KPI・ペルソナ等）はプロジェクトの性質に応じて使う。
  個人開発の実用ツールでは省略してよい

## 品質チェック（作成後）

- [ ] 受け入れ条件がすべて「入力 → 観測結果」の形か
- [ ] 失敗経路・境界値の条件が含まれているか
- [ ] 実装手段を先に決めていないか
- [ ] スコープ外が明記されているか
- [ ] ロードマップ表に行を追加したか
