# プロセスガイド

反復開発のフローを手順として展開したガイド。
プロセスの設計思想と完了条件の正は `agile-process` スキル
（`SKILL.md` と `maturity.md`）。ここでは重複させず、手順だけを書く。

## 全体フロー

```
ゴール定義 → バックログ → 骨組み（完走）→ 反復 ⇄ リファクタリング → 完成
```

| 工程 | 成果物 | 使うスキル / コマンド |
|---|---|---|
| ゴール定義 | `docs/concept.md`（一行 + 完走の定義） | concept-definition |
| バックログ | `docs/backlog.md`（スライス 3〜8 本） | agile-process / `/backlog init` |
| 骨組み | E2E 1 本 + 通る実装 + `docs/slices/S01-*.md` | walking-skeleton / `/skeleton` |
| 反復 | スライス 1 枚 + テスト + 実装 + 負債の記録 | slice-definition / `/iterate` |
| リファクタリング | `整理:` コミット群 + 負債の `済` | refactoring / `/refactor` |
| 厚い経路（例外） | 要求仕様書 + 設計書 + tasklist | requirements-definition / functional-design / `/add-feature` |

**前工程を飛ばさないのは「ゴール定義 → バックログ → 骨組み」の 3 つだけ。**
骨組みが通った後は、反復とリファクタリングを行き来する。

## 1 反復の順序

1. バックログの最上段を 1 本取る（WIP = 1）
2. スライス文書に仕様（3 行）と薄い設計（5 行）を書く
3. TDD で実装する（下記）
4. E2E を実行する（骨組みの E2E を含めて全緑にする）
5. 実物を動かして出力をスライス文書に貼る
6. 残した手抜きを負債表に転記する
7. バックログの成熟度を 1 段上げてコミットする

**1 反復は半日以内。** 超えたらスライスが大きすぎるので分割する。

## TDD サイクル（Red → Green → Refactor）

1. **Red**: テストを先に書き、プロファイルのテストコマンドで失敗を確認する。
   失敗確認を飛ばさない（テストが最初から通る = テストが仕様を検証していない疑い）
2. **Green**: テストを通す。 **通し方は成熟度で変わる**:
   - **L1**: 仮実装（固定値を返す・ハードコード）でよい。
     ケント・ベックの「Fake It」をそのまま使う。ただし負債に記録する
   - **L2**: 要求を満たす実装にする。仮実装は残さない
3. **Refactor**: **その場では最小限** 。整えたくなったら負債表に積み、
   `/refactor` の工程で返す（実装中に整え始めると反復が止まる）
4. コミットしてから次の最小ステップへ

Red が確保できなかったテストは、変異テストで有効性を確認する:

```
<ツール実行コマンド> .claude/tools/mutate.py --file <実装> --find <正> --replace <誤> --expect <テスト名>
```

SURVIVED が出たらテストの穴。テストを足してから次へ進む。

## マイクロコミット

- 1 コミット = 1 つの意図（アトミック）。関連のない変更を混ぜない
- 目安: 差分が 20〜30 行を超える、または無関係な複数の関数にまたがるなら
  コミットのタイミングが遅すぎる
- コミット前に必ず全テストの緑を確認する（骨組みの E2E を含む）
- **先回りの実装・過剰な作り込みは禁止**（今の成熟度に必要な最小限のみ）

## コミットメッセージ規約

書式の正はプロファイル。既定（日本語）は次のとおり。

接頭辞:

| 接頭辞 | 使うとき |
|---|---|
| `骨組み:` | 骨組み（`/skeleton`）の実装 |
| `実装:` | 反復の中のコード変更 |
| `テスト:` | E2E・統合テストの追加 |
| `整理:` | リファクタリング（振る舞い不変） |
| `docs:` | スライス文書・バックログ・現状設計・マニュアルの更新 |
| `要求:` / `設計:` | 厚い経路の要求仕様書・設計書 |
| `プロセス:` | `.claude/` のエージェント・スキル・ツールの変更 |

本文は「何を・どのファイルに・なぜ」を箇条書きで具体的に。テスト結果も書く。

```
実装: 行数カウントを追加（S02 を L1 へ）

- src/tool/count.py に count_rows(path) を追加（1 行目は常にヘッダとみなす仮実装）
- test/test_count.py にテスト 2 件を追加（Red 2 件 → Green 確認）
- 残した手抜き: ヘッダ判定の固定化（D03・痛み 中）
- テスト: 12 passed / 0 skipped
```

Windows / PowerShell 5.1 環境では here-string（`@'…'@`）でコミットし、
メッセージに二重引用符（"）を含めない（引数分解事故の既知の教訓）。

## 記録の同期

反復の終わりに **必ず** 更新するもの（`doc-syncer` のチェックリスト A）:

1. スライス文書の成熟度・実績・仕様・残した手抜き
2. `docs/backlog.md` の成熟度・次の一手・いま着手中・負債表

L3 に上げる反復でだけ追加するもの（チェックリスト B）:

3. `docs/design.md`（現状設計 1 枚）・`docs/reference.md`・`docs/manual.md`

**L1・L2 の反復で現状設計書やマニュアルを触らない。**
これが従来プロセスで最も時間を食っていた工程であり、
渡す予定が立つまで後回しにしてよい。

## 矛盾したときの止まり方

- **仕様と実装が食い違う** → 勝手にどちらかへ寄せず、
  blockers.md に記録してユーザーに確認する（絶対ルール 3）
- **リファクタリング中にテストの期待値を変えたくなった** → 仕様変更なので
  リファクタリングを止めて確認する
- **不可逆な操作が必要になった** → 止めて確認する（絶対ルール 4）

## 文書の記法

文書の記法規約（Markdown・数式と図表の番号・作図言語・マニュアル）の正は
**`writing-conventions` スキル** 。ここでは重複させない。

作業前に必ず読むもの:

- 本文を書く: `writing-conventions/guides/markdown.md`
- 数式・図・表を出す: `writing-conventions/guides/numbering.md`
- 図を描く: `writing-conventions/guides/diagrams.md`
- マニュアルを更新する: `writing-conventions/guides/manual.md`

検証コマンド（NG が出たまま完了としない）:

```
powershell -File .claude/tools/check_numbering.ps1 -Path <file.md|dir>
powershell -File .claude/tools/check_diagrams.ps1 -Path <file.md|dir>
```

図は **L3 で必要になるまで書かない** 。L1・L2 のスライス文書に図は要らない。
