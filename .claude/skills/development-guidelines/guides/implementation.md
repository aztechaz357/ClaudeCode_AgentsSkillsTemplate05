# 実装ガイド

CLAUDE.md の規約を実装時にそのまま使える形に展開したガイド。
言語固有の書式（docstring の形式・命名の慣習）は
**プロファイルの「言語・スタイル」節を正とする** 。以下は一般形と例。

## レイヤー別の配置規則

依存の流れ: **Presentation → Application → Domain ← Infrastructure**

| 追加するもの | 置き場所 | import してよいもの |
|---|---|---|
| 契約（インタフェース）・エンティティ | domain | 標準ライブラリのみ |
| ユースケース | application | domain のみ |
| 具体実装（外部 I/O・状態） | infrastructure | domain のみ（+ プロファイル許可の外部ライブラリ） |
| UI・表示・入出力 | presentation | application（と domain のエンティティ） |
| 配線 | Composition Root | 全層（Composition Root のみの特権） |

- 依存ルールは機械検証（アーキテクチャテスト）で担保するのが望ましい。
  未整備なら整備を提案する（決定論的操作を増やす）
- 新機能は原則「domain に契約 + infrastructure に実装 +
  Composition Root で注入」。中核クラスは変更しない（家風: core 無変更）

## 命名規則

プロファイルに記載があればそれを優先。無い場合の既定:

- 契約（インタフェース）: `Base` 接頭辞 + PascalCase（例: `BaseTool`）
- 実装クラス: 具体性がわかる PascalCase（例: `PostgresUserRepository`）
- デコレータ実装: 役割 + 被装飾対象（例: `TracingLLMClient`）
- 関数・メソッド・変数: 言語の慣習に従う。内部ヘルパは可視性を落とす
- 定数: UPPER_SNAKE_CASE
- エンティティ: 不変（イミュータブル）を基本とする

## docstring 規約（実装コード）

すべての関数・クラスに「役割」を書く。引数・戻り値があれば明記する。

```python
class Spinner:
    """生成待ちの間、背景スレッドでスピナーを描画する責務を持つ。"""

def should_animate(stream: TextIO, no_color: str | None) -> bool:
    """スピナーを描画すべきかを判定する。

    Args:
        stream: 出力先ストリーム。
        no_color: 環境変数 NO_COLOR の値（未設定は None）。

    Returns:
        TTY かつ NO_COLOR 未設定のとき True。
    """
```

（上は Python の例。他言語ではその言語の標準的な docstring / doc comment
形式に読み替える。書く項目「役割・引数・戻り値」は共通）

## テストコード規約

- 置き場所: テストルート配下でソースの層構成をミラーする
- 各テスト関数の docstring に4項目を必ず書く:

```python
def test_spinner_disabled_writes_nothing():
    """テスト対象: Spinner(enabled=False) の start/stop
    入力: enabled=False で start() → stop() を呼ぶ
    期待値: ストリームに何も書き込まれない
    理由: 非 TTY 環境では装飾を一切出さない仕様のため（no-op が安全動作）
    """
```

- 外部依存（ネットワーク・時計・ストリーム・DB）はフェイクを注入して検証する
  （ネットワークに出るテスト・本物の外部サービスに触るテストを書かない）
- エッジケース（空入力・失敗経路・冪等性・境界値）を設計書の
  「テスト観点」から漏らさず翻訳する

### 単体テストと統合テストの境界

| | 単体テスト | 統合テスト |
|---|---|---|
| 起点 | 設計書の「テスト観点」 | 要求仕様書の「受け入れ条件」 |
| 対象 | 1 クラス・1 関数の振る舞い | Composition Root 経由で組んだ実物の経路 |
| フェイク | 依存はすべてフェイク可 | 外部境界のみフェイク |
| 担当 | tdd-implementer | integration-tester |

## エラー処理の家風

- **フェイルソフト（実行時の想定内の失敗）**: 例外で処理全体を壊さず、
  結果値（成功/失敗を持つ型）として呼び出し元に返す
- **フェイルクローズ（オプトイン機能の前提欠如）**: 設定・外部コマンド・
  実行環境が無ければ機能ごと無効化する。黙って劣化した動作で続けない
- 失敗時の結果には常に情報を持たせる（空文字・null で終わらせない）
- 表示装飾（ANSI 等）をデータ・履歴・ログに混入させない

## 依存の追加

- 依存追加の可否は **プロファイルの「依存方針」に従う** 。方針と矛盾する
  追加は、依頼されてもブロッカーとして報告する
- 追加する場合はプロファイルのパッケージマネージャのコマンドを使う
  （別のツールを推測で使わない）
