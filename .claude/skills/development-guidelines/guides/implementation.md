# 実装ガイド

規約を実装時にそのまま使える形に展開したガイド。
言語固有の書式（docstring の形式・命名の慣習）は
**プロファイルの「言語・スタイル」節を正とする** 。以下は一般形と例。

層の配置と依存ルールは **`layered-architecture` スキルを正とする**
（ここでは重複させない）。覚えるのは 2 つ ——
「下の層が上の層を import しない」と「外部 I/O は契約を介す」。

## 成熟度別「今どこまで書くか」

実装を始める前に、対象スライスの **目標成熟度** を確認する
（`docs/backlog.md` の成熟度列。完了条件の正は `agile-process/maturity.md`）。

| | L1 動く | L2 固い | L3 整った |
|---|---|---|---|
| ファイル分割 | 4 層に分ける（1 層 1 ファイル可） | 責務ごとに分ける | 同 + 重複の統合 |
| 依存の向き | 内向き（違反は負債に記録する） | 同 | 違反ゼロ |
| 契約（Port） | 外部 I/O があれば 1 本 | 外部 I/O はすべて契約経由 | 同 + フェイクを備える |
| 配線 | 入口で直接注入してよい | Composition Root 1 か所 | 同 |
| docstring | 不要 | 公開する関数・クラスのみ | 全関数・クラス |
| 型注釈 | 不要（言語が要求しなければ） | 公開する境界のみ | 全体 |
| 定数化 | 不要（ハードコード可） | 設定・引数へ | 同 |
| エラー処理 | 不要（落ちてよい） | 想定内の失敗は結果値で返す | ＋利用者に読めるメッセージ |
| ログ | 不要 | 失敗経路のみ | 必要な箇所 |

**L1 で「きれいに書こう」としないこと。** 骨組みが通る前の整形は、
通った後に高い確率で作り直しになる。整えたい欲は負債表に書いて発散させる。

## 命名規則

プロファイルに記載があればそれを優先。無い場合の既定:

- 関数・メソッド・変数: 言語の慣習に従う。内部ヘルパは可視性を落とす
- 定数: UPPER_SNAKE_CASE
- クラス: 具体性がわかる PascalCase（例: `CsvRowCounter`）
- 契約（インタフェース。L2 以降で作る場合のみ）: `Base` 接頭辞 + PascalCase
- 実装クラス: 何の実装か分かる名前（例: `PostgresUserRepository`）
- エンティティ・値: 不変（イミュータブル）を基本とする

**L1 では名前が雑でよい** 。命名の統一は `/refactor` の「名前を変える」変換で
まとめて返す（そのとき初めて何が良い名前か分かることが多い）。

### 識別子は ASCII（成熟度に関係なく必須）

Python などは日本語の識別子も構文として通るが、 **使わない** 。
日本語の説明は docstring に書く（`unittest -v` は docstring の 1 行目を
テスト名の隣に出すので、読みやすさは落ちない）。

```python
def test_rejects_duplicate_spec_number(self):
    """仕様番号の重複を落とす。"""
```

**理由**: 端末の文字コードが UTF-8 でないと識別子が化ける。実測で
`test_日本語と…` が `test_���{���…` になり、 **どのテストが落ちたのかが
読めなくなった** 。テスト名が読めないテストは、失敗したときに役に立たない。

Python は `check_py_names.ps1` が機械的に検査する（PostToolUse フックが
編集のたびに走り、`.claude/tools/test_check_py_names.py` がリポジトリ全体を
毎回のテストで検査する）。他の言語では規約として守る。

## docstring 規約（実装コード）

L2 以上で書く。すべての関数・クラスに「役割」を書き、引数・戻り値があれば明記する。

```python
class Spinner:
    """生成待ちの間、背景スレッドでスピナーを描画する責務を持つ。"""

def should_animate(stream: TextIO, no_color: str | None) -> bool:
    """スピナーを描画すべきかを判定する。

    Args:
        stream: 出力先ストリーム。
        no_color: 環境変数 NO_COLOR の値（未設定は None）。

    Returns:
        TTY かつ NO_COLOR 未設定のとき True。
    """
```

（上は Python の例。他言語ではその言語の標準的な doc comment 形式に
読み替える。書く項目「役割・引数・戻り値」は共通）

## テストコード規約（成熟度に関係なく必須）

**テストは省かない。** 省くのは前工程の文書と構造であって、テストではない。

- 置き場所: テストルート配下。L2 以上ではソースの構成をミラーする
- E2E / 統合テストはプロファイルの「統合テスト」パスに置く
- 各テスト関数の docstring に 4 項目を必ず書く:

```python
def test_spinner_disabled_writes_nothing():
    """テスト対象: Spinner(enabled=False) の start/stop
    入力: enabled=False で start() → stop() を呼ぶ
    期待値: ストリームに何も書き込まれない
    理由: 非 TTY 環境では装飾を一切出さない仕様のため（no-op が安全動作）
    """
```

- 外部依存（ネットワーク・時計・ストリーム・DB）はフェイクを注入して検証する
  （ネットワークに出るテスト・本物の外部サービスに触るテストを書かない）
- L1 で書くのは **E2E 1 本 + 芯のロジックのユニット** だけ。
  境界値・失敗経路は L2 の反復で足す（先に網羅すると反復が終わらない）

### ユニットテストと E2E の境界

| | ユニットテスト | E2E / 統合テスト |
|---|---|---|
| 起点 | 薄い設計の「流れ」 | スライス文書の「仕様」 |
| 対象 | 1 関数・1 クラスの振る舞い | 入口を叩いて出口を見る |
| 内部構造への依存 | あってよい | **無いこと**（構造は成熟度で変わる） |
| フェイク | 依存はすべてフェイク可 | 外部境界のみフェイク |
| 担当 | unit-tester・coder | integration-tester |

E2E が内部構造（クラス名・シグネチャ）に依存していると、
リファクタリングのたびに壊れて負債を返せなくなる。 **入口と出口だけを見る。**

## エラー処理の型（L2 以上）

- **フェイルソフト（実行時の想定内の失敗）**: 例外で処理全体を壊さず、
  結果値（成功 / 失敗を持つ型）として呼び出し元に返す
- **フェイルクローズ（オプトイン機能の前提欠如）**: 設定・外部コマンド・
  実行環境が無ければ機能ごと無効化する。黙って劣化した動作で続けない
- 失敗時の結果には常に情報を持たせる（空文字・null で終わらせない）
- 表示装飾（ANSI 等）をデータ・履歴・ログに混入させない

**L1 では例外で落ちてよい** 。スタックトレースが出るだけで十分
（誰も使っていない段階で読めるメッセージを整えるのは早すぎる）。

## 依存の追加

- 依存追加の可否は **プロファイルの「依存方針」に従う** 。方針と矛盾する
  追加は、依頼されてもブロッカーとして報告する
- 追加する場合はプロファイルのパッケージマネージャのコマンドを使う
  （別のツールを推測で使わない）
- **骨組みの段階で依存を増やさない** 。標準ライブラリで通るなら通す
  （通した後に必要性が判明したら足す）

## 手抜きの記録（L1 の中核ルール）

**記録された手抜きだけが許される。書かずに残すことだけが規約違反。**

実装中に「本当はこうすべきだが今はやらない」と思ったら、その場で
スライス文書の「残した手抜き」表に 1 行足す。

| 内容 | 痛み | 返す条件 |
|---|---|---|
| 出力先を標準出力にハードコード | 低 | ファイル出力の要求が出たとき |
| presentation から infrastructure を直接呼んでいる | 中 | 同じ逆流が 2 か所目に出たとき |

痛みは 高（次の反復を遅くする）/ 中（読みにくい）/ 低（気になるだけ）。
反復の終わりに `docs/backlog.md` の負債表へ転記する。
