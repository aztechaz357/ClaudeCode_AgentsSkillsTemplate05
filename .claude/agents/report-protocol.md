# サブエージェント共通レポートプロトコル（レポート駆動）

**すべてのサブエージェントは、作業の前後でこのプロトコルに従うこと。**

エージェント間でコンテキストは共有されない（Task ツールの終了とともに
サブエージェントのコンテキストは破棄される）。そのため、構造化ノート
（`.steering/` 配下のファイル）が **唯一の情報共有手段** である。
「詳細はファイルに、応答には要約だけ」を徹底する。

## 0.1 役割の並び（8 点セットを 8 段で回す）

反復 1 回は、成果物 1 つにつき 1 役で流れる。 **前の役のレポートを読んでから
自分の作業を始める** （読まずに始めると、前の役の判断が失われる）。

| 段 | 役割 | 成果物 | 読む | 書く |
|---|---|---|---|---|
| 1 | `requirement-writer` | 要求仕様書 | backlog・concept | `01-requirement-writer.md` |
| 2 | `designer` | 設計書 | 01・要求 HTML | `02-designer.md` |
| 3 前半 | `test-designer` | テスト観点の合意（コードは書かない） | 01・02 | `03a-test-designer.md` |
| 3 | `unit-tester` | 単体テスト（Red まで） | 01・02・03a | `03-unit-tester.md` |
| 4 | `coder` | 実装（Green まで） | 02・03 | `04-coder.md` |
| 5 | `integration-tester` | 統合テスト | 01・04 | `05-integration-tester.md` |
| 6 | `test-summarizer` | テスト結果まとめ | 03・04・05 | `06-test-summarizer.md` |
| 7 | `manual-writer` | マニュアル | 01・06 | `07-manual-writer.md` |
| 8 | `implementation-validator` → `doc-syncer` | 判定・記録 | すべて | `08-*.md` / `09-doc-syncer.md` |

**自分の段の成果物だけを作る。** 隣の段の成果物に手を出すと分業が壊れる
（特に `unit-tester` が実装を書く／`coder` がテストを直す のは禁止）。

作業を終えたら、レポートに加えて `.steering/<反復>/INDEX.md` に
**1 行だけ追記する**（時刻・段・誰が・何をした・触ったもの）。
これはユーザーが後から追うための履歴なので、書き換えず追記だけを行う。

## 0. 動作原理: 知覚-行動ループ（全エージェント共通）

すべてのエージェントは「環境 → 知覚 → 判断 → 行動 → 環境の反応 → 知覚 …」の
ループで動く。 **記憶（会話コンテキスト）ではなく環境を正とする** 。
環境とは、リポジトリ（コード・docs・git 状態）と `.steering/` のノート、
コマンドの実行結果である。

1. **知覚**: Tool（Read / Grep / Glob / Bash）で環境を読む
   （ノート・コード・git 状態・テスト結果）。推測で状態を仮定しない
2. **判断**: 依頼内容と完了条件に照らして、次の行動を 1 つ決める。
   **LLM が考えるプロセスは最小に** する —— 判断基準・チェックリスト・
   テンプレートが定義済みならそれに従い、その場の創意で手順を変えない
3. **行動**: **必ず Tool を通して** 環境に働きかける（Write / Edit による
   ファイル変更・Bash によるコマンド実行・レポートの書き出し）。
   Tool を使わない「行動したつもり」—— テキストに書いただけの結論、
   実行していないコマンドの結果の推測 —— は禁止
4. **環境の反応**: Tool の結果（ファイル内容・終了コード・テスト出力・
   エラー）を次の知覚として取り込み、1 に戻る
5. 完了条件を満たしたらレポートを書き出して終了する
   （レポートの書き出しも Write による行動）

行動に必要な Tool・スクリプトが環境に無い場合は、その場しのぎの複雑な
ワンライナーで済ませず、 **まずツールを作ることを検討する** 。自分の権限で
作れないときは「ツール不足」としてレポートの「引き継ぎ」に記録する
（ツールの新設は `tool-authoring` スキルのフロー: エージェント → スキル →
ツールの順で作る）。

## 0.5 プロジェクトプロファイル（コマンド・パスの正）

テスト・ビルド・実行のコマンド、ソース・テストの配置、層構成などの
プロジェクト固有値は、 **リポジトリ直下の `CLAUDE.md` の
「プロジェクトプロファイル」節を正とする** 。作業前に必ず読むこと。

- コマンド・パスを推測や他プロジェクトの記憶でハードコードしない
- プロファイルに必要な項目が無い場合は、勝手に決めずブロッカーとして
  報告する（プロファイルの整備は `/setup-project` の領分）

## 1. 作業ディレクトリの決定

1. 親のプロンプトに `.steering/[YYYYMMDD]-[タスク名]/` のパスが渡されていれば
   それを使う
2. 渡されていなければ `.steering/` 配下を確認し、進行中とわかるディレクトリが
   あればそれを使う
3. どちらも無ければ `.steering/[今日の日付YYYYMMDD]-adhoc/` を作成して使う

## 2. 開始時: 経緯の回復（何を読むか）

**リポジトリの文書が正で、`.steering/` は作業メモ** 。この順に読む。

1. **`docs/backlog.md`** —— 進捗・成熟度・負債の正。対象スライスの
   現在の成熟度と、記録済みの負債をここで把握する
2. **対象の要求**（`docs/usdm/src/S##-*.html`）—— 要求・理由・仕様・
   トレース表。 **要求の正はここ 1 か所** （厚い経路でも同じ）
3. **対象の設計書**（`docs/design/S##-*.md`）—— 層・契約・入口・
   **判断の記録** 。 **設計の正はここ**
   （厚い経路では `docs/requirements/S##-*.md` と
   `docs/design/proposals/S##-*.md` が加わる）
4. **ハブ**（`docs/slices/S##-*.md`）—— 8 点セットへの索引・実績・
   残した手抜き。どの成果物がどこにあるかはここで分かる
5. 作業ディレクトリ内の存在するファイル:
   - `tasklist.md`（8 点セットのチェックリスト）/ `INDEX.md`（反復ログ）
   - `decisions.md`（重要な決定事項）/ `blockers.md`（ブロッカー）
   - `reports/` 配下の既存レポート（ **前の段のものは必ず読む** 。
     それ以外は自分の作業に関係するものを選んで読む）

**正を抜粋した中間ファイルは作らない・探さない** 。`.steering/` に
要求や設計を書き写すと、正とドリフトして事故になる（判断メモは
`decisions.md` へ、恒久的に残す判断はスライス文書の「決めたこと」へ）。

自分の依頼内容と矛盾する決定が decisions.md にある場合は、勝手に上書きせず
レポートの「引き継ぎ」で親に報告する。

## 2.4 関与モードの確認（省略禁止）

**どこで止まって選択肢を出すか** は関与モードで決まる。正の順序:

1. 親のプロンプトの「関与モード: {伴走 / 既定 / 任せる}」
2. 書かれていなければ `CLAUDE.md` の「関与モード」節の `- モード:` の行
3. どちらでも分からなければ **`既定` と仮定し、レポートに明記する**

| モード | 振る舞い |
|---|---|
| `伴走` | 成果物を **書く前に** 選択肢を出して待つ（段0〜段3 の役のみ） |
| `既定` | 判断点に当たったときだけ聞く（`option-first` の 3 つ） |
| `任せる` | 聞かない。決めた理由と却下案を記録に残す |

規約の正は `Skill('option-first')` 。段4 以降の役（`coder`・
`integration-tester`・`test-summarizer`・`manual-writer`・`doc-syncer`）は
**どのモードでも聞かない** —— そこは判断ではなく翻訳作業。

## 2.5 目標成熟度の確認（省略禁止）

このプロジェクトは **まず完走 → インクリメンタルに改善** で進む。
規約をどこまで守るか・何を完了とするかは **成熟度で変わる** 。
完了条件の正は `.claude/skills/agile-process/maturity.md` 。

1. 親のプロンプトの「現在 L{n}、目標 L{n+1}」を読み取る
2. 書かれていなければ `docs/backlog.md` の成熟度列を見る
3. どちらでも分からなければ **L1 と仮定して進み、レポートに明記する**

そして次の 2 つを守る:

- **判定は「現在 → 目標」の 1 段だけ** 。上のレベルの条件
  （層の分離・重複除去・文書整備）で不合格にしない。
  上のレベルに該当する所見は **負債候補** として、痛みと返す条件を
  添えて別枠に書く
- **目標より上のレベルの作業をしない** 。L1 の依頼で失敗経路を網羅する・
  契約を増やす・文書を作り込むのは越権（次の反復の仕事）

L1 では仮実装・ハードコード・エラー処理の欠落が許される。
ただし **残した手抜きの記録は必須** —— ハブの「残した手抜き」と
`docs/backlog.md` の負債表に書く。書かずに残すことだけが規約違反。

**成果物の種類はどのレベルでも 8 点で固定** （`agile-process/deliverables.md`）。
薄くするのは中身であって、成果物を落とすことではない。
「今回は L1 だからマニュアルは無し」は、どのレベルでも認められない。

## 3. 終了時: レポートの書き出し（必須）

`reports/[NN]-[エージェント名].md` に書き出す。`NN` は 2 桁連番
（reports/ 内の既存最大値 + 1。初回は 01）。形式:

```markdown
# [NN] [エージェント名]: [依頼の一言要約]

- 日時: YYYY-MM-DD HH:MM
- 依頼内容: （親からのプロンプトの要約）
- 対象と成熟度: S## / 現在 L{n} → 目標 L{n+1}（親の指示 / backlog / L1 と仮定）
- 参照したもの: （読んだ backlog・スライス文書・steering ファイル・レポート）

## 結論（3 行以内）

## 所見

### [必須]（目標レベルの条件違反・放置すると壊れる）
- **箇所**: `パス:行` / **内容**: … / **対処案**: …

### [推奨] / ### [提案]

### [負債候補]（目標より上のレベル向け。[必須] に混ぜない）
- **内容**: … / **痛み**: 高/中/低 / **返す条件**: … / **向け先**: L{n+2}

## 知覚・行動ログ

（時系列で「知覚: 何を読んだか / 行動: 何を実行したか / 反応: 結果は
 どうだったか」を記録する。次のエージェントが検証をやり直さなくて済む粒度。
 このログはプロセス改善の分析材料でもある —— 無駄な試行・手戻りも隠さず残す）

## 引き継ぎ（親・次のエージェントへ）

- （未解決の点・確認してほしい判断・次にやるべきこと・ツール不足）
```

該当が無いセクションは「なし」と明記する（省略しない）。

## 4. 共有ノートへの追記

- 作業中に **重要な決定**（設計判断・方針の確定）に相当する事実を見つけたら
  `decisions.md` に日付付きで追記する（無ければ作成）
- 作業を完了できない **ブロッカー**（環境不備・前提の欠落・ユーザー判断待ち）
  に当たったら `blockers.md` に日付付きで追記する（無ければ作成）
- **残した手抜き・見つけた手抜き** は `docs/backlog.md` の負債表へ
  （`D##` を採番し、痛みと返す条件を書く）。`.steering/` は捨てられるので、
  後で返す必要があるものをここに置いてはならない

## 5. 親への応答

応答は次の 2 点だけに絞る（詳細を応答に展開しない。親のコンテキストを
守るのがサブエージェントの存在意義）:

1. レポートのパス（例: `.steering/20260719-P03-user-auth/reports/02-test-analyzer.md`）
2. 結論の要約（5 行以内。[必須] の件数と最重要事項を含める）
