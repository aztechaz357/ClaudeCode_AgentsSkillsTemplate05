# フックが約 99% 失敗していた原因（stdin のコードページ）と直し方の判断

## 要点

- `PreToolUse` / `PostToolUse` のフックが **約 99% の実行で落ちていた** 。
  保護（凍結パスと破壊的コマンドの拒否）は無効なまま、1 編集あたり
  約 1.1 秒だけを払っていた
- 原因は `[Console]::In.ReadToEnd()` —— **stdin をコンソールの入力コード
  ページ（cp932）で復号していた**
- 直し方は **共有部品 `lib-hook.ps1` に 1 箇所** 置き、各フックが
  dot-source する形にした。同時に回帰テストを新設した

## 背景 / きっかけ

`/doctor` の集計で判明した。

| フック | 実行回数 | エラー率 | 中央値 |
|---|---|---|---|
| `pre-tool-guard` | 618 | 約 99% | 約 500 ms |
| `post-edit-markdown` | 1,429 | 約 98% | 約 620 ms |

エラーは `認識できないエスケープ シーケンスです。` と
`':' または '}' ではなく無効なオブジェクトが渡されました。` の 2 種類。
どちらも `ConvertFrom-Json` が投げていた。

フックはフェイルオープン（終了コード 1 で非ブロッキング）に作ってあるため、
**落ちても作業は止まらない** 。それがちょうど、壊れていることに
1,000 回以上気づけなかった理由でもある。

## 中身

### 原因

Claude Code は payload を **UTF-8 のバイト列** で stdin に書く。一方
`[Console]::In` は `[Console]::InputEncoding` で復号する。日本語 Windows では
これが **cp932** になる。

cp932 は先行バイト（`0x81-0x9F` `0xE0-0xEF`）を見ると次の 1 バイトを
後続バイトとして食う。UTF-8 の日本語 1 文字は 3 バイトなので、
日本語が続くと **バイトの位置合わせが 1 つずれる** 。そして
cp932 の後続バイト範囲（`0x40-0x7E` `0x80-0xFC`）には **`0x5C`（`\`）が
含まれる** 。

結果、日本語の直後の `\\` が 1 本食われる:

```
入力（UTF-8）:  "あ\\Users"
cp932 で復号:   "ぁE\Users"        ← `\` が 1 本消えた
ConvertFrom-Json → 認識できないエスケープ シーケンス（\U）
```

`\"` が食われれば文字列が早く閉じ、こちらは
`':' または '}' ではなく無効なオブジェクト` になる。エラーが 2 種類
あったのはこのため。

**「日本語の本文」と「Windows のパス」が同居する payload** —— つまり
このプロジェクトのほぼ全ての編集 —— で起きる。

### 決定1: 共有部品に切り出す（各フックへコピペしない）

- **採用**: `lib-hook.ps1` に `Read-HookPayload` と `Set-HookOutputUtf8` を
  置き、各フックが `param()` の直後に dot-source する。
  **そう考えた理由**: この不具合は「同じ 3 行が 6 本のフックへコピペ
  されていた」から 6 本まとめて壊れた。 **同じ壊れ方を繰り返させない**
  ことが、1 ファイル増えるコストより重い
- **他の選択肢**:
  - 案B「各フックに同じ関数を複製する」
  - 案C「`[Console]::InputEncoding` を UTF-8 に設定する」
- **メリット / デメリット**:
  - 採用案 = 直す場所が 1 つ / フックが単体のファイルでなくなり、
    README の「1 本ずつ他 OS へ移植する」話に部品が 1 つ増える
  - 案B = 各フックが自己完結のまま移植できる / 次に誰かが新しいフックを
    書くとき、**壊れていた方をコピペする危険が残る**
  - 案C = 1 行で済む / stdin が既にリダイレクト済みだと設定が効かない
    場合があり、環境依存の直し方になる。
    `OpenStandardInput()` を直接読めばコードページは最初から関係ない

### 決定2: 「拒否できること」と「壊れないこと」を両方テストする

- **採用**: `.claude/hooks/test_hooks.py`（15 本）を新設し、フックを
  **実プロセスとして起動** して検証する。各フックについて
  ① 拒否すべき入力で deny / findings が出る
  ② 日本語 + `\\` を含む payload で **標準エラーが空** である
  の 2 種類を持たせた。
  **そう考えた理由**: ① だけなら今回も緑のままだった（壊れた payload は
  例外になり、テストは正常系しか通っていない）。 **フック自身の失敗を
  落とせる assertion** が無いと、フックのテストは意味を持たない
- **他の選択肢**: 案B「README の手動チェックリストのままにする」
- **メリット / デメリット**:
  - 採用案 = 回帰を機械で落とせる / PowerShell の起動が 15 回で
    約 8 秒かかる（速いテストではない）
  - 案B = 追加コスト 0 / 今回まさに 1,000 回以上見逃した方法

罠となる文字列は `TRAP = "あ\\Users"` として定数に置いた。
なぜこの並びが壊れるのかはテストの冒頭コメントに書いてある。

### 決定3: 識別子は ASCII にし、機械で守らせる

- **採用**: Python の識別子は ASCII、説明は docstring に日本語で書く
  （`unittest -v` は docstring の 1 行目を併記する）。既存の
  `.claude/tools/test_*.py` 4 本にあった **73 個の日本語メソッド名も
  すべて改名** し、元の日本語はそのまま docstring に移した。
  **そう考えた理由**: 最初は既存に合わせて日本語のメソッド名で書いたが、
  **Red の出力でテスト名が化けてどれが落ちたか読めなかった** 。
  テスト名が読めないテストは、失敗したときに役に立たない
- **他の選択肢**:
  - 案B「既存に合わせて日本語のメソッド名のままにする」
  - 案C「規約として書くだけで、機械検査は付けない」
- **メリット / デメリット**:
  - 採用案 = 端末のコードページに関係なく読める。改名は機械的で
    意味を失わない（説明は docstring に残る） / 既存 4 ファイルの
    差分が大きくなる（73 行の改名 + 73 行の docstring 追加）
  - 案B = 差分ゼロ / 失敗時に名前が読めない状態が続く
  - 案C = すぐ書ける / **今回まさに規約が無かったのではなく、
    守られていることを誰も確かめていなかった** 。同じことが起きる

守らせ方は 2 段構えにした。

| いつ | 何が走るか |
|---|---|
| `.py` を編集した直後 | `post-edit-python.ps1`（PostToolUse フック）がその 1 ファイルを検査し、NG を Claude に差し戻す |
| テストのたび | `test_check_py_names.py` がリポジトリ全体を検査する |

フックだけだと、フック無しで書かれたコード（他の環境・過去のコード）が
すり抜ける。テストだけだと、気づくのが遅れて直す量が増える。

検査は日本語を **識別子の位置でだけ** 落とす。引数の既定値・docstring・
コメントの日本語は誤検出しない（三重引用符の中の `def` も数えない）。

## 次にやること

- 識別子の ASCII 検査は Python だけ機械化した。他の言語を足すときは
  `check_py_names.ps1` と同じ形の検査を用意し、`post-edit-*.ps1` に配線する
- `post-edit-lint.ps1` の `Invoke-Expression` は `-Command` の値を
  そのまま実行する。settings.json から渡す値なので現状は安全だが、
  外から来る値を混ぜないこと
